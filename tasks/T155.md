## Task

A movement (protocol v4) session cannot survive a dropped connection, so the
dedicated server does not serve movement, so the dedicated smoke cannot move
(D71a). Three facts, in code:

- The host refuses to hold a v4 session through a grace:
  `resumable_kind` is `session.snapshot && !v4`
  (`crates/crpg-server/src/host.rs:5514–5516`), so `issue_resume_ticket` and
  `begin_grace` answer `NotResumable` (`:5183–5184`, `:5217–5222`; T025b
  Reading 3, `tasks/T025b.md:88–95`).
- The movement endpoint takes no resume opening: `bind_movement` is
  `bind_setup(.., &[V2], false, true)`
  (`crates/crpg-net-quic/src/server.rs:248–250`), and the client has no
  movement resume call (`crates/crpg-net-quic/src/client.rs:287–372` is `/2`
  only).
- The dedicated binary binds `bind_resumable` and `start_resumable` and
  registers only `/1`/`/2` invitations (`crates/crpg-server/src/main.rs:602–618`;
  T040 Reading 8, `tasks/T040.md:152–158`).

The row's other prerequisite, "the QUIC v4 route", is done: T150c merged it
(`crates/crpg-server/src/quic.rs:1353–1452`, `:1723–1791`).

**A latent defect this task removes.** `QuicHost::start_resumable` over a
`bind_movement` server poisons the adapter on the first `/3` hello: the hello
path issues a ticket for every `Framing::V2` binding
(`crates/crpg-server/src/quic.rs:1536`), a `/3` binding is `V2` (`:1412–1414`),
the host answers `NotResumable` for v4, and `let bytes = result?;` (`:1549`)
returns it into `pump`, which poisons (`:973–975`). No caller does this today
(the binary binds `bind_resumable`), and T025b's N-1 says `start_resumable`
takes "any `QuicServer::bind*`". T155a makes the ticket succeed.

## Readings

1. **A v4 session resumes through the v3 path it already has.** The host's
   resume for a v3 session plans and commits `plan_stage(.., Resume)` with
   `commit_v3_stage(.., None)` (`crates/crpg-server/src/host.rs:5363–5385`,
   `:5452–5466`), and `plan_stage` dispatches a v4 session to
   `plan_v4_stage` (`:2808–2819`), whose snapshot clears the position
   view's "told" set (`project_snapshot_v4`,
   `crates/crpg-net/src/positions_v4.rs:252–265`), so the staging page
   re-anchors every granted, present mover (T037 B-7, `tasks/T037.md:626–636`).
   Lane 0 of a v4 session therefore needs no new resume code: only
   `resumable_kind` changes. *Rejected:* a v4-specific snapshot path (it
   would duplicate B-7).
2. **Lane 1 needs no progress on the resume wire (Question 1 (a)).** The
   client recovers lane 1 by resending `MoveOutbox::pending` after a resume
   (the outbox's own rule, `crates/crpg-net/src/outbox_v4.rs:5–7`, `:87–90`).
   A resent intent the host already answered is a duplicate answered from
   the lane-1 cache with its original receipt (T037 D-4,
   `tasks/T037.md:758–763`; the cache holds 256 entries, the window is 8,
   `:743–755`); one the host never answered is admitted as new (Reading 3).
   Every sample also carries the host's lane-1 `processed_seq`
   (`crates/crpg-net/src/movement_v4.rs:143–147`; T037 C-5), so the client
   learns lane-1 progress within one tick. A lane-1 entry in the resume
   answer would add nothing the client can act on. Resume v1 refuses any
   lane but 0 (`crates/crpg-net/src/protocol_resume.rs:303–305`,
   `crates/crpg-net/src/codec_resume.rs:62–64`), so carrying lane 1 needs a
   new resume version (Question 1 (b)). *Rejected:* widening resume v1's
   lane rule (changes the decode result of bytes a frozen version refuses,
   and edits `crpg-net` tests).
3. **Unanswered lane-1 intents are un-admitted at grace start and at
   resume.** At those two points the host drops the session's lane-1 slots
   (admitted, no receipt released), its released-but-untaken receipts and
   its queued samples, frees their egress, and moves the lane's next
   sequence back to the first dropped slot. Slots always hold the
   contiguous sequences `[front.seq, next_seq − 1]` (each admitted sequence
   gets one slot; slots release from the front in order, D-3,
   `tasks/T037.md:743–756`), so afterwards `next_seq == processed_seq + 1`.
   No dropped slot had any effect (decisions happen only in `advance`, D-5,
   `:765–768`; a `NotAuthorized` slot changes nothing), so nothing executes
   twice, and each resent intent gets exactly one receipt (L3). This is
   T025b Reading 8's purge for lane 1, and Reading 7's log discard for its
   receipts. *Rejected:* keeping the slots frozen through the grace and
   deciding them after resume (the graced session would hold up to eight
   egress reservations, against T025b G-4's "holds no egress", and the
   client resends them anyway); keeping the receipt queue (a client whose
   resend crosses an untaken receipt would receive it twice). ADR-0032 H6
   ("never reset `next_new_seq`") is kept for lane 0; for lane 1 the reset
   is of sequences no receipt was ever issued for ("Manager edits").
4. **A live resume resets lane 1 too.** T025b Reading 9 lets a live session
   be resumed; its old connection may still have receipts in flight. The
   same reset at the resume commit makes the rule one rule: after
   `Accepted`, the host holds no lane-1 slot, receipt or sample for the
   session, and the client resends its pending intents once. *Rejected:*
   resetting only after a grace (a live resume would then deliver queued
   receipts beside the client's resends: duplicates).
5. **The `/3` resume opening is `/2`'s, on a new endpoint (Question 2 (a)).**
   A `/3` connection's first stream is the `/2` lane stream exactly (T150
   Reading 2, `tasks/T150.md:148–157`), and on `/2` the resume opening is an
   endpoint option, not an ALPN property: `bind_dual` refuses it and
   `bind_resumable` takes it (`crates/crpg-net-quic/src/server.rs:234–243`).
   The opening reader already takes `resumable` and `movement` separately
   (`:1109–1137`). So `bind_movement_resumable` is `bind_movement` with the
   flag on, the same ALPN and transport parameters, and `bind_movement`
   keeps refusing the opening (its test
   `crates/crpg-net-quic/tests/movement.rs:333–374` stays byte-identical).
   After an accepted resume the client opens stream 2 for lane 1, exactly as
   after a welcome (`crates/crpg-net-quic/src/client.rs:987–998`). *Rejected:*
   a new ALPN `crpg-lane0/4` (a second movement label for the same bytes);
   changing `bind_movement` (edits T150b's approved rule and its test).
6. **`accept_resume` must claim the lane-1 reader on a movement
   connection.** `accept` sets `lane1_reader_active = record.movement`
   (`crates/crpg-net-quic/src/server.rs:427`) and a close is published only
   when both reader claims are released (T150 N-11 (4),
   `tasks/T150.md:776–780`); `accept_resume` sets only `reader_active`
   (`:453–456`). On a movement connection it must set both, or a close could
   be published while lane-1 frames are still being read.
7. **Resume is checked by connection kind only through the adapter's one
   server.** A `QuicHost` owns one `QuicServer`, `start` refuses a host with
   any session (`HostInUse`, `crates/crpg-server/src/quic.rs:927–935`), and
   the host is reachable only as `&Host` (`:2676`), so every session on a
   movement adapter is v4 and every snapshot session on a `/2` adapter is
   not. A v4 epoch can therefore never be resumed over `/2` or the reverse.
   *Rejected:* a kind check in `resume_peer` (a new parameter for a case the
   ownership rule already excludes).
8. **Lane-1 frames are fence-checked like lane-0 frames.** ADR-0032 H2 says
   "every inbound frame of a bound connection"; T025b-q checks lane-0 frames
   (`crates/crpg-server/src/quic.rs:1635–1664`) and T150c's lane-1 drain
   does not (`:1745–1762`), because no resumable movement binding existed.
   The check is traced as the existing `HostCall::CheckFrame` in `calls`, so
   no exhaustive replay match changes (T150 Reading 13, `tasks/T150.md:292–300`).
   *Rejected:* skipping it because `retire_resumed` runs before the answer
   (true today, but H2 is the rule the fence exists for).
9. **Lane-1 refusals are rejected client messages.** T040 Reading 5 left
   lane-1 traces out because the dedicated endpoint carried no lane 1
   (`tasks/T040.md:124–125`). Once it does, D67a's "a log line for every
   rejected client message" covers lane-1 frames refused before admission
   (except `QueueFull`, which is held and retried, T150 Reading 14) and
   intents refused at admission (`MoveAdmission::Rejected`, D-2 step 9).
   Intents refused later, in the decision window (`WrongMode`,
   `IllegalAction`, D-7), are not in a pump report (`advance` decides them,
   `crates/crpg-server/src/run.rs:941–943`) and are out of scope.
10. **The dedicated server serves one wire per world, chosen by the operator
    (Question 3 (a)).** One `QuicHost` serves one endpoint kind (ADR-0026
    item 1; T150 Question 1's answer: a movement world is v4-only,
    `tasks/T150.md:1666–1686`). A `"movement": true` configuration key
    selects `bind_movement_resumable` and v4 invitations; without it the
    binary is byte-for-byte T040b's, so T040b's suite and T041d's smoke are
    unchanged. A movement world needs a navigation mesh to route anything,
    so `movement` without `area` is a configuration error. *Rejected:*
    movement always (breaks T041d's `/1` smoke and T040b's suite); two
    endpoints for one world (needs `QuicHost` to own two servers, an
    ADR-0026 change).

## Behaviour
Normative. **First failure wins** in every ordered list. "Refused" means the
stated result and no state change.

### T155a — the host
H-1. **v4 sessions are resumable.** `resumable_kind(session)` is
`session.snapshot`: true for every `bind_snapshot_peer`, `bind_v3_peer` and
`bind_v4_peer` session (`bind_v4_peer` builds a snapshot session,
`crates/crpg-server/src/host.rs:1401`), false for `bind_peer`. Every
precedence of T025b G-2, G-3 and G-6 is unchanged. *Tests:* V1, and the
sanctioned G13 line.

H-2. **`reset_lane1(egress_bytes, session)`**, a no-op unless the session has
v4 state; otherwise, in order: (1) `freed = session.lane1_egress().1`
(`:800–805`); (2) if `lane.slots` is not empty, `lane.next_seq =
lane.slots.front().seq`; (3) clear `lane.slots`, `lane.receipts` and
`v4.samples`; (4) `*egress_bytes -= freed`. Unchanged: `processed_seq`, the
lane-1 cache and `cache_bytes`, the move bucket, `positions`, `withheld`,
`Host.next_move_order`. Afterwards `lane1_egress() == (0, 0)` and
`lane.next_seq == lane.processed_seq + 1`. *Tests:* V2, V3, U1.

H-3. **At grace start.** `begin_grace`'s commit (T025b G-3 step 6) calls
`reset_lane1` right after the delivery-log discard (`:5239–5246`) and before
the session moves to `graces` (`:5247–5255`). *Tests:* V2, V3, U1.

H-4. **At resume.** `resume_peer`'s commit (G-7) calls `reset_lane1` on the
session right after a graced session is moved back to `sessions`
(`:5447–5450`) and before the staging commit (`:5452`), for a live and a
graced session alike (a no-op after H-3). No refusal (`Denied`, `Busy`, an
`Err`) calls it. *Tests:* V2, V4, U1.

H-5. **Progress is lane 0's only** (Question 1 (a)): `Accepted.progress` stays
`[LaneProgress { lane: LANE_COMBAT, finalized_through: next_new_seq − 1 }]`
(`:5399–5418`). *Tests:* V2, V4.

H-6. **Everything else of T025b holds for v4 unchanged**: while graced, the
handle is unbound for `ingest_move` (`Refused { seq: None, code:
Unauthenticated }`, T037 D-1 step 3) and `UnknownPeer` for
`take_move_receipts`, `take_samples` and `set_position_withheld`; the decision
window and the sample pass skip it (they iterate live sessions); expiry,
unbind, shutdown and checkpoints are G-5, G-11, G-12. The resume snapshot is
Reading 1's: `Cancel(in_flight, Superseded)` if a transfer is in flight, a
`0x82` `Begin` with the next transfer id and `cursor` the last issued
`event_seq`, its chunks, then the anchoring page. *Tests:* V1, V4, V5, V6.

### T155b — the resumable movement endpoint
N-1. **`bind_movement_resumable(config)`** is `bind_setup(config, &[Framing::V2],
true, true)`: `bind_movement` exactly (ALPN `[crpg-lane0/3]`, the movement
transport parameters, the datagram floor, `server.rs:243–305`, `:1182–1191`)
plus the resume opening. *Tests:* R1, R3.

N-2. **The opening.** On this endpoint the existing reader
(`server.rs:1109–1158`) applies unchanged: a first header byte `0x91` is a
resume request (cap `MAX_RESUME_FRAME_BYTES`), queued as
`ServerNotice::Resume`; any other opening is a hello decoded with
`decode_for(.., true)` (version 4 only). No change to `read_opening`. *Tests:*
R1, R3.

N-3. **`accept_resume`** keeps its precedence (`:438–458`) and, on success,
also sets `record.lane1_reader_active = record.movement` (Reading 6). The
answer is the first frame; then the lane-0 tasks start and, on a movement
connection, `lane1_accept` waits for stream 2 (`:1415–1422`, unchanged).
*Tests:* R1, R4.

N-4. **`connect_movement_resume`**, in order: (1) `limits.validate()` →
`Config`; (2) `session.encode_for(true)` fails → `Handshake`; (3) `request`
empty or longer than `MAX_RESUME_FRAME_BYTES` → `Handshake`; (4)
`framed_channel(Channel::Resume, request, ..)`; (5) quinn config
`tls::client_movement_config`; bind the socket; (6) the attempt is
`Kind::Resume { request_frame, welcome: session }` with `framing: V2`,
`movement: true`; (7) in `handshake`'s resume branch
(`client.rs:1009–1039`), after the answer body is read, open stream 2 when

## Questions for the user

1. **When a movement player reconnects, must the server's "welcome back"
   message say how far their movement orders got?** Each movement order a
   player's game sends has a number. On reconnecting, the game needs to know
   which orders the server already answered. Today's reconnect message
   reports this only for the combat channel.
   (a) **No: the game re-sends its unanswered movement orders, and the
   server answers each exactly once** — from its memory for orders it
   already answered (the same answer as before), as new for the rest. The
   game also learns the number from the position updates it receives every
   tick. No message format changes. *(Recommended.)*
   (b) **Yes: a new version of the reconnect message** (first byte `0x92`)
   that carries a movement entry. It needs a new `crpg-net` part before
   T155a, and both ends must speak the new version on movement connections.
   Old clients are unaffected (only movement connections would use it), but
   it is a second reconnect format to keep.
   *If (b):* a part T155n (`crpg-net`: `protocol_resume`/`codec_resume`
   version `0x92` allowing lanes 0 and 1) comes first; H-5 adds `{ lane: 1,
   finalized_through: lane.next_seq − 1 }` for v4 sessions; T155c's C-1
   decodes `0x92` on movement connections and answers with it; QR2's answer
   bytes change; Reading 2 is replaced.
2. **May a movement connection reopen with a reconnect request without a
   new connection label?** Connections announce a label naming their wire
   rules (`crpg-lane0/3` for movement). The reconnect request is the same
   opening message the combat label already allows on its reconnect-capable
   servers.
   (a) **Same label, new server type**: a "reconnect-capable movement
   server" (`bind_movement_resumable`), exactly as the combat side has one;
   the existing movement server keeps refusing reconnects, and no existing
   test changes. *(Recommended.)*
   (b) **A new label `crpg-lane0/4`** for movement-with-reconnect: clients
   must offer a second movement label; more code for the same bytes.
   (c) **Let the existing movement server accept reconnects**: one server
   type, but it changes T150's approved rule and its test.
   *If (b) or (c):* T155b's Interface, N-1, N-2, R1, R3 and Reading 5
   change; (b) also needs an ALPN constant and ADR text; (c) edits
   `crates/crpg-net-quic/tests/movement.rs:333–374`.
3. **How does the dedicated server offer movement?** One server world speaks
   one kind of connection.
   (a) **An operator switch, `"movement": true` in the configuration file**:
   the world then takes only movement clients (with movement invitations:
   the extra "facts" and "rights" keys); without the switch the program is
   exactly today's, so today's tests and the fight smoke are untouched.
   *(Recommended.)*
   (b) **Movement always**: simpler file, but today's combat-only clients and
   the approved fight smoke (T041d) stop working.
   (c) **Both kinds on two ports, one world**: the most flexible, but the
   host adapter must own two servers, an architecture change (ADR-0026)

   *If (b):* B-M1..B-M5 lose their combat branch, T040b's suite and T041d's
