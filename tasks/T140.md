## Task
Add protocol version 3 to `crpg-net`, carrying ADR-0029 N1 (`:324–331`):
the world facts mode, pending mode, clock, timeline order with keys, pools,
attached effects, standing orders and stat values (round and the active
combatant already travel in the v1 `Turn` op); the host facts pause state and
reason, the viewer's own pause rights, the auto-pause toggles and the turn
timer (the server tick is every frame's header); the events `RoundStarted`,
`ModeChanged`, `OrderEnded` plus T139's `Joined`/`Left`; the intents `Stop`,
`Pause`, `Unpause`, `RequestMode` beside `DeclareAction`/`EndTurn`; the
rejection codes T137, T138 and T139 left here; per-field grants for every new
fact (N2, `:333–336`); the N4 `Clock` heartbeat op (`:342–345`); and the N3
snapshot allowlist extension as transfer version `0x82` (`:338–340`). v1, v2,
`0x81` and `0x91` stay frozen byte for byte. `crpg-net` still reads no
`World`: T141 builds every value and grant.

- **T140a — v3 vocabulary and scalar codec.** `protocol_v3` (version, tags,
  intents, codes, receipts, modes, pause reasons, host facts, the delta enum
  without the three fact ops), `codec_v3` for intents and for delta tags
  0..=10 and 14..=20.
- **T140b — fact ops and event projection.** The fact types, bounds and
  checks; codec for tags 11..=13; the frame splitter `frame_spans`;
  `projection_v3`.
- **T140c — fact filtering.** `facts_v3`: `FactView`, the per-row,
  per-encounter and host-fact grants, change detection, and the composite
  `project_page`.
- **T140d — the `0x82` snapshot.** `transfer_v3` (body, codec, framing with
  the v3 caps of 4 MiB and 128 chunks, `check_begin`, `plan_transfer`) and
  the composite `project_snapshot_v3`.
- **T140e — v3 receiver sizing.** `reassembly_v3`: `TransferAssemblyV3` (a
  128-chunk assembly) and `TransferLimitsV3` (T024's staging, deadline and
  held-delta budgets re-sized for the 4 MiB envelope). It fixes no byte.

## Crate(s)
**`crpg-net` only**, for all five parts. No dependency is added; `crpg-sim`
and `crpg-data` stay dev-only (`crates/crpg-net/Cargo.toml`, ADR-0019 `:10–11`).
`tools/lint/deps.py` `ALLOWED` is untouched.

**S-set.** A wire version is a schema version, so **T140a, T140b and T140d
are S-set** (they fix bytes): serialized, Claude implementer, Claude reviewer
and a two-keys writer. **T140c** fixes no byte (it decides which existing
fact ops a viewer receives); it is not S-set but is H-filter work and gets
the Claude reviewer. **T140e** fixes no byte either (it sizes receiver
memory and time); it is not S-set and gets the Claude reviewer.

**Who builds what.** `crpg-sim` holds and hashes the world facts (T138,
T139) and journals the events. `crpg-server` (T141) reads `World` and host
state, builds every `FactRow`, `EncounterInput`, `HostInput`, grant,
`EventCandidate` and `Receipt`, and sends frames. `crpg-net` (this task)
only defines bytes, filters host-supplied values by grant (world facts and
host facts alike), remembers what each viewer was last told, splits ops into
frames, and encodes.

**Left to T141 (`crpg-server`):** P1–P9 (pause, rights, auto-pause, restore,
turn timer); the host's mode-request authorization; reading

`crates/crpg-server/src/host.rs:2484–2489` (`Moved` stays `None`); mapping
sim errors to the new codes; heartbeat timing (H-1); choosing v2 or
v3 per session; choosing each viewer's `HostGrants`; sending `HostFacts`
and `Clock` after each publication; cutting frames with `frame_spans` (H-6).
**Left to T026p (`crpg-net`):** `DeclareMove`, `Moved`, position grants and
lane 1, as protocol version 4 (ADR-0036 `docs/adr/0036-movement-and-navigation.md:413–417`, `:568–571`).
**Left to a new `crpg-net` receiver task** (manager to file): `ReassemblyPool`
gating of v3 deltas and publication of `0x82` bodies
(`crates/crpg-net/src/reassembly.rs:249–282` are v1/v2/`0x81`-only), built on
T140e's `TransferAssemblyV3` and `TransferLimitsV3`, and a v3

## Readings of the ADR
Each needs the user's approval with the contract. "Draft a/b" name the blind
drafts; their claims were checked, not trusted.
1. **Version 3, new modules, no negotiation.** v1 is byte 1
   (`crates/crpg-net/src/protocol.rs:25`), v2 byte 2
   (`crates/crpg-net/src/protocol_v2.rs:34`); v3 is byte 3 in new modules, and
   each codec refuses the others' bytes with `UnsupportedVersion`
   (`docs/architecture/crpg-net.md:213–217`). Both drafts agree.
2. **Tags 0..=10 are re-declared natively in v3, not wrapped in `Legacy`.**
   New codes must reach a receipt, and the receipt's code byte is a v1 type
   frozen at 1..=20 (`crates/crpg-net/src/protocol.rs:391–472`). Wrapping v2
   (draft a) leaves two receipt ops (tag 7 and a new tag 21) for one meaning;
   draft b's native re-declaration gives one op per tag. Payload bytes of
   tags 0..=10 are unchanged, and `From` conversions from v1 and v2 ops let
   `InterestView` and `projection_v2` output flow into v3 pages.
3. **Round and active stay in `Turn` (tag 6)** under the existing
   `turn_granted` grant (`crates/crpg-net/src/interest.rs:86–89`). A second
   carrier (draft a's `Encounter.round`/`active`) could disagree with it.
   Draft b is right here.
4. **Facts are images, and absent means withheld.** Each fact op carries the
   viewer's complete current image of its subject: an `Option` that is `None`
   is "not disclosed", never zero (ADR-0029 U7 `:389–391`). A nullable fact
   that is disclosed is `Option<Option<_>>` (for example "granted, and there
   is no pending mode"). An op whose fields are all withheld tells the client
   to forget that subject (for example the encounter ended).
5. **The timeline carries the authority order.** Entries come in ascending
   `(key, EntityId)` (`crates/crpg-sim/src/timeline.rs:27–31`), but the client
   sees `NetId`s, whose order can differ inside a tie. The wire therefore keeps
   input order, and the decoder checks only non-decreasing keys and distinct
   entities. Draft a's "descending `(key, entity)` pair is `Malformed`" would
   reject legal tie orders. Hidden entities have no entry.
6. **One `EntityFacts` op per entity** with five families: pools, effects,
   order, stats, and tags. Tags are not in N1; T139 assigned "record tags" to
   T140 (`tasks/T139.md:1914–1917`). Health stays in the v1 `Health` op
   (draft a duplicated it). Pools are `(id, current, max)` with ULID ids
   (`crates/crpg-rules/src/resource.rs:24`, `:80–87`; draft a's string ids
   are wrong). Effects are `(effect, expires_round)` (`crates/crpg-sim/src/combat.rs:190–198`),
   orders `(ability, target, repeat)` (`:95–104`), and stats are the `Int`
   attributes and `Fixed` stats by name (`:247–250`, `:292–295`).
7. **Change detection lives in a companion `FactView`, not in
   `InterestView`.** Adding fields to `FieldMask`, `EntityFact` or
   `ViewerContext` (draft b) would break the struct literals in
   `crates/crpg-net/tests/interest.rs` and reopen T027b. `FactView` mints
   nothing: it resolves keys through the one `InterestView` of the epoch
   (`crates/crpg-net/AGENTS.md:107–113`). It is driven only through the
   composites `project_page` and `project_snapshot_v3`, which validate
   before the view mutates, so a call is all-or-nothing. Draft a's stateless
   `facts_page` re-sent every fact every page and emitted ops for viewers
   with no grant, which contradicted its own item 17.
8. **Over-limit families are withheld, never truncated or refused.** A
   family whose list or names break a wire bound (Interface, T140b) renders
   as withheld for that row. That fails closed: the client shows "hidden",
   and the session continues. The limits are the raised ones the user chose
   in Question 2: 16 pools, 16 effects, 32 stats, 8 tags, names of 1..=32
   bytes.
9. **Orders.** `FactMask::order` defaults to false. T141 sets it only for the
   controlling peer (N2, `:334`). An order whose target has no `NetId` for
   this viewer is withheld as a family, because a hidden target cannot be
   named. T141 grants `OrderEnded` under the same rule.
10. **Codes 21..=30.** `ModeUnsupported`, `WrongMode` (`tasks/T138.md:859–866`);
    `StatEvaluation` (`tasks/T137.md:823`); `EncounterTerminal`,
    `RulesetMismatch`, `PlacementInUse`, `NotCreature`, `AlreadyParticipant`,
    `NoEntrants` (`tasks/T139.md:1914–1916`); and one `NoPauseRight` for P4's
    typed refusal (`:296–297`). The client knows which verb it sent, so one
    code is enough (draft b; draft a's two codes add nothing). A paused host
    still runs commands (P2), so there is no `Paused` code. `TooManyTags`
    stays host-side (`tasks/T137.md:823–824`).
11. **Intents 2..=5 share the v1 header.** `Stop`, `Pause`, `Unpause` carry
    nothing; `RequestMode` carries one mode byte. The header still requires a
    nonzero `actor`. For `Pause`, `Unpause` and `RequestMode` it names the
    requesting peer's bound character, and T141 decides what it authorizes.
12. **`Clock` is an op, and the server tick is the frame header.** A delta
    frame has no kind byte, so a heartbeat is an ordinary delta frame
    holding a `Clock` op. It consumes an `event_seq` like any frame (draft b
    reading 2). N4's `server_tick` is the header's `server_tick`, so it is not
    copied into the op (draft a's copy needed a consistency rule). N4's
    `paused` is carried with its reason, and `Clock` is the only carrier of
    pause state: `Clock { paused: Option<Option<PauseReason>> }`, where
    `None` is running, `Some(None)` is paused with the reason withheld, and
    `Some(Some(r))` is paused for `r` (Reading 13). `POLICY_CLOCK_HEARTBEAT_TICKS = 100`,
    half the 200-tick window (`crates/crpg-net/src/protocol.rs:159–165`), so
    one lost heartbeat still leaves a fresh tick (both drafts).
13. **Host facts have grants, with two reasoned exceptions.** `HostFacts`
    is one op: the viewer's two rights, the auto-pause toggles and the turn
    timer as remaining milliseconds. It is remaining time, not a host
    wall-clock deadline, because the client's clock is not the host's (P8
    keeps wall-clock reads in the server, `:314–316`). N2 (`:333–336`) and
    U7 (`:389–391`) require a grant per field and "hidden, never zero", so
    the pause **reason**, the **toggles** and the **timer** each have a grant
    (`HostGrants`, T140c, default deny), and a withheld one is `None` on the
    wire, never confused with a disclosed "nothing": the timer is
    `Option<Option<u32>>` (`Some(None)` = disclosed, no timer running) and
    the reason is the inner `Option` of `Clock.paused`. Two host facts are
    deliberately **not** granted. (a) Whether the session is paused: a
    pause stops every World of the host for every peer (P1, P3, `:281–288`),
    so each client already observes it (its clock stops), and the client
    must know it to show a paused state rather than a stall. (b) The
    viewer's own rights: they describe only that viewer (P4, `:290–297`),
    and it needs them to know whether its own Pause button works. The
    server tick is the frame header of every frame (Reading 12).
    `PauseReason::Player` carries no peer identity. Whether the reason
    (including "a party member died") reaches every player is Question 3.
14. **`0x82` is `0x81`'s framing with a new first byte, a wider body and a
    larger envelope.** T024 reserved `0x82` for new facts
    (`tasks/T024.md:333–334`). Frame layout, tags, the segment and chunk
    rules (4,096-byte segments, at most 8 per chunk, 32,768-byte chunks, the
    canonical cut) are unchanged. Three things differ: byte 0, the body, and
    two caps, total bytes 4,194,304 (`MAX_SNAPSHOT_BYTES_V3`) and chunks 128
    (`MAX_SNAPSHOT_CHUNKS_V3`) (Question 2, Reading 15). The body is the
    `0x81` body (`:321–335`) with a fact set after each entity's health,
    then an encounter block and a timeline block. Host facts are not in the
    body: they are per viewer and not state at the cursor, so T141 sends them
    as ops after publication. **The v1/v2/`0x81` caps stay 1 MiB and 32
    chunks.** `MAX_SNAPSHOT_BYTES` and `MAX_SNAPSHOT_CHUNKS`
    (`crates/crpg-net/src/protocol.rs:89`, `:95`) are frozen pins that
    `BeginTransfer::validate` (`crates/crpg-net/src/protocol_transfer.rs:111–145`),
    the `0x81` codec (`crates/crpg-net/src/codec_transfer.rs:181`, `:274–298`,
    `:327`, `:516`), `TransferAssembly`'s 32-bit bitmap
    (`crates/crpg-net/src/reassembly.rs:52–57`) and `TransferLimits`
    (`:128–223`) hard-code, so moving them would move v1 bytes and tests.
    v3 therefore has its own caps, and `BeginTransfer`'s fields already hold
    v3 values (`total_bytes: u32`, `chunk_count: u8`,
    `crates/crpg-net/src/protocol_transfer.rs:90–107`; 128 fits one raw
    byte), so no layout changes. T140d adds `check_begin`/`chunk_len` with
    the v3 caps and its own frame codec; T140e adds the 128-chunk assembly
    and the re-sized receiver limits. Draft b's 64-chunk/2 MiB envelope is
    still rejected: 2 MiB does not hold the raised limits' largest body.
15. **The raised limits fit a 4 MiB envelope with the 1,024-row cap kept.**
    With the T140b bounds the largest valid `0x82` body is **2,847,788
    bytes** (D-4). The smallest power-of-two-MiB cap that holds it is 4 MiB:
    1 MiB = 1,048,576 and 2 MiB = 2,097,152 are smaller, and 4 MiB =
    4,194,304 leaves 1,346,516 bytes of headroom. 4,194,304 ÷ 32,768 = 128
    chunks; the largest valid body needs ⌈2,847,788 ÷ 32,768⌉ = 87 chunks at
    8 segments per chunk. `MAX_VISIBLE_ENTITIES` stays 1,024.
16. **Rolls stay off the wire.** No v3 field carries a roll, modifier, DC or
    margin. History never stores them (`crates/crpg-sim/src/history.rs:77–86`,
    `docs/adr/0021-authoritative-host-capture.md:72`), and no ruleset has an
    opt-in flag, so v3 would have nothing to send. Question 1 covers this.
17. **`Joined`/`Left` are in, `Moved` is out.** `Joined`/`Left` are notices
    (tags 17/18) that never mint or retire ids. `Moved` and `DeclareMove` need
    position grants, quantized points and lane-1 rules (ADR-0036 L1–L6). That
    is a second H-filter decision about the size of T026p, so T026p defines
    protocol v4 after this contract closes (ADR-0036 `:568–571`). Both drafts
    left `Moved` out; draft b's question recommended folding it in, and that is
    declined.
18. **Receiver sizing scales with the envelope (T140e).** T024's
    `TransferLimits` (`crates/crpg-net/src/reassembly.rs:128–223`,
    `tasks/T024.md:403–425`) is re-sized for v3 in a new type, so v1 stays
    byte- and test-identical. Staging per receiver is
    `MAX_SNAPSHOT_BYTES_V3` (4,194,304), with the largest valid body
    (2,847,788) as its floor, as v1's floor is its largest body (22,552,
    `crates/crpg-net/src/reassembly.rs:171`). Pool staging is 8 × 4 MiB =
    33,554,432, which keeps T024's rule that eight maximal transfers fit at
    once. The deadline is 20,000 ms: T024 allowed 5 s for 1 MiB
    (`tasks/T024.md:179–190`), and four times the bytes keeps the same
    floor of 1 MiB per 5 s (about 205 KiB/s). The held-delta budgets stay
    128 frames, 2 MiB per receiver and 16 MiB per pool, because T024 tied
    them to the egress caps (`POLICY_EGRESS_*`,
    `crates/crpg-net/src/protocol.rs:139–143`), which do not change. A
    receiver whose held deltas overflow during a slow transfer resyncs by
    T024's existing overflow rule, which fails closed. Worst-case pool memory
    goes from 24 MiB to 48 MiB (32 MiB staging + 16 MiB held deltas), plus
    decoded bodies.
19. **The QUIC windows do not constrain a larger transfer; the egress
    queue does, and that is T141's.** The `crpg-net-quic` windows are flow
    control, not size caps: the client's 1 MiB stream and 2 MiB connection
    receive windows (`crates/crpg-net-quic/src/limits.rs:40–41`) only stall
    the sender until the client reads, and a full inbound queue parks one
    frame and stalls the peer rather than refusing
    (`docs/architecture/crpg-net-quic.md:133–135`). T024 already sends
    1 MiB + 1,692 bytes through a 1 MiB window this way (`tasks/T024.md:187–190`).
    No `crpg-net-quic` change and no follow-up task is needed there. The
    per-peer egress queue is different: the largest body's `0x82` plan (D5)
    is 88 frames and 2,851,124 bytes, over the 2 MiB per-peer egress bytes
    (`crates/crpg-net/src/protocol.rs:141`), and the v1 host admits a
    snapshot plan only if all of it fits at once
    (`crates/crpg-server/src/host.rs:1690–1694`). T141 must pace `0x82`
    frames into the egress queue (H-7) instead; the egress caps stay.

## Interface
Every public item has a doc comment (`#![warn(missing_docs)]`). Every new
struct and enum derives `Debug, Clone, PartialEq, Eq`, plus `Copy` where
marked. No serde derive, no `Serialize`, no restore constructor. Numbers
from `crate::protocol` are used by path, never copied. Errors reuse
`crate::codec::CodecError` (re-exported as `codec_v3::CodecError`) and
`crate::projection_v2::ProjectionError`.

### T140a — `protocol_v3`
```rust
pub use crate::protocol::{NetId, SessionEpoch};
pub const PROTOCOL_VERSION: u8 = 3;
// Intent tags (0 and 1 keep their v1 meaning and payload).
```

### Wire layout (T140a and T140b)
**Intent frame:** `3`, `epoch [u8;16]`, `lane u8`, `seq u64`,
`observed_tick u64`, `actor u64`, body tag `u8`, then the body: tag 0 is
`ability` ULID text and `target u64`; tags 1..=4 carry nothing; tag 5 is
`mode u8`.

**Delta frame:** `3`, `lane u8`, `server_tick u64`, `event_seq u64`,
op count `u64`, then each op as its tag and these fields:

| Tag | Fields after the tag, in order |
|---|---|
| 0..=10 | exactly the v1/v2 payload (`crates/crpg-net/src/codec.rs:23–33`, `codec_v2.rs:16–19`); tag 7's code byte is a v3 `RejectionCode` |
| 11 Encounter | `mode_disclosed bool` [`mode u8`]; `pending_disclosed bool` [`pending_some bool` [`pending u8`]]; `clock_disclosed bool` [`clock_some bool` [`round_ticks u32`, `elapsed u64`]] |
| 12 Timeline | `disclosed bool` [`count` varint (≤ 1,024); per entry `key i32` (zigzag), `entity u64`] |
| 13 EntityFacts | `entity u64`, then the fact set: `pools_disclosed bool` [`count` (≤ 16); per pool `pool` ULID text, `current u32`, `max u32`]; `effects_disclosed bool` [`count` (≤ 16); per effect `effect` ULID text, `expires_round u64`]; `order_disclosed bool` [`order_some bool` [`ability` ULID text, `target u64`, `repeat bool`]]; `stats_disclosed bool` [`count` (≤ 32); per stat `name` string (1..=32 B), `kind u8` (0 Int, 1 Fixed), `value i32` (zigzag)]; `tags_disclosed bool` [`count` (≤ 8); per tag a string (1..=32 B)] |
| 14 RoundStarted | `round u64` |
| 15 ModeChanged | `mode u8`, `round u64` |
| 16 OrderEnded | `actor u64` |
| 17 Joined, 18 Left | `entity u64` |
| 19 Clock | `paused bool` [`reason_disclosed bool` [`reason u8` (0 Player, 1 Auto, 2 Operator, 3 Restore) [`trigger u8` (0..=4), only when the reason is Auto]]] |
| 20 HostFacts | `pause bool`, `unpause bool`, `auto_disclosed bool` [`bits u8`], `timer_disclosed bool` [`timer_running bool` [`remaining_ms u32`]] |

Brackets hold bytes present only when the flag before them is `true`. Mode
bytes are 0 `TurnBased` and 1 `RealTime`.

### T140a: version, intents, scalar ops
A-1. **Version gate.** `encode_*` writes byte 3 first. `decode_intent` and
`decode_delta` check, in this order: (1) input over 4,096 / 65,536 bytes is
`FrameTooLarge`; (2) empty input is `Malformed`; (3) a first byte other than 3
(including 1, 2, `0x81`, `0x91`) is `UnsupportedVersion`. The v1 and v2 codecs
refuse byte 3 with `UnsupportedVersion`; no codec guesses or falls back.
*Tests:* A1.

A-2. **Intent decode order:** frame cap → version → `epoch` (16 bytes) →

*Tests:* A2, A3.

A-3. **Intent encode** checks `lane` (`WrongDirection`), then `seq`

returns partial bytes. *Tests:* A3.

A-4. **Delta decode order:** frame cap → version → `lane` (`WrongDirection`)
→ `server_tick`, `event_seq` (any `u64`) → op count (> 256: `LimitExceeded`,

*Tests:* A1, A8, A9.

A-5. **Tags 0..=10 are byte-identical to v2.** For every v2 op `o` whose
receipt code (if any) is 1..=20, `codec_v3::encode_delta` of a frame holding

additionally accepts codes 21..=30. A code byte of 0 or 31..=255 and a status

`WrongDirection` and a receipt `seq` outside the range is `Malformed`

A-6. **Codes.** `RejectionCode::from_u8(n)` is `Some` exactly for 1..=30, and

A11, B7, B9.

### T140b: fact ops and event projection
B-1. **Encounter (tag 11).** Each of the three fields is a disclosed flag;
`pending_mode` and `clock` add a `some` flag. A mode or pending byte of
2..=255 is `UnknownMessage`. A `round_ticks` of 0 is `Malformed`. An
`elapsed` above `MAX_CLOCK_ELAPSED` is `Malformed`, checked when read. All 36
combinations of `mode` (3 values), `pending_mode` (4) and `clock` (3)
round-trip. *Tests:* B1.

B-2. **Timeline (tag 12).** A disclosed flag of `false` ends the op. Otherwise
the count is read as a bounded varint: over 1,024 is `LimitExceeded`, checked
before any entry (a ten-byte hostile count included), and a varint
overflowing `u64` is `Malformed` (`crates/crpg-net/src/codec_v2.rs:124–143`).
Each entry reads `key`, then `entity` (0: `Malformed`), then checks
`key` ≥ the previous entry's key (`Malformed`), then that `entity` has not
appeared before (`Malformed`). Equal keys may come in any `NetId` order.
*Tests:* B2.

B-3. **Fact set (tag 13 after `entity`; also the `0x82` body).** The families
are read in the order pools, effects, order, stats, tags. Each is a disclosed
flag, then for a list a bounded-varint count (over its cap: `LimitExceeded`,
before any element), then each element with these checks in this order:
- pool: ULID text, `current`, `max`; then `current > max` is `Malformed`;
  then a `pool` equal to an earlier pool's is `Malformed`.
- effect: ULID text, `expires_round`; then an `effect` not strictly greater
  than the previous one (by `Ulid` order) is `Malformed`.
- order: `some` flag, then ULID text, `target` (0: `Malformed`), `repeat`.
- stat: the name's length varint (over 32: `LimitExceeded`, before the body
  bytes; 0: `Malformed`), its body (short: `Malformed`), UTF-8
  (`Malformed`); `kind` (2..=255: `UnknownMessage`); `value` (zigzag `i32`;
  out of range: `Malformed`); then a name equal to an earlier stat's is
  `Malformed`.
- tag: as a stat name; then a tag not strictly greater than the previous one
  (byte order) is `Malformed`.
A withheld family has no bytes after its flag. A disclosed empty list is the
flag `01` plus count `00`, which is distinct from withheld. *Tests:* B3, B4,
B5, B6.

B-4. **Encode-side checks** are the public `check_*` functions, applied in
wire order. A count over its cap is `LimitExceeded`. Then, per element in list
order: a stat or tag name of more than 32 bytes is `LimitExceeded`; an empty
name, `current > max`, a duplicate, an out-of-order element, `round_ticks` 0
and `elapsed` over the cap are `Malformed`. Each function returns exactly the
error that `encode_delta` returns for an op holding the same value.
*Tests:* B4, B5, B7.

B-5. **`project_events`.** More than 256 candidates is `TooManyEvents`, with
no output. Candidates are visited in input order, and one op is appended per
fully disclosed event: no sorting and no deduplication. `V2(c)` yields exactly
the ops `projection_v2::project_events(&[c])` returns, converted with `From`;
its `StringLimit`/`InvalidOutcome` errors fail the whole call. `RoundStarted`
needs `round`, `ModeChanged` needs `mode` and `round`, `OrderEnded` needs
`actor`, and `Joined`/`Left` need `entity` and `disclose == true`. A
candidate missing any of these is omitted without inspecting its other
fields. *Tests:* B8.

B-6. **Frame splitting.** `frame_spans(ops)` first runs, op by op in order,
the per-op encode checks of A-8 and B-4; the first failure is returned, with
no spans. Otherwise it walks the ops once and returns contiguous ranges
that cover `0..ops.len()` in order. A frame closes, and the next op starts a
new one, exactly when adding that op would make the frame hold more than
`MAX_DELTA_OPS` (256) ops or more than `MAX_FRAME_OP_BYTES_V3` (65,512)
bytes of encoded ops (tag included). Empty input gives no spans. Because
the 24-byte header bound is the largest possible header, a `DeltaFrame` of
lane 0 holding one span encodes within `MAX_DELTA_FRAME_BYTES` for every
`server_tick` and `event_seq`. No valid v3 op is larger than 15,364 bytes
(a 1,024-entry `Timeline`; an `EntityFacts` is at most 2,755: tag 1 + entity
10 + a 2,744-byte fact set, D-4), so no single op
needs a frame of its own beyond the cap and the split never fails on size.
*Tests:* B9.

C-1. **`project_page` checks before anything changes**, in order:

### T140d: the `0x82` snapshot
D-1. **Frames.** Every `0x82` frame layout is the `0x81` layout with byte 0

(`crates/crpg-net/src/codec_transfer.rs:160–482`,
`crates/crpg-net/src/protocol_transfer.rs:111–164`), with exactly three
bounds replaced: the Begin `total_bytes` cap `MAX_SNAPSHOT_BYTES` becomes
`MAX_SNAPSHOT_BYTES_V3` (4,194,304), and the Begin `chunk_count` cap and the
Chunk `index` bound (on encode and decode) `MAX_SNAPSHOT_CHUNKS` become
`MAX_SNAPSHOT_CHUNKS_V3` (128). `check_begin` and `chunk_len` are
`BeginTransfer::validate` and `BeginTransfer::chunk_len` with those
replacements, and the v3 codec calls them wherever T024's calls the
originals. Because the `0x81` codec and `BeginTransfer::validate` refuse the
wider values, `transfer_v3` encodes and decodes Begin and Chunk itself and
never calls `codec_transfer` or `BeginTransfer::validate` for them (Cancel,
Published and Resync may delegate). Then:
- (a) for every message the `0x81` encoder accepts, `encode_down`/`encode_up`
  return its bytes with byte 0 changed from `0x81` to `0x82`;
- (b) `decode_down`/`decode_up` check, in order: (1) input over 65,536 /
  4,096 bytes is `FrameTooLarge`; (2) empty input is `Malformed`; (3) a first
  byte other than `0x82` is `UnsupportedVersion`; (4) for any frame whose
  Begin has `total_bytes` ≤ 1,048,576 and `chunk_count` ≤ 32, whose Chunk has
  `index` < 32, or that is another message, the result (message or error)
  is what the `0x81` decoder returns for a copy with byte 0 set to `0x81`,
  so lane, tag, field and trailing-byte precedence are T024's
  (`tasks/T024.md:350–395`);
- (c) a Begin with `total_bytes` 1,048,577..=4,194,304 or `chunk_count`
  33..=128, and a Chunk with `index` 32..=127, are accepted when otherwise

The `0x81` decoders and `codec_v3` refuse `0x82` with `UnsupportedVersion`.

### T140e: v3 receiver sizing
E-1. **`TransferAssemblyV3::new`** returns `transfer_v3::check_begin(begin)`'s

## Errors
No new codec error variant. `CodecError` (six variants,
`crates/crpg-net/src/codec.rs:51–66`) covers every wire refusal:

| Refusal | Error |
|---|---|
| frame over 4,096 (intent, up) / 65,536 (delta, down) bytes | `FrameTooLarge` |
| first byte not 3 (lane 0) / not `0x82` (transfer v3) | `UnsupportedVersion`; empty input `Malformed` |
| lane, receipt lane or transfer direction wrong | `WrongDirection` |
| unknown op, body, status, code, mode, reason, trigger or stat-kind byte | `UnknownMessage` |
| count over cap (ops, timeline, pools, effects, stats, tags, entities), ULID text or outcome over 256 bytes, name over 32 bytes, `0x82` body or Begin `total_bytes` over 4,194,304 bytes, `segments_per_chunk` over 8, `0x82` chunk count over 128 or chunk index of 128 or more | `LimitExceeded` |
| truncation, trailing bytes, flag byte not 0/1, varint overflow, id 0, `seq` or `cursor` out of range, `segments_per_chunk` 0, bad ULID/UTF-8/outcome, empty name, `current > max`, duplicate or out-of-order element, `round_ticks` 0, `elapsed` over cap, toggle bits over `0x1F`, entity not ascending, a referenced entity missing from the body | `Malformed` |

`ProjectionError` (`TooManyEvents`, `InvalidOutcome`, `StringLimit`) is
reused unchanged. `FactError` is new, with four variants (Interface, T140c):
its `Display` texts are `<Variant> at projection/facts`, with no payload, and
`source()` is `None`. Gameplay refusals are receipts, never codec errors.
T140e reuses `AssemblyError` (four variants) and `LimitsError`
(`InvalidLimits`, `LoosensPolicy`) from `crate::reassembly` unchanged; it

## Questions for the user
1. **Should players see their own dice rolls? (ADR-0029 Open question 8.)**
   When a character attacks, the server rolls dice and tells clients only the
   result ("hit", "miss", damage). You accepted in principle (D30) that a
   ruleset may let a player see their own character's roll and bonuses
   ("you rolled 14 + 3"), while target numbers stay hidden unless the
   ruleset makes them public. Today the engine never keeps the roll after
   resolving it: the history stores only the result, and no ruleset has a
   "show rolls" setting. This protocol therefore has nothing to send yet.
   (a) Leave rolls out of v3, and add them in a later protocol version
   together with the history and ruleset changes that produce them. (b)
   Reserve an empty roll message in v3 now, which nothing would fill until
   then. *Recommend (a):* a message with no sender cannot be tested, and the
   later version is needed anyway. Players and authors see no difference
   until the roll work lands.
   *Answered 2026-11-10 (user): (a), leave rolls out of v3. No change to the
   contract (Reading 16).*
2. **How much can players see on one creature?** Every fact sent to a
   player has a size limit, so that a player who joins or reconnects
   mid-fight can get the full picture in one bounded package (1 MiB, the
   existing limit). This contract allows, per creature, 8 resource pools, 8
   active effects, 12 stats, 4 tags, and stat and tag names of up to 16
   characters. If a creature has more of one kind (for example 13 stats),
   that whole kind shows as "hidden" for that creature; nothing breaks. (a)
   Keep these limits and the existing 1 MiB package. Later, campaign
   validation can warn authors who exceed them. (b) Raise them (for example
   16 effects, 32 stats, 32-character names). That needs a bigger package
   and a rework of the client's download logic, which T024 sized for 1 MiB.
   *Recommend (a):* today's rulesets use at most 5 stats with names of at
   most 7 characters. Raising later is a new protocol version.
   *Answered 2026-11-10 (user): (b), raise them now to 16 resource pools, 16
   active effects, 32 stats, 8 tags, and stat and tag names of up to 32
   characters. Asked what should give, the user chose a bigger package with
   the 1,024-creature cap kept. Applied: the largest reconnect package is
   now 2,847,788 bytes, so the `0x82` package cap is 4 MiB (the smallest
   power-of-two MiB that holds it) in 128 chunks, while the v1/v2 package
   stays 1 MiB (Readings 8, 14, 15). The client's download sizing is
   reworked in a new fifth part, T140e (Reading 18), and the host must send
   the package in paced steps (H-7, Reading 19). Confirmed by the user the same day: the
   20 s reconnect deadline, 32 MiB pool staging (eight maximal transfers at
   once), and the unchanged held-delta budgets (an overflow resyncs).*
3. **What do players learn about a pause?** In multiplayer, a pause stops
   the game for everyone, so every player is always told "paused" or
   "running". The *reason* is a separate, switchable fact: "paused by a
   player", "paused by the host", "paused after loading", or "auto-paused
   because …" (an encounter started, a round started, the mode changed, an
   order ended, or **a party member died**). The last one tells a player
   that someone in the party died, even if that character is out of their
   sight. The host decides per player whether the reason, the auto-pause
   settings and the turn timer are shown; this contract only makes that
   possible. Two choices: (i) the host's default: (a) show the reason to
   every player, or (b) show it only to players allowed to pause, with
   everyone else seeing just "paused"; (ii) naming who paused: (c) keep it
   anonymous, or (d) send which player paused, which needs a player number
   on the wire that no message has today. *Recommend (a) and (c):* the party
   is shared, an unexplained stop is worse than knowing why, and
   multiplayer auto-pause is off unless the host turns it on (P6). The
   timer and settings are shown to every player by default. The defaults
   can be tightened later without a new protocol version; naming the player
   would need one.
   *Answered 2026-11-10 (user): (a) and (c), the reason goes to every
   player, and the player who paused is never named. No change beyond
   recording it (H-2's defaults follow it).*
4. **Approve the four-part split and its limits on what this version
   includes.** The work is about 1,500 lines of code, in four parts in
   order: (a) message formats for commands and simple events; (b) the
   encounter, turn order and per-creature facts; (c) deciding which of
   those facts each player receives; (d) the reconnect package. Movement
   messages are not included and come next with T026p. The client-side
   reader for the new reconnect package comes in a separate follow-up task.
   *Recommend: approve.*
   *Answered 2026-11-10 (user): the split is approved, with the T024 sizing
   rework added as its own part. Applied as T140e, after T140d (Routing and
   size gives why it is not folded into T140d).*
5. **Approve T140b's edits to the first part's tests (approved by the user as D53, 2026-11-10).** The first
   part's tests check that three message numbers (11, 12, 13) are still
   unknown, because the messages they stand for (the encounter, the turn
   order, and per-creature facts) only arrive in the second part. Once they
   arrive, those checks must expect the new messages instead, or the second
   part cannot pass. This revision lets T140b change exactly those checks
   (EX1–EX5, "Tests → Existing-test edits"), each to the result the message
   layout already fixes, and nothing else; every other message number
   stays unknown as before. No message layout or limit changes.
   *Recommend: approve.*
