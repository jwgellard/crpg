# T017 — Second ruleset (`srd-lite`) as the production-path abstraction gate

## Status and purpose

**Milestone contract approved 2026-09-27; per-crate executable contracts
pending. Implementation and verification are not claimed.**

Deliver the abstraction proof the project actually needs: a second,
materially different ruleset driven through the same production data path,
the same generic simulation path, and the same replay/golden machinery as
`minimal-d6` — with no package-name branches anywhere. Where T016 proved
authored data can drive combat, T017 proves the engine is data-driven:
changing the ruleset changes behavior through content alone.

This is workstream B of the
[project gap remediation plan](../docs/reviews/REMEDIATION_PLAN_2026-09-27.md)
(§5). It reuses T017 from the backlog rather than creating a competing
milestone.

## Scope and execution boundary

The specification step creates only `tasks/T017.md`.

T017 cannot be executed as one implementation task: it requires changes in
more than one crate. E004 explicitly requires splitting T017 at
specification time. The ordered work packages below are that split; the
data child (B1) is written first, and each child requires its own task file
with exact public shapes, allowed paths, errors, limits, tests, and
stopping command before implementation begins. This parent file does not
authorize a multi-crate branch or waive a crate's ADR requirement.

| B2 | — | **Vacuous: no kernel task.** The scenario maps onto existing T014/T015 APIs in full (see *Kernel mapping*); lifetime is caller-owned per T014 by design. Any future gap found during B1/B3 stops into its own finding instead. | Scenario analysis (done here) |

Each child may extend its own `AGENTS.md`, its own architecture document,
and its own task completion record. B1 owns the external authored content
and schema changes explicitly listed in its child contract. B4 owns replay

Status-file and CI changes require explicitly scoped follow-up work if needed.

No changes to `crpg-rules`, `crpg-core`, `crpg-contracts`, or
`rust-toolchain.toml` are authorized by this specification. (B2's absence
is the point: if the existing kernel cannot express the scenario, the child
stops and documents the exact missing primitive rather than hiding rules
knowledge in sim or the CLI.) No new dependencies are authorized. No
commits, pushes, or PRs without separate instruction.

## Required ruleset behavior (hand-calculated content, fixed before schemas change)

`srd-lite` shares the stat vocabulary shape with `minimal-d6` (same
attribute names, proving data-driven selection) and differs in every
behavioral dimension: target-derived defense, two abilities, two pools,
a natural-face rule, a lifetime-bearing modifier effect, and an explicit
turn policy. Names, identities, values, and thresholds below are content;
production code holds none of them.

- Stats `[might, guile, resolve, ward, health]`, all kind `int`;
  `attributes: [might, guile, resolve]`; `health_stat: health`.
  Creatures: hero `{might 8, guile 6, resolve 7, ward 7, health 10}`,
  goblin `{might 6, guile 7, resolve 5, ward 5, health 6}` — base values
  identical to `combat_basic`, `ward` new.
- Pools: `action {max: 1, refresh: on_turn_start}` (identical shape to
  minimal-d6, proving interop) and `focus {max: 2, refresh: on_round_start}`
  (independent maximum and trigger).
- Heavy (both creatures): dice `2d6`, defense `TargetStat(ward)`, table
  `[{i64::MIN: failure}, {-2: success}, {2: critical}]` with natural rule
  `{face: 6, effect: Shift(+1)}` on selected die index `0`, damage
  `{failure: 0, success: 3, critical: 5}`, costs `[{action: 1}]`,
  `ends_turn: true`, no effect, targeted, no self-target.
- Focus (both creatures): dice `1d6`, defense `ActorAttribute(might)`
  (the minimal-d6 defense shape, proving both kinds coexist), table
  `[{i64::MIN: success}, {1: failure}]`, no naturals, no selection,
  damage `{success: 0, failure: 0}`, costs `[{focus: 1}]`,
  `ends_turn: false`, effect `E1` applied to self on success.
- E1: target self, `duration_rounds: 2`, one shared `mod_type` with policy
  `StackAll`, modifiers `[Roll +2 priority 0, Roll +1 priority 1]`
  (two contributions exercising fold ordering, not a bare sum).

Hand-calculated examples (arithmetic, no RNG claim; oracles recompute these
at B4 against recorded faces):

- `2d6 [3, 2] = 5` vs goblin `ward 5`: margin `0` → success → `3` damage
  (`6 → 3`). Actor Roll fold over base `5` with no modifiers; defense is
  the target's `ward` stat value `5` with no Dc modifiers.
- Same roll with E1 active on the hero: Roll `5 + 2 + 1 = 8`
  (priority order `0` then `1`) vs `5` → margin `3` → critical → `5` damage.
- `2d6 [6, 1] = 7` vs hero `ward 7`: margin `0` → success; selected die
  `0` shows `6`, matching the natural rule → shift `+1` → critical →
  `5` damage instead of `3`.
- `1d6 [4]` focus vs hero `might 8`: margin `-4` → success → E1 attached
  (`expires` at round `R+2`), `focus` spent (`2 → 1`), turn stays active.
- Accepted-but-failed attacks spend their costs (validation passed);
  malformed or rejected actions spend neither resources nor randomness
  (pre-draw validation; kernel transactional RNG).
- An explicit `EndTurn` by the active actor advances without spending or
  drawing (RNG streams identical pre/post).
- E1 applied in round `0` expires at the rollover reaching round `2`; a
  save in round `1` reloads with the identical `+3` breakdown, and the
  post-expiry breakdown is empty.

## Kernel mapping (why B2 is vacuous)

| Scenario need | Existing kernel API (read-only) |
|---|---|
| Roll bonus vs target stat defense | `resolve` with `RollSpec::Dice`, `Against::Stat{entity: target, stat, modifier_target}`, `query_numeric` on `Roll(tag)`/`Dc(tag)` |
| Two-modifier fold with ordering | `Modifier{id, source, target: Roll(tag), op: Add(Int), mod_type, name, condition: None, priority}`, `ModifierPipeline::new(defs, {mod_type: StackAll})` |
| Missing policy gate | `policies.get(mod_type)` errors at query time — hence B1 authors one policy per effect mod-type (no silent default) |
| Pools, tables, naturals, dice | `ResourcePool::{new,spend,refresh}`, `OutcomeTable::{new,evaluate}` incl. `Shift` clamping, `DiceExpr` grammar |
| Turn/refresh timing | Caller-supplied `RefreshEvent::{TurnStart,RoundStart}`; pools own no timeline |
| Effect lifetime | Caller-owned by T014 design ("Caller owns active modifier membership and lifetime") — sim-owned attached state in B3, no kernel change |
| Transient stat views | `StatBlock::{new,insert}` through the world issuing interner (`intern_stat`); `Modifier` has no serde, so B3 persists attached `(effect ULID, expires_round)` pairs and rebuilds modifiers from the hashed definition |

## Authoritative simulation contract (B3 mechanism summary; B3's task pins code)

- Definitions generalize to per-ability entries (dice, defense selector,
  table, damage, per-pool costs, `ends_turn`, optional effect, optional
  natural selector) with the encounter ability set addressed by ULID;
  `UnknownAbility` keeps its meaning for unlisted identities. Templates
  carry every pool; combatants carry one balance per template in template
  order plus attached effects; the definition embeds effect documents (with
  their modifier wire and policies) so all behavior-affecting bytes hash.
- Resolution builds a real pipeline per action: actor Roll modifiers from
  unexpired attached effects, target Dc modifiers likewise, target guard
  via a transient `StatBlock`, `natural_die` from the ability (bound
  against the parsed dice count in sim — data stores notation only, as in
  T016a). `ends_turn: false` skips the advance (active stays, no refresh);
  a new `EndTurn{actor}` action validates turn-holding and advances with no
  spend, no draw, no damage, no effect.
- Round rollover additionally drops effects whose `expires_round` is
  reached (silent: state and hash show it; no event). Costs check every
  pool before spending any (`InsufficientAction` gains its pool identity
  under B3's ADR with mechanical updates to existing constructions;
  `Display` stays byte-identical).
- The T016e load checks extend to the new shapes: per-pool identity/
  maximum/refresh agreement, costs drawn from declared pools, effect
  references resolving into the definition with sane durations, attached
  pairs resolving with future expiries, multi-ability coherence. Invalid
  saves still fail before publishing a World.
- Neutrality holds: no minimal-d6/srd-lite identifier, name, die count,
  threshold, damage, margin, pool, or policy value in production; the
  neutral-scan test extends to the new files.

## Content and replay delivery

B1 produces `rulesets/srd-lite/` (canonical source) and
`campaigns/fixtures/combat_srd/` (complete loadable campaign reusing the
T016a self-contained pattern: embedded ruleset/ability/table/effect
documents, empty requires, gate 8 untouched). Scenario facts stay
identical: placements, initiatives, areas, and base stat/health numbers;
everything ruleset-governed varies under new ULIDs (suggested block
31–47, disjoint from T016a's 11–22; B1 finalizes the map).

Schema evolution (B1): one new family `crpg.effect/1` (registry 19 → 20,
22nd generated schema file); `crpg.ruleset/1 → /2` (plural pools, policy
table if B1 keeps it ruleset-level rather than effect-level — B1 decides
against the no-conflict requirement); `crpg.ability/1 → /2` (per-pool
costs, `ends_turn`, optional effect, defense selector, optional natural
selector); migration edges for both bumps mapping old content to its
preserved meaning (missing defense → actor-attribute, single cost →
single-pool entry, `ends_turn: true`). Minimal-d6 bytes and the
`migration_v1` golden stay untouched; new families/edges get gate coverage
in the B1 suite. Data validation gains positioned codes for the new
reference sites (effect refs, cost pools, defense stats, policy coverage);
B1 pins their spellings.

B4 provides `fixtures/combat_srd.replay` (seed probed ascending `0..=1023`,
first satisfying: at least one heavy failure, one heavy success, one
natural-6 shift hit, one focus success with E1 applied and later expired,
an explicit `EndTurn`, a rejected pool spend, exactly one death within
`K <= 12` ticks with `T = 4` trailing; if unsatisfiable, stop and report
rather than changing content) and two independently generated native
goldens (`srd_lite_*` scope naming per T009c convention). T016c's
`combat_basic` artifacts stay byte-identical and green.

B5 runs the unchanged `crpgc replay --campaign <root> --golden <baseline>`
command over both campaigns outside the repository working directory; no
new flag is anticipated (content selects semantics, per T016d) — B5's
contract confirms or owns any flag it actually needs.

## Required acceptance coverage

- Production load/validation and canonical round trip of the srd-lite
  ruleset and campaign through the data path; malformed/unknown/duplicate
  references and every new limit at largest-valid/first-invalid values.
- The six scenario proofs from §5 of the remediation plan (modified roll
  vs target defense with breakdowns; two abilities/two pools with
  independent balances and triggers; turn-staying success + explicit
  completion + spend-nothing rejections; effect lifetime across a midway
  save with identical pre/post breakdowns; natural-face invocation;
  generic path with no package-name branch — extend the neutral scan).
- Full-world rollback for representative invalid inputs across the new
  shapes (unknown ability, wrong-pool/empty-pool costs, out-of-range
  natural selector, out-of-turn/dead/unknown-ability `EndTurn`).
- Same seed/content/inputs repeat every hash; mutating faces, ward,
  damage, pools, or effect numbers changes independently expected
  behavior; mutating health, balances, round, active, timeline, attached
  effects, or pending events changes the hash.
- Exactly one dead combatant at the end with positive-health survivors;
  hash equality alone is insufficient; trailing ticks attack nothing.
- Existing `combat_basic` replay, goldens, CLI suites, and all prior
  suites pass unmodified (B3 behavior preservation is a constraint, not a
  follow-up).

## Native goldens and required gates

Use the pinned toolchain, normal test profile, and default features.
Generate `combat_srd` goldens independently on native
`x86_64-pc-windows-msvc` and genuine `x86_64-unknown-linux-gnu` through
the production replay path with a temporary deleted-before-finish helper,
reviewed before acceptance, verified read-only afterwards. Never copy
hashes between targets, skip missing baselines, tolerate mismatches, or
regenerate goldens during tests.

Reserved suite names (established in the executable children):

```text
cargo test -p crpg-data --test srd_content --locked
cargo test -p crpg-sim --test combat_multi --locked
cargo test -p crpg-testkit --test srd_replay --locked
cargo test -p crpg-cli --test srd_replay --locked
```

Each implementation child runs, for its literal crate name in place of
`<crate>`, on both supported native targets:

```text
cargo fmt --all
cargo clippy -p <crate> --all-targets -- -D warnings
cargo test -p <crate>
python tools/lint/deps.py
python tools/lint/determinism.py
python -m unittest discover -s tools/lint -p "test_*.py"
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo deny check
git diff --check
```

Each child's stopping command is its `cargo test -p <crate> --locked` after
its focused coverage and full required gates. The final milestone stopping
command is `cargo test -p crpg-cli --test srd_replay --locked`, on both
native targets. That suite must invoke the real `crpgc replay` binary over
the authored srd-lite replay and scoped golden.
