## Task
Make the host run what ADR-0036 and T026p built: bind a navigation mesh at
area load and keep sim's routes on it (H1, H5), compute routes for clients'
destinations (H2, H3, S3), speak protocol v4 to a session that asks for it
(lane 0 version 4 plus the lane-1 movement subprotocol `0xA1`, HM-1), admit
and decide lane-1 intents with exactly one ordered receipt each (HM-2..HM-4),
send position anchors and samples under the per-viewer position grant (H4,
HM-5..HM-7), and publish `HistoryEvent::Moved` (HM-8). Today the host has no
navigation at all (`crates/crpg-server/src/host.rs:779–803` holds no mesh),
discards stage 4's movement facts (`:3214–3216`), withholds `Moved`
(`:4462`, `:4498`), and speaks v1, v2 or v3 per session (`:1195–1202`).

- **T037a — navigation and trusted movement.** The `crpg-nav` edge and H5's
  compile-time asserts; `bind_nav_mesh` / `bind_area_bounds` (H1); the one
  route computation (H2's path, S3's snap) behind trusted `move_to`, `halt`,
  `place` and the turn-based `host_move` (ADR-0036 W7, M6). No wire.
- **T037b — v4 sessions (H-filter).** `bind_v4_peer`, the lane-0 v4 codec
  per session, `PositionRow`s and the position grant (HM-6), v4 pages and
  the anchoring staging page (HM-7), and `Moved` (HM-8).
- **T037c — the turn-based move and samples.** `DeclareMove` (H3, HM-9) and
  the per-tick sample datagrams with their refresh interval (H4, HM-5).
- **T037d — lane 1 (H-filter).** `ingest_move`, admission (HM-2, HM-3), the
  decision window and receipts (H2, HM-4), and HM-10.
- **T037e — real data, end to end (`crpg-testkit`).** Authored area bounds
  and authored movement rules through the host and a v4 client.

v1, v2 and v3 sessions keep every byte and rule they have; a host that never
calls a T037 operation behaves exactly as today.

## Readings
Design decisions this contract makes. Each needs approval with the contract.

1. **A v4 session is a v3 session plus a v4 state.** HM-1 says T140's
   H-1..H-7 and T141's H-8 apply to v4 sessions unchanged with the v4 names
   (`tasks/T026p.md:968–972`), and T026p wraps v3 ops rather than copying
   them (Reading 2, `:174–184`). So `V3Session`
   (`crates/crpg-server/src/host_v3.rs:136–157`) gains
   `v4: Option<Box<V4State>>`; every `session.v3.is_some()` path (binding,
   staging, pacing, throttle, pages, receipts, the cache, `cached_status_v3`)
   serves v4 sessions, and only the points that produce or read bytes branch
   on `v4`. *Rejected:* a separate v4 session type (duplicates about 900
   lines of T141c–e that would drift).
2. **Mesh input: a mesh, or the area's two bounds.** `bind_nav_mesh` takes a
   `crpg_nav::NavMesh` (a later baked artifact, spec §6.3, needs no API
   change); `bind_area_bounds(min, max)` is H1's v1 bake from `Area.bounds`'
   two fields (`crates/crpg-data/src/types.rs:250–257`):
   `bake_box(min[1], rect(min.x, min.z, max.x, max.z), &[])`, the floor at
   the bounds' lowest `y`. *Rejected:* a `&crpg_data::Area` parameter (a
   normal `crpg-data` edge for two arrays; the user declined even a test-only
   `crpg-data` edge in T141 Question 2, `tasks/T141.md:1708–1720`); baking
   in the caller only (H1 makes it the host's step).
3. **The mesh is host state, not checkpointed.** `World.nav` (the revision)
   is saved; the mesh is not. A restored host has `nav_revision() == None`
   until the embedding binds the mesh again; binding the same mesh is then a
   no-op for routes, because `bind_nav` of the bound revision changes
   nothing (`crates/crpg-sim/src/movement.rs:706–716`). Until then every
   route request is refused (`NoNavMesh`, or `IllegalAction` on the wire).
   *Rejected:* mesh bytes in the checkpoint (a new checkpoint version, S-set,
   for bytes the area data already determines).
4. **The revision is announced by the trusted API only, for now.** H1 says
   "Announce the revision to clients with the area" (`:424`), but no v4 op
   carries a revision: T026p defined none (`tasks/T026p.md:326–377`). Its
   only reader is G2's prediction gate (`:453–458`), which is T026's. T037
   exposes `Host::nav_revision()`; the wire announcement is a `crpg-net`
   task the manager files before T026 ("Manager edits"). *Rejected:* putting
   it in an existing op (changes T026p's approved bytes).
5. **Off-mesh means `locate` is `None`, and only binding places.**
   `bind_nav_mesh` places every mover whose position `locate`s to no polygon
   (`crates/crpg-nav/src/query.rs:79–86`, boundary included) at
   `nearest_on_mesh` of it (`:87–92`), ascending `EntityId`. A mover created
   later (spawn, join, area transfer) is the caller's to `place` (M6,
   `:214–216`); a route request from an off-mesh mover is refused
   (`StartOffMesh`). *Rejected:* re-placing off-mesh movers before every
   query (a client intent would silently teleport a creature, against A1).
6. **One route computation, S3 first.** `plan_route` is the one function
   behind `move_to`, `host_move`, `DeclareMove` and lane-1 `MoveTo`: the
   mover's position as `from`, then
   `nearest_on_mesh(snap(measure, destination))` as the goal, then
   `find_path` (H2, `:426–432`; S3, `:327–333`). `measure` is the encounter
   definition's `TurnMovement.measure` when the world has an encounter with
   movement rules (`crates/crpg-sim/src/movement.rs:90–99`), else
   `Measure::Euclidean`; `snap` is the identity in v1 (`:384–388`). The
   route copies `NavPath::into_points()` (`crates/crpg-nav/src/path.rs:27`)
   whole (A2, R5).
7. **Route tags are request identities.** A lane-1 route is
   `RouteTag(seq)` of its intent; a `DeclareMove` route is `RouteTag(seq)` of
   its lane-0 intent; a trusted host route is `HOST_ROUTE_TAG` =
   `RouteTag(0)` (lane sequences start at 1, so they never collide with 0).
   The tag is hashed with the route, so it must be deterministic. *Rejected:*
   a host counter (not checkpointed, so a restored host would tag the same
   play differently and its hashes would diverge).
8. **The AI moves through trusted host operations (W7).** `move_to` and
   `halt` are zero-event operations with no record; `host_move` is the
   turn-based move recorded as a `HostOp::Action` host record (T141s,
   `crates/crpg-server/src/capture.rs:164–173`): a TB move is a host action,
   and its `Moved` envelope says which kind. *Rejected:* a new
   `HostOp::Move` (a checkpoint serde vocabulary change, S-set).
9. **Lane-1 admission is synchronous.** `ingest_move` runs every check and,
   if the intent is admitted, queues it for the next decision, in one call.
   Lane-1 bytes are never staged in the lane-0 FIFO, because `pump`'s public
   `PumpSummary` and `AdmissionResult` are built by struct literal in
   existing tests (`crates/crpg-server/tests/host_quic.rs:78–88`,
   `crates/crpg-server/tests/host_capture.rs:725`) and could carry no
   pending outcome. HM-3 holds: a lane-1 frame spends the session's shared
   intent buckets per attempt, needs the same per-peer and host ingress room
   `ingest` checks (`crates/crpg-server/src/host.rs:1435–1442`) and is
   refused `QueueFull` without it, but never occupies that room.
10. **Which HM-2 refusals are answered.** Steps 1–8 refuse with no receipt
    and no sequence consumed, exactly as lane 0's decode, epoch, sequence
    and ingest refusals (`crates/crpg-server/src/host.rs:1600–1661`,
    `:1427–1442`); a conforming `MoveOutbox` (window 8,
    `crates/crpg-net/src/outbox_v4.rs:54`) within the policy rate never
    trips 7 or step 8's in-flight test (step 8's egress test trips only while
    the session's egress is full, as lane 0's `QueueFull` does, Reading 23),
    and a sender that is refused recovers by resending its pending intents. Step 9 (`NotAuthorized`) consumes the sequence and is answered
    with a receipt, as lane 0's resolution refusals are (`:1670–1695`).
    "Admitted" in L3 (`:396–400`) means "its sequence was consumed": every
    such intent gets exactly one receipt. *Rejected:* receipts for steps 7–8
    (a receipt must wait behind the pending intents before it, so it would
    itself count as unreceipted and the queue would have no hard bound).
11. **"Unreceipted" (HM-2 step 8)** is the session's admitted intents whose
    receipt is not yet released plus released receipts the transport has not
    yet taken (`take_move_receipts`). So an adapter that stops taking
    receipts stops admission, as lane 0's egress caps do.
12. **The decision window is one `advance` call.** Pending lane-1 intents are
    decided at the start of `advance`, after the time check and before the
    turn timer and the tick, paused or running. Decided at server tick `t`,
    an accepted route starts in the stage 4 of tick `t + 1`: in this same
    call when running, on the first tick after unpause when paused (W5,
    `:266–267`). H2's "at most one navigation query per actor per tick"
    (`:426–428`) is read as one per actor per window; a running `advance`
    ticks at most once per window (`tasks/T141.md:695–700`). `tick()` never
    decides. *Rejected:* deciding inside `tick` (a tick refused for
    `CaptureFull` changes nothing, T141 S-4, `:591–600`, but decisions made
    before its refusal would have committed) and deciding at admission (an
    earlier intent could then never be superseded).
13. **Superseding is per actor across sessions.** In one window the last
    admitted intent (host-wide admission order) for an entity wins and every
    earlier one for it is `Superseded`, whichever session sent it: routes
    are replaced whole (R5), so only the last could take effect.
14. **`WrongMode` covers `MoveTo` and `Halt`.** HM-4's `WrongMode` ("a
    turn-based participant", `tasks/T026p.md:994–995`) is applied to every
    lane-1 intent whose actor is a combatant of a turn-based encounter: lane
    1 is the real-time and exploration lane, and turn-based moves are
    `DeclareMove` (W2, `:245–247`). *Rejected:* accepting `Halt` there
    (`clear_route` would succeed as a no-op, `crates/crpg-sim/src/movement.rs:807–820`,
    but clients would need two rules).
15. **Lane-1 rejection receipts spend the failure budget but are never
    dropped.** HM-3's "count toward the failure budgets" is read as "spend
    them": a `Rejected` lane-1 receipt calls the session's failure buckets
    (`crates/crpg-server/src/host.rs:3955–3959`), so lane-1 refusals share the
    budget with lane 0, and is released whatever they say, because L3 needs
    exactly one receipt per admitted intent and a gap would break the
    client's in-order `MoveOutbox::receive` (`tasks/T026p.md:955–962`).
    *Rejected:* dropping it as lane 0 does (a reliable stream with a hole).
16. **The position grant is presence minus a withheld list.** HM-6's default
    (`tasks/T026p.md:1002–1008`, the user's Question 1 (a), `:1571–1592`):
    `granted` is true exactly when the viewer has the entity's presence,
    unless the operator withholds that entity's position from that viewer
    with `set_position_withheld`. The list is empty by default, so the
    default is exactly HM-6; it is the host-side per-creature, per-player bit
    HM-6 asks the host to keep, and the hook a later fog-of-war or stealth
    policy calls. It is neither an authoring setting nor a perception rule.
    *Rejected:* no hook (HM-6's "a revoked grant is `granted: false` from the
    tick it is revoked" would have no host path and no test).
17. **`Moved` follows HM-8 literally** (`tasks/T026p.md:1013–1021`): the
    entity id is the viewer's post-page id (no pre-page fallback, unlike the
    v3 candidates' `after.or(before)`, `tasks/T141.md:927–936`), and
    `disclose` is that entity's row `granted` in the same page; an entity
    with no row is not disclosed.
18. **The staging page anchors (HM-7).** For a v4 session the staged delta
    after the `0x82` frames is a whole `project_page_v4` page (the anchors)
    followed by `Clock` and `HostFacts`, cut by `codec_v4::frame_spans`, so
    it may be several frames. The v4 outbox bound is therefore 94 entries
    and 2,880,916 bytes: T141's 90 / 2,852,148
    (`crates/crpg-server/src/host_v3.rs:35–40`) with the one 992-byte delta
    replaced by up to five frames: 1,024 `Position` ops of at most 28 bytes
    (28,672), `Clock` and `HostFacts` (at most 968 bytes, the 992-byte
    allowance less a 24-byte header) and five 24-byte headers (120), 29,760
    bytes in all (`tasks/T026p.md:607–609`). The throttle counts every
    staged delta frame.
19. **`DeclareMove` checks the turn before navigating.** Order: the
    `UseAbility` turn checks through `validate_action(EndTurn { actor })`
    (W4's own first step, `crates/crpg-sim/src/movement.rs:858–860`), then
    `plan_route`, then `validate_move` with the route, then the reservation
    and `perform_move`. The per-window query cap does not apply: lane 0 is
    window 1 and rate-limited, and a turn-based player may move several times
    while the host is paused (H3 shares H2's path computation, `:434`, not
    its lane-1 cadence). *Rejected:* navigating first (an out-of-turn player
    would spend a query and get `IllegalAction` instead of the turn error).
20. **Samples: every tick, refreshed every 20 ticks, one tick queued.** After
    every committed tick, each v4 session's `project_samples` runs with
    `refresh = server_tick % POLICY_SAMPLE_REFRESH_TICKS == 0`, 20 ticks (one
    second at 20 Hz, spec §2.5); its datagrams replace any the transport has
    not taken, which is datagram loss and is recovered by the next change or
    refresh. A walking creature samples every tick anyway, so the refresh
    only repairs a lost final ("stopped") sample, whose error is at most one
    tick's step (4 m at the U7 maximum, `:117–130`). Worst case at 1,024
    visible movers: 27 datagrams (ceil(1,024 / 38)) per peer per second.
    *Rejected:* 4 ticks (five times the refresh traffic to repair the same
    rare loss); appending untaken datagrams (unbounded when an adapter stalls).
21. **Route state never publishes on lane 0.** `move_to`, `halt`, `place`,
    `bind_nav_mesh` and lane-1 decisions change no v3 fact and no anchor
    (an anchor follows the grant, not the point), so they log no frame:
    movement reaches clients by samples (L4) and turn-based moves by `Moved`.
22. **Lane 1 never touches lane-0 state** (HM-10): its own sequence, cache,
    bucket and receipt queue per session (`POLICY_RETRY_CACHE_PER_PEER_LANE`
    is per lane, `crates/crpg-net/src/protocol.rs:147`); lane 0 stays
    window 1, and `RT` and exploration routes spend no resource (C5).
23. **Lane-1 bytes count toward the egress caps.** T026p Reading 14 says
    "Lane-1 traffic also counts toward every existing aggregate
    (`POLICY_INTENT_*`, the ingress and egress caps, the failure budgets)"
    (`tasks/T026p.md:298–299`), and Reading 15 leaves the aggregate-cap test
    to T037 (`:313–315`). So a v4 session's lane-1 egress is: its queued
    sample datagrams; its released, untaken receipts at their length; and,
    for each admitted slot not yet released, a reservation of one frame and
    `MAX_MOVE_RECEIPT_BYTES` (60, the largest receipt, `:607–609`). Every
    per-peer egress check of that session (frames ≤ 128, bytes ≤ 2 MiB:
    `room_for` and pacing, `crates/crpg-server/src/host.rs:2242–2247`,
    `:3909–3934`) counts them beside its delivery log, and the host's
    `egress_bytes` includes every session's lane-1 bytes, so lane 0 and
    lane 1 share one budget. Lane 1 never fails on it after admission: a
    slot's room is reserved when it is admitted (D-2 step 8), so its receipt
    is never dropped (L3); a resend that does not fit is not queued
    (`resent: false`); a tick's samples that do not fit are dropped whole
    (datagram loss, which the refresh repairs). Taking receipts or samples
    frees the room, as `acknowledge_delivery` frees lane-0 room. *Rejected:*
    exempting lane 1 from egress (departs from T026p's sentence, and a
    stalled adapter would then hold lane-1 bytes outside every cap).

## Interface
Additions only. Every public item has a doc comment (`#![warn(missing_docs)]`).
No `HashMap`/`HashSet`, clock, thread, sleep, socket, filesystem call or
float in `host.rs`, `host_v3.rs`, `host_v4.rs` or `nav.rs` (crate invariant
7). Types from `crpg_nav`, `crpg_net` and `crpg_sim` are used by path, not
re-exported; `Fx16_16` is `crpg_core::Fx16_16`. New `HostError` variants go after `NotV3Peer`
(`crates/crpg-server/src/host.rs:515–516`), in the order below; `Display`
stays `<VariantName> at host/admission`, `source()` stays `None`. Every
existing public item keeps its signature, fields, variants and `Display`; in
particular `DeliveryKind`, `PumpSummary`, `AdmissionResult` and
`AdvanceReport` (`:256–263`, `:374–387`, `:354–365`, `:449–456`) are
unchanged, because other crates and existing tests match or build them.

/// The tag of every route a trusted host operation sets (Reading 7).
pub const HOST_ROUTE_TAG: crpg_sim::RouteTag = crpg_sim::RouteTag(0);

/// What one navigation binding did (H1).
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NavBinding {
    /// BLAKE3 of the mesh's canonical bytes (R2).
    pub revision: crpg_sim::NavRevision,

## Errors
Five new `HostError` variants, appended after `NotV3Peer` in this order:
`NavBake(BakeError)`, `NoNavMesh`, `NoPath(NavError)`, `Move(MoveError)`
(T037a), `NotV4Peer` (T037b). `Display`: `"NavBake at host/admission"`,
`"NoNavMesh at host/admission"`, `"NoPath at host/admission"`,
`"Move at host/admission"`, `"NotV4Peer at host/admission"`; `source()` is
`None`. Every existing variant, payload and text is unchanged, and so are
`CheckpointError`'s. New `Invariant` texts: `"nav binding refused"`,
`"nav placement refused"`, `"v4 plan exceeds the outbox bound"`.
No codec error and no rejection code is added (T026p Reading 3).

| Refusal | Result |
|---|---|
| bake of the area bounds fails | `Err(NavBake(e))`, nothing changes |
| route request with no mesh bound (trusted) | `Err(NoNavMesh)` |
| `find_path` fails (trusted) | `Err(NoPath(e))` |
| sim refuses `place`, `set_route`, `clear_route`, `validate_move` (trusted) | `Err(Move(e))` |
| `host_move` turn check | `Err(Combat(e))` |
| v4-only call on a v1–v3 session | `Err(NotV4Peer)` |
| `DeclareMove`: actor unmapped, not granted or not controlled | receipt `Rejected(NotAuthorized)` (17) |
| `DeclareMove` outside turn-based mode | receipt `Rejected(WrongMode)` (22); `AdmissionResult` `IllegalAction` |
| `DeclareMove`: other turn error, no mesh, no path, cost or route refusal | receipt `Rejected(IllegalAction)` (18) |
| lane-1 frame refused before admission | `MoveAdmission::Refused`, no receipt |
| lane-1 actor not controlled | `MoveAdmission::Rejected`, receipt `Rejected(NotAuthorized)` |
| lane-1 decision: superseded / turn-based actor / any other refusal | receipt `Superseded` / `Rejected(WrongMode)` / `Rejected(IllegalAction)` |
