Append the exact bridge API for immutable permitted replica queries, prediction

No new MoveTo fields, speed/range/nav rule or public engine signature is invented
from the spike. If lane-0 window ever grows, it is a separately approved net
policy/conformance task, not a bridge behavior change.

## Behaviour

E015 requires speculative state in a separate local movement buffer, outside
sim and the immutable authoritative replica. Reconcile at the acknowledged seq,
then replay newer local inputs using the approved movement rules. Server tick
is time, seq is identity; neither grants client scheduling authority. Never
predict attacks, damage, resources, turns or remote entity authority.

Remote entities interpolate only permitted samples. Old/out-of-order ack must
not regress accepted state; explicit resync/fenced epoch clears incompatible
buffered inputs. Define drop/overflow/resync policy before implementation. No
hidden entities can appear through interpolation history after revocation.
Spatial presentation smoothing cannot alter authoritative hashes or receipts.

## Constraints

[Standing rules](POST-T018-RULES.md) apply; sole bridge crate, no sim/net edits
or new dependencies without approval. Godot stays isolated to this crate;
Linux headless server/tooling must never acquire a Godot dependency. No
cross-target lockstep promise or movement-spike code copied as approved API.

## Test

Public `prediction` suite: acknowledged snap-and-replay, clean-path control,
out-of-order/duplicate/lost acks, bounded buffer saturation, reconnect/resync,
visibility revocation and no combat/replica authority mutation. Independent
authoritative trajectory is the oracle; a corrupted ack/sample must be detected.
ADR-0004's 150 ms RTT / ±15 ms jitter / 3% loss scenario is required; approve
measurable correction tolerance with E019 rather than inventing a 60 fps gate.

```text
cargo test -p crpg-godot --test prediction --locked
cargo clippy -p crpg-godot --all-targets --locked -- -D warnings
```

Windows engine/presentation smoke command must be pinned to the actual Godot

public prediction logic tests and workspace/headless dependency gates remain
mandatory; this is not a promise of Linux GUI builds. Common gates then stopping
command: `cargo test -p crpg-godot --locked`.

## Revision 2026-11-21 (T026c): what is met, why prediction waits, what it will need

Written by the Claude architect with `tasks/T049.md` and `tasks/T050.md`.
Not approved; the deferral is D77e (`tasks/DECISIONS-D77.md`).
**Decided 2026-11-22: the user chose D77e (a), defer.**

**Met since the gate text.** Navigation and authoritative movement (T035,
T036), the lane-1 protocol with processed-seq and server-tick receipts
(T026p1–p5, `crates/crpg-net/src/movement_v4.rs:89–154`; `MoveOutbox`,
`crates/crpg-net/src/outbox_v4.rs:54`), the host adapter (T037a–e), the server
run loop (T154) and the bridge's v4 session (T151). ADR-0036 G2 now pins the
scope this file asked D13 for (`docs/adr/0036-movement-and-navigation.md:453–458`):
only actors the peer controls, never in turn-based play, only when the
client's baked mesh revision equals the announced one, local `find_path` plus
sim's pure functions, re-timed to `start_tick` on `Accepted`, dropped on
`Rejected` or `Superseded`, corrected beyond a measured threshold.

**Why it waits (recommended, D77e (a)).** The only Godot session is the
embedded one: client and server are one process, and a click reaches the
next 50 ms server cycle through an in-memory link. With T049a the whole lag
from click to first drawn motion is at most one cycle plus the 100 ms render
delay, the same for every row; there is no network round trip to hide, so
prediction would add a second movement path (and its corrections) with no
visible gain, while ADR-0004's target is 150 ms RTT and 3 % loss
(`docs/adr/0004-quic-movement-spike.md:11`), which only a remote client has.

**What a T026 contract will need first** (none exists today):
1. **A remote Godot session** ("join a server", T151 Question 1's later task,
   `tasks/T151.md:1073–1085`), which is where latency exists.
2. **The mesh revision announced to clients** (backlog row "announce the nav
   revision to clients (T037 Reading 4), before T026", `tasks/BACKLOG.md:370`):
   G2 forbids prediction without it.
3. **The mover's speed on the client.** Samples carry only entity, point and
   moving (`crates/crpg-net/src/movement_v4.rs:131–151`); the client must
   either read the ruleset's speed from its campaign data or get it on the
   wire (a `crpg-net` decision).
4. **The `crpg-godot → crpg-nav` path edge**, which `ALLOWED` permits
   (`tools/lint/deps.py:71`) but ADR-0036 says needs approval (`:463`).
5. **A measured correction threshold** (D06/E019; ADR-0004's "visible" is
   more than 0.5 world units, `docs/adr/0004-quic-movement-spike.md:50`).

**What it will build on.** T049a's smoother already estimates the server
time (`tasks/T049.md` Reading 2) and owns each row's drawn position; a
prediction would replace the drawn position of a controlled row while a
prediction is live, and fall back to the smoothed one when it ends. The
in-flight bound is `MoveOutbox`'s window, 8 (`POLICY_MOVE_IN_FLIGHT`).

**Superseded here.** "Interface — prerequisite and exact-API gate" (the
prerequisites are met as listed above; the bridge API is T151's and T050a's),
the `--test prediction` command (a future contract names its own), and the
Definition-of-done boxes (they move to that contract). Behaviour, Constraints
and Out of scope stand as requirements on it.
