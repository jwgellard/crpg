# T023c — QUIC flow-control window limits (`crpg-net-quic`)

## Task / Crate(s) / Purpose

Sole crate: `crpg-net-quic` (ADR-0024). Phase 4. Filed 2026-10-05 as a
prerequisite to [T023b](T023b.md) by the user's decision recorded in T023b's
"Implementation blocker and decision — 2026-10-05 (UTC)".

T023 fixed the QUIC flow-control windows in `src/tls.rs`. A stalled client
therefore absorbs about 1 MiB of small delivery frames before the server's
`try_send` reports `QueueFull` (measured: 40,331 frames of 22 bytes), so
T023b's stall cases cannot be written as designed. This task makes the
windows **tightening-only limits** whose v1 values equal today's values. It
also makes the first attempt at the intermittent Windows close-code failure
of `graceful_close_flushes_and_reports_codes`, as the user chose, before any
test expectation is changed.

### C§1. Findings

#### C§1.1 What `tls.rs` sets today

`transport()` in `src/tls.rs` builds one `quinn::TransportConfig` per
endpoint from two private constants:

| `TransportConfig` call | Server (`SERVER_WINDOWS`) | Client (`CLIENT_WINDOWS`) |
|---|---|---|
| `max_concurrent_bidi_streams` | 1 | 0 |
| `max_concurrent_uni_streams` | 0 | 0 |
| `stream_receive_window` | 65,536 | 1,048,576 |
| `receive_window` | 131,072 | 2,097,152 |
| `send_window` | 1,048,576 | 262,144 |
| `datagram_receive_buffer_size` | `None` | `None` |
| `datagram_send_buffer_size` | 0 | 0 |
| `max_idle_timeout`, `keep_alive_interval` | from limits | from limits |

These are exactly E§8.3. The windows are therefore **not** a uniform 1 MiB:
only the client's stream receive window and the server's send window are
1 MiB.

#### C§1.2 What each window controls (quinn-proto 0.11.19)

- **`stream_receive_window` (W)** is advertised as all three
  `initial_max_stream_data_*` transport parameters. For the one lane
  stream it is the number of bytes the peer may send beyond what this
  endpoint's application has **read**. After a read, a `MAX_STREAM_DATA`
  update is sent only when the credit has grown by at least `W / 8`
  (integer division; `recv.rs`, `max_stream_data`).
- **`receive_window` (C)** is advertised as `initial_max_data`, the same
  bound across all streams, with an update threshold of `C / 8`
  (`state.rs`, `add_read_credits`). With one stream, C binds only if it is
  below W. Crypto and DATAGRAM frames do not count.
- **`send_window` (S)** bounds `buffered_data`: bytes accepted from this
  endpoint's writes and not yet released. A write is limited to
  `min(peer credit − sent, S − buffered)` (`state.rs`, `write_limit`).
  Acknowledged data is released (`state.rs`, on ACK), so **S does not bound
  what a stalled peer absorbs**: a peer that stops reading still
  acknowledges. S bounds this endpoint's own buffer memory and its bytes in
  flight.
- **What bounds a stalled peer** is therefore the stalled peer's own
  receive windows, which it advertises. A server cannot impose them on a
  client, so in production its protection against a slow client remains its
  outbound queue caps, its send window (memory) and T023b's slow-consumer
  fence (B§16 Q6). In tests, the client's limits are under the test's
  control.
- **Interactions.** quinn documents worst-case receive memory as
  `max_concurrent_bidi_streams × stream_receive_window`, capped by
  `receive_window`. Here that is one stream per connection: the server
  holds at most 65,536 bytes of unread intent data per connection, and the
  client at most 1,048,576 of unread delta data. DATAGRAM frames are off
  (`datagram_receive_buffer_size(None)`) and are not flow controlled
  anyway. quinn imposes no minimum on any window: W and C are `VarInt`s
  (below 2^62) and S is a `u64`. A window smaller than one frame still makes
  progress, because the lane reader consumes partial frames as they arrive.
  The floors in C§6 are a policy, not a liveness requirement.

#### C§1.3 The exact stall bound

Take a server whose per-connection outbound queue holds 1 frame. A client
stops at an inbound queue of 1 frame (its reader queues frame 1, parks
frame 2 and stops reading). Payload frames of `p` bytes have framed size
`F = p + 4`. The stream carries the 21-byte welcome first (`4 + 17`).

The client reads `21 + 2F` bytes. If `21 + 2F < W / 8` and
`21 + 2F < C / 8`, it sends **no** window update, so the server's stream
credit stays exactly `min(W, C)`. The server's writer then hands
`⌊(min(W, C) − 21) / F⌋` complete frames to QUIC, holds one more popped
frame (partly written) and has one queued. So the number of `Ok` sends
before a lasting `QueueFull` is:

```text
N = ⌊(min(W, C) − 21) / F⌋ + 2          (delta direction, 1-frame queues)
N = ⌊(min(W, C) − 22) / F⌋ + 2          (intent direction; the 16-byte-credential hello is 22 framed bytes)
```

If the no-update condition fails, the client sends updates whose final
value depends on how its reads were chunked, so the count is not
deterministic. Tests that assert an exact count must satisfy the
condition.

Measured on Linux/GNU (environment in C§1.5). "Formula" is the expression
above.

#### C§1.4 The Windows close-code failure

`graceful_close_flushes_and_reports_codes` (case 17), in its "Server Discard
with N queued" part, queues 64 × 65,536-byte frames for a v1 client, closes
with `(SessionFenced, Discard)`, and requires the client's last result to
be `Peer { code: 9 }`. Windows CI intermittently sees `Reset`.

**Why it never reproduced on Linux.** The default case was instrumented
(test-only hooks reading quinn's `Connection::stats()`). In all 32 Linux
runs of the original shape (8 per option in the last table below), the
server had sent nothing that the client had not received when `close` was
called: bytes in flight were 0. The debug-build
test thread generates each 64 KiB pattern slowly enough that the transfer
stalls before the close. The client's reader parks with 32 frames queued,
16 more sit in QUIC's 1 MiB window, k = 47–48 arrive, and 15–16 are
discarded. With nothing in flight there is nothing to lose, whatever the
UDP buffer size, which is why shrinking the buffers to 32 KiB changed
nothing.

**Reproduced on Linux with a slow receiver.** A test-only relay passes
server → client datagrams through a modelled receive buffer of B bytes,
drained one datagram per 30 µs, and drops overflow. That stands in for a
Windows receiver with a small default `SO_RCVBUF`; quinn 0.11 never sets
socket buffer sizes. The frames were generated before connecting, so the
test thread outruns the network as it may on Windows.

| Config (server send S / client W, C) | B = 64 KiB: `Peer {9}` / `Reset` | B = 32 KiB | Bytes in flight at close (B = 64 KiB) |
|---|---|---|---|
| v1 (1,048,576 / 1,048,576, 2,097,152) | **1 / 33** (34 runs) | 0 / 10 | 132–289 KB |
| S = 65,540, client v1 | **32 / 2** (34 runs) | 3 / 7 | 24–67 KB |
| client W = C = 65,540, server v1 | **34 / 0** (34 runs) | 6 / 4 | 13–47 KB |
| both of the above | 20 / 0 | 4 / 6 | — |
| client W = C = 262,144 | 4 / 16 | 0 / 10 | — |
| v1, lossless relay (B = 16 MiB) | 9 / 1 | — | 180–938 KB |

In every `Reset` run, the client received **no** `CONNECTION_CLOSE` frame,
although the server received 12–37 datagrams from it after the close. The
`Reset` arrived 87–93 ms after `close` (219 ms in the lossless run, with a
10 ms RTT), which is quinn's 3 × PTO close timer. In every `Peer {9}` run,
exactly one `CONNECTION_CLOSE` arrived within 0.8–2.5 ms.

**Root cause (in quinn-proto 0.11.19, confirmed by experiment).** In
`Connection::poll_transmit`, a packet is congestion controlled when
`ack_eliciting` is true. That is computed from pending control frames and
`can_send_stream_data()`, and it is **not** cleared when the only frame to
send is `CONNECTION_CLOSE`. A `Discard` close leaves unsent lane data in
quinn's send buffer, so the close packet is congestion controlled. In the
closed state, quinn processes no ACKs (`process_decrypted_packet` looks
only for a peer's close), so bytes in flight never fall. If
`bytes_in_flight + one datagram ≥ cwnd` at the moment of `close`, quinn
never sends the close: not at first, and not in answer to the peer's later
packets. The server drains after 3 × PTO, and the client's next packet gets
a stateless reset, which becomes `ConnectionError::Reset` →
`CloseReason::Reset`.

A scratch copy of quinn-proto patched with one line (inside
`poll_transmit`, after `ack_eliciting` is computed:
`if close { ack_eliciting = false; }`) turned the v1 row at B = 64 KiB from
1 / 33 into **10 / 0**, and kept both tightened rows at 10 / 0. The patch is
evidence only. It is not proposed for this crate (C§11, C§12 Q6).

**What smaller windows do.** Bytes in flight are at most
`min(server S, client credit beyond its reads, cwnd)`. Tightening either
window keeps them small, so `bytes_in_flight + one datagram < cwnd` holds far
more often when `close` runs. The close is then sent at once, and loss of
it is recovered by the normal closed-state replies. This **lowers** the
exposure (33/34 → 2/34 or 0/34 in the 64 KiB model). It does **not** remove
it: losses can cut cwnd below 64 KiB (the 32 KiB model). Whether Windows CI
resembles the 64 KiB or the 32 KiB model is not known from here.

**The test's own shape under each option** (original test, Linux loopback,
8 runs each, no relay):

| Option | k delivered | Discarded | `QueueFull` retries | Outcome |
|---|---|---|---|---|
| v1 (today) | 47–48 | 15–16 | 0 | `Peer {9}` 8/8 |
| server `send_window_bytes = 65_540` | 47 | 16 | 0 | `Peer {9}` 8/8 |
| client stream and connection windows 65,540 | 34 | 29 | 0 | `Peer {9}` 8/8 |
| client stream 262,144 / connection 524,288 | 36 | 27 | 0 | `Peer {9}` 8/8 |

The server-send option leaves the test's shape unchanged: the same prefix,
and 16 frames of headroom below the 32-frame (2 MiB) outbound queue. Every
`try_send` in that loop is `expect("send")`, so headroom matters. The
client-window option leaves only about 3 frames of headroom, so on a host
where the test thread outruns the network it risks a new `QueueFull`
panic. The test's assertions (in-order prefix, `k + discarded ≤ 64`,
`Peer { code: 9 }`, `Local(SessionFenced)`) hold under every option.

### C§2. Decisions this contract makes

1. **Six new limit fields, three per endpoint**, one per quinn window, with
   v1 values equal to C§1.1. Behaviour is unchanged unless a caller
   tightens them (C§12 Q1, Q2).
2. **Floors are one maximal frame of the direction plus its header**:
   4,100 bytes for intents and 65,540 for deltas. A connection window is at
   least its stream window (C§6, C§12 Q3, Q4).
3. **Not a wire change.** Transport parameters are negotiated in every
   handshake and peers must honour what the other side advertises, so ALPN
   `crpg-lane0/1` stays (C§7 item 3).
4. **The other E§8.3 parameters stay fixed**: stream counts, no DATAGRAM,
   no migration, `max_incoming`, no 0-RTT.
5. **The close-code failure is addressed by configuration, not by changing
   an expectation.** The proposed edit (C§8.5) runs the Discard part of
   case 17 on a server with a tightened send window and changes no
   assertion. It is conditional on C§12 Q5.
6. **Case 4 is not edited.** The new fields get their own case (24), so
   T023's test stays byte-identical (C§12 Q7).

### C§4. Interface (exact public Rust)

`ServerLimits` gains three fields after `outbound`, in this order:

```rust
    /// QUIC stream receive window of the lane stream: intent bytes the
    /// client may send beyond what the server has read
    /// (`4_100..=65_536`).
    pub stream_window_bytes: u32,
    /// QUIC connection receive window
    /// (`stream_window_bytes..=131_072`).
    pub connection_window_bytes: u32,
    /// Bytes quinn may hold from this connection's writes until they are
    /// acknowledged, sent or not (`65_540..=1_048_576`).
    pub send_window_bytes: u32,
```

`ClientLimits` gains three fields after `outbound_bytes`, in this order:

```rust
    /// QUIC stream receive window of the lane stream: delta bytes the
    /// server may send beyond what the client has read
    /// (`65_540..=1_048_576`).
    pub stream_window_bytes: u32,
    /// QUIC connection receive window
    /// (`stream_window_bytes..=2_097_152`).
    pub connection_window_bytes: u32,
    /// Bytes quinn may hold from this connection's writes until they are
    /// acknowledged, sent or not (`4_100..=262_144`).
    pub send_window_bytes: u32,
```

`ServerLimits::v1()` sets 65,536 / 131,072 / 1,048,576, and
`ClientLimits::v1()` sets 1,048,576 / 2,097,152 / 262,144. Their doc
comments gain "windows 64 KiB / 128 KiB receive, 1 MiB send" (server) and
"windows 1 MiB / 2 MiB receive, 256 KiB send" (client).

`u32` rather than `usize`: the values are QUIC varints, `VarInt::from_u32`
is infallible, and every v1 value fits. The queue byte fields stay `usize`
because they are in-process accounting.

`limits.rs` gains private constants: `V1_SERVER_STREAM_WINDOW`,
`V1_SERVER_CONNECTION_WINDOW`, `V1_SERVER_SEND_WINDOW`,
`V1_CLIENT_STREAM_WINDOW`, `V1_CLIENT_CONNECTION_WINDOW`,
`V1_CLIENT_SEND_WINDOW`, and the floors `MIN_INTENT_WINDOW: u32 = 4_100`
and `MIN_DELTA_WINDOW: u32 = 65_540`. Each floor is tied to its protocol
constants by a compile-time check:

```rust
const _: () = assert!(MIN_INTENT_WINDOW as usize == MAX_INTENT_FRAME_BYTES + FRAME_HEADER_BYTES);
const _: () = assert!(MIN_DELTA_WINDOW as usize == MAX_DELTA_FRAME_BYTES + FRAME_HEADER_BYTES);
```

`FRAME_HEADER_BYTES` comes from `crate::handshake`. The module doc comment
names the window limits. Nothing else in the public API changes:
`ConfigError` and its `Display` text (`"<Variant> at quic/config"`) are
unchanged, and the new field names are the `field` strings.

### C§5. Mapping to `quinn::TransportConfig`

Private signatures in `tls.rs` become:

```rust
struct Windows {
    bidi_streams: u32,
    stream_receive_window: u32,
    receive_window: u32,
    send_window: u32,
}

fn transport(windows: &Windows, idle_timeout_ms: u32, keep_alive_ms: u32) -> TransportConfig;

pub(crate) fn server_config(identity: &ServerIdentity, limits: &ServerLimits) -> Option<quinn::ServerConfig>;

pub(crate) fn client_config(
    pin: CertificatePin,
    mismatch: Arc<AtomicBool>,
    limits: &ClientLimits,
) -> Option<quinn::ClientConfig>;
```

| Limit field | quinn call | Server | Client |
|---|---|---|---|
| `stream_window_bytes` | `stream_receive_window(VarInt::from_u32(v))` | server's | client's |
| `connection_window_bytes` | `receive_window(VarInt::from_u32(v))` | server's | client's |
| `send_window_bytes` | `send_window(u64::from(v))` | server's | client's |
| (fixed) | `max_concurrent_bidi_streams` | 1 | 0 |
| `idle_timeout_ms`, `keep_alive_ms`, `max_connections` | as today | as today | as today |

`server_config` reads `idle_timeout_ms`, `keep_alive_ms` and
`max_connections` from `limits`. `client_config` reads `idle_timeout_ms`
and `keep_alive_ms`. Every other call in `transport()` is unchanged. Each
endpoint advertises its own receive windows to the peer, and enforces its
own send window locally.

### C§6. Validation

`validate` keeps its rules: fields are checked in declaration order, so
the window fields come after every existing field, and `InvalidLimits`
(below a floor or inconsistent) is reported before `LoosensPolicy` (above
v1) for one field. Each new field uses the existing `bounded(field, value,
floor, v1)` helper:

| Endpoint | Field | Floor (`InvalidLimits` below) | v1 (`LoosensPolicy` above) |
|---|---|---|---|
| server | `stream_window_bytes` | 4,100 (`MIN_INTENT_WINDOW`) | 65,536 |
| server | `connection_window_bytes` | `self.stream_window_bytes` | 131,072 |
| server | `send_window_bytes` | 65,540 (`MIN_DELTA_WINDOW`) | 1,048,576 |
| client | `stream_window_bytes` | 65,540 (`MIN_DELTA_WINDOW`) | 1,048,576 |
| client | `connection_window_bytes` | `self.stream_window_bytes` | 2,097,152 |
| client | `send_window_bytes` | 4,100 (`MIN_INTENT_WINDOW`) | 262,144 |

Zero is below every floor. `bind` and `connect` report these errors
through `BindError::Config` and `ConnectError::Config` before any I/O, as
today.

Why one maximal frame plus its header:

1. It is the same rule the existing byte caps follow: every queue byte cap
   is at least one maximal frame of its direction.
2. A sender can always hand QUIC one complete maximal frame without
   waiting a round trip for credit, and a parked reader that wakes can
   find a complete next frame already buffered.
3. It keeps the update traffic proportionate. A receiver sends
   `MAX_STREAM_DATA` every `W / 8` bytes it reads, so a 65,540-byte delta
   window means one update per 8,192 bytes, while a 1 KiB window would mean
   one per 128 bytes and 512 round trips for one maximal delta.
4. It holds the hello (≤ 134 framed bytes) and the welcome (21) with room
   to spare.

It is not needed for liveness (C§1.2). A connection window below its stream
window would silently replace the stream window as the real bound, so it
is refused. This mirrors "host-wide ≥ per-connection".

### C§7. ADR-0025 addendum (verbatim, appended by the implementation)

The implementation appends this section after "Supersession and
corrections", with today's date and a signed agent-log entry:

> ## Addendum — <date> (UTC): flow-control windows are tightening-only limits (T023c)
>
> Accepted with the approval of [T023c](../../tasks/T023c.md).
>
> 1. The QUIC stream receive window, connection receive window and send
>    window of each endpoint are no longer fixed in `tls.rs`. They are the
>    `ServerLimits` and `ClientLimits` fields `stream_window_bytes`,
>    `connection_window_bytes` and `send_window_bytes`, under the same
>    tightening-only rule as every other limit. Their v1 values are the
>    values T023 fixed: server 65,536 / 131,072 / 1,048,576, client
>    1,048,576 / 2,097,152 / 262,144. An endpoint built from `v1()`
>    advertises and enforces exactly what it did before.
> 2. Each window holds at least one maximal frame of the direction it
>    carries, plus the 4-byte header: 4,100 bytes for intents (client
>    send, server receive) and 65,540 for deltas (server send, client
>    receive). A connection receive window is at least its stream receive
>    window.
> 3. This is not a wire change. Transport parameters are exchanged in the
>    QUIC handshake, and every QUIC peer must honour whatever the other side
>    advertises. The stream mapping, framing, hello and welcome, close codes
>    and ALPN `crpg-lane0/1` are unchanged, so no new ALPN is needed.
> 4. Every other E§8.3 parameter stays fixed: one client-initiated bidi
>    stream, no uni streams, no DATAGRAM extension, no migration,
>    `max_incoming = max_connections`, no 0-RTT.
> 5. Why: a peer that stops reading is bounded by its **own** receive
>    windows, not by the sender's send window, because quinn releases
>    acknowledged data and a stalled reader still acknowledges. Tests and
>    hosts that need a stalled client to push back within a few frames must
>    be able to tighten the client's receive windows. Operators can tighten
>    the per-connection buffer memory quinn may hold (up to
>    64 × (65,536 + 1,048,576) bytes on a v1 server).
> 6. Recorded transport behaviour, not changed here: quinn-proto 0.11.19
>    congestion-controls the `CONNECTION_CLOSE` packet of a locally closed
>    connection that still holds unsent stream data, and it processes no
>    ACKs once closed. If `bytes_in_flight + one datagram ≥ cwnd` when the
>    close happens, the close is never sent. The peer then learns of it
>    only from a stateless reset after the 3 × PTO drain
>    (`CloseReason::Reset`), or from its own idle timeout. Smaller windows
>    lower the bytes in flight and so the exposure, but do not remove it.
>    Evidence: T023c C§1.4.

### C§10. Downstream: amending T023b after T023c lands

T023b is not edited by this task. Once T023c lands, T023b's contract is
amended for these cases:

- **Case 12 `ingest_queue_full_holds_frame_and_resumes`.**
  - B's limits become `ClientLimits { inbound_frames: 1, inbound_bytes:
    65_536, stream_window_bytes: 65_540, connection_window_bytes: 65_540,
    ..ClientLimits::v1() }`. The server keeps `outbound` 1 frame / 65,536
    bytes per connection.

    B returns `QueueFull`. Every frame whose cumulative framed size, after
    the 21-byte welcome, stays within 65,540 is written, plus one partly
    written and one queued. For uniform framed size F,
    `N_B = ⌊65,519 / F⌋ + 2`:
    - 2,521 at 22-byte payloads (against 40,331 at v1);
    - 631 at 100 bytes;
    - 67 at 1,000 bytes.
  - That is exact only while 21 + B's first two framed frames < 8,192
    bytes. Otherwise B sends one window update, and only `≥` and stall
    behaviour may be asserted.
  - **The fixed 400 `EndTurn`s are no longer enough.** With about 22-byte
    deliveries, B's transport takes about 2,521 frames, and B's host log
    must also fill before `backpressured: 1`.
  - The amendment should size A's command count from B's measured delivery
    sizes: N_B, plus B's T022 egress capacity, plus A's 128 staged. It
    could also replace the literal 400 by a count the test computes and
    asserts, with the "1..=n, each once, in order" checks kept against that
    n.
  - The +100 ms per pump keeps the rate budget from refusing, whatever the
    count.
- **Case 14 `slow_consumer_fenced_after_stall_timeout`.** B is the same as
  in case 12, and the stall now starts after N_B frames. B is stalled by
  flow control and acknowledges what it received, so the server has about

  not apply, and `Peer { code: 9 }` stays the right expectation.

    - It adds a bind-time failure path.
    - It does nothing for a stalled peer, so it does not unblock T023b.

### C§12. Open questions (each with a recommendation)

1. **Six fields, three per endpoint, named `stream_window_bytes`,
   `connection_window_bytes` and `send_window_bytes`, typed `u32`.**
   T023b needs only the client's stream window. The send window is the
   only server-side knob on quinn's per-connection memory and on bytes in
   flight, which C§1.4 shows matters.
   *Recommendation:* approve all six. That keeps one rule (every quinn
   window is a limit) instead of a partial set.
2. **v1 defaults stay equal to today's values.** Nothing measured needs a
   different default. T023b's stall and case 17's exposure are both
   handled by opting in, and the Windows failure is not root-caused to the
   defaults themselves (C§1.4).
   *Recommendation:* approve with no default change. Revisit the server
   send window default (64 × 1 MiB) with T040's operator configuration or
   T024's snapshot measurements.
3. **Floors are one maximal frame plus its header (4,100 and 65,540).**
   The consequence is that a stalled client still takes 2,521 22-byte
   frames at the floor, so T023b's case 12 needs more commands (C§10). A
   lower client floor (for example 4,100) would stall within about 160
   small frames. The cost would be a `MAX_STREAM_DATA` every 512 bytes, at
   least 16 credit round trips per maximal delta, and limit values that
   cannot hold the frames their direction allows.
   *Recommendation:* keep the one-maximal-frame floors, and let T023b
   scale its counts.
4. **Connection window ≥ stream window, refused as `InvalidLimits`
   otherwise**, rather than one combined knob or silently clamping.
   *Recommendation:* approve. It mirrors "host-wide ≥ per-connection", and
   it keeps v1 exactly as T023 advertised it (a combined knob could not
   reproduce today's 2:1 ratios without a special rule).
5. **Case 17's Discard part runs on a server with `send_window_bytes =
   65_540`** (C§8.5). This is a configuration change, not an assertion
   change.
   - Evidence: in the slow-receiver model it took `Reset` from 33 of 34
     runs to 2 of 34, and it leaves the test's Linux shape identical (k =
     47, 16 discarded, no `QueueFull`).
   - The alternative is to tighten the client's windows. That gave 0 of 34
     in the model, but cuts the outbound headroom from about 16 frames to
     about 3, which risks a new `expect("send")` panic.
   - Neither option removes the quinn mechanism.

   *Recommendation:* approve the server send-window edit inside T023c,
   with four Windows runs as acceptance (C§8.7). Parts 1 and 3 stay on
   v1.
6. **If case 17 still shows `Reset` on Windows after T023c.** The
   mechanism is in quinn-proto (C§1.4), the newest release. The options
   are:
   - (a) report it upstream (a user action; the one-line evidence patch
     and the C§1.4 table are the report);
   - (b) a separate dependency task that carries the one-line quinn-proto
     fix through D23's prepared vendoring mechanism, with its own H-dep
     record, possibly folded into T026p's planned vendoring;
   - (c) an explicit expectation change that accepts `Reset` for that one
     Discard assertion, with the reason in a comment;
   - (d) UDP buffer sizing (C§11).

   *Recommendation:* do (a) now, whatever happens. If the failure
   persists, prefer (b) over (c), because (b) fixes production behaviour
   too: a fenced client should learn its code. Use (c) only as a stopgap
   the user approves explicitly while (b) is pending. Do not use (d).
7. **Case 4 stays byte-identical, and the window fields are covered by the
   new case 24** rather than by extending case 4's "every policy field"
   lists. Extending would not weaken case 4, but leaving it untouched
   keeps T023's evidence exactly as merged.
   *Recommendation:* approve the new case. Case 4's comment then reads as
   T023's field set, which the completion record notes.
