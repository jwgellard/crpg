# T016 — Minimal-d6 and headless combat

## Status and purpose

**Specified at milestone level; prerequisite decisions and per-crate executable
contracts pending. Implementation and verification are not claimed.**

Deliver the first end-to-end proof that authored ruleset data drives combat:
load `rulesets/minimal-d6`, instantiate the two-creature campaign
`campaigns/fixtures/combat_basic`, play its recorded inputs headlessly, verify
every tick against the native target's golden, and prove that exactly one
creature is dead at the end.

This is the T16 abstraction gate in `docs/CRPG_ENGINE_SPEC.md` §24, not a
script that applies predetermined damage or despawns the designated loser.
Resolution must go through the T014/T015 rules kernel; combat state and
mutations must belong to the authoritative simulation.

## Prerequisites to resolve before opening implementation

1. **Authored format.** The current data surface has no typed ruleset or
   combat-ability document. Creature stats are symbolic `Fx16_16` values,
   whereas T015 resolution requires integer DCs and supports dice-valued stats.
   T016a must specify schema/version/migration policy, package placement,
   references, and checked conversions. Do not invent a private JSON decoder
   in sim, stash executable behavior in `_note`, or silently truncate fixed
   values into integers. Existing data fixtures must retain their meaning.
2. **Dependency approval.** Sim currently depends on core, not data or rules.
   The lint's allowed edges are architectural permissions, not approval to add
   dependencies. Request approval for the exact existing-workspace path edges
   needed by T016b and any additional T016c edges, together with narrowly scoped
   manifest/lockfile changes. No external package is expected.
3. **Public API and state representation.** The sim contract requires an ADR
   for public API changes. Before T016b, record the combat API, issuing
   interner ownership, symbolic persistence, hash representation, turn policy,
   event ownership, and compatibility strategy in a new reviewed ADR. Preserve
   prior ADRs and attribution history. An unreviewed task sketch is not an ADR.
4. **Replay initialization and dispatch.** Testkit constructs `World::new(seed)`
   and accepts an opaque caller-owned `ApplyInput`; the CLI currently supplies
   only reference intents. Specify how validated campaign content reaches that
   world, how combat versus legacy payloads are selected without ambiguity,
   and how initialization is included in hashed state. Replay metadata is
   recorded, not enforced; do not quietly make `campaign_id` a filesystem path.
   Any changed testkit public API requires its contract's ADR process too.
5. **Baseline compatibility.** Adding combat state to World may change skeleton
   serialization and every old hash. Decide compatibility before coding.
   Preserve old behavior and goldens where possible; if a hash-format change
   is necessary, obtain a separately scoped reviewed re-baseline. Never make
   old tests pass by omitting behavior-affecting combat fields from hashing.

T016a's executable task must settle the authored wire contract first. T016b's
task then pins concrete runtime signatures against it; T016c/T016d pin replay
and CLI shapes against the landed sim surface. Do not substitute guessed
signatures for an unresolved prerequisite.

## Required ruleset behavior

The following requirements bind the child specifications:

- Exactly three named attributes, plus a separately declared health stat.
  Names, identities, initial values, and which attribute an ability checks
  are authored data. There are no levels, armor class, or derived system
  assumptions in the minimal ruleset.
- One targeted attack ability: roll `2d6`, succeed when the total is **less
  than or equal to** the actor's selected attribute, and apply a positive flat
  integer damage amount authored on that ability. A failure applies no damage.
- Use T015's existing margin `roll_total - against_value`. For inclusive
  roll-under, author two bands: lower bound `i64::MIN` maps to `Success`,
  lower bound `1` maps to `Failure`. There are no natural-face rules. Do not
  reverse the kernel subtraction or special-case six-sided dice.
- The ability data maps the outcome to the damage operation. Engine code may
  implement generic operations, but must not give an outcome label an implicit
  damage rule or contain this ruleset's identifiers, attribute names, die
  count, thresholds, or damage values.
- One action per turn, represented by authored capacity/cost and turn-start
  refresh using the existing resource model. No additional action categories
  are exposed by minimal-d6. A failed attack still consumes its action;
  malformed or rejected actions consume neither resources nor randomness.
- No AI, movement/range system, effect interpreter, arbitrary expression
  language, rest system, networking, editor, or general script dispatcher is
  required to prove this fight. Replay inputs choose actors and targets;
  they do not choose roll results, damage results, or the winner.

The named attributes, numeric fixture values, seed, and exact expected trace
must be fixed in the child contracts/artifacts before golden authoring. Use
values that exercise both successful and failed attacks in the chosen replay.
Do not claim that arbitrary stochastic fights always terminate.

## Authoritative simulation contract

T016b must specify and test all of these behaviors:

1. Instantiate both creatures from validated authored records, retaining a
   deterministic mapping from authored placement identities to runtime IDs.
   Resolve symbols through one documented issuing interner. Reject unresolved
   references, incompatible stat types, invalid costs, and out-of-range values
   before publishing a partially initialized encounter.
2. Own all behavior-affecting state in World: stats, modifiers used by the
   encounter, resource balances, alive/dead state, active turn, remaining turn
   order/round state, content identity, and RNG. A closure-local mutable copy
   of health or turn state would escape `state_hash` and is forbidden.
3. Keep Timeline a container. Specify a combat controller over its ascending
   `(InitiativeKey, EntityId)` ordering, with deterministic tie breaks, one
   entry per participant, repeatable rounds, and dead-participant removal.
   Retain existing `end_turn` pop-only semantics; use a separate combat
   operation for action completion and round progression.
4. Refresh the incoming actor once at turn start. An accepted attack consumes
   the single action and advances the turn after resolution/damage/death
   processing. Pin initial turn, round rollover, event ordering, and terminal
   encounter behavior in the runtime task. Ordinary no-input ticks must not
   invent actions or extra resource refreshes.
5. Reject absent/dead actors and targets, out-of-turn actions, unknown or
   unavailable abilities, self-targeting for this ability, and unaffordable
   costs. Pin multifault precedence. A rejected operation leaves the entire
   World, event sequence, resources, and owning RNG unchanged.
6. Call T015 `resolve` using World's deterministic named streams and apply its
   successful result transactionally with cost, damage, and turn changes.
   Flat damage is nonnegative, uses checked/widened integer arithmetic, and
   floors health at zero. Zero damage is a valid generic operation.
7. A transition from positive health to zero emits death once and removes
   the participant from combat scheduling. Death is distinct from arena
   despawn: retain the entity and its zero-health state for the terminal
   assertion. Subsequent rejected actions cannot emit duplicate death.
8. Use core-closed hook payloads and deterministic correlation identities.
   Specify producers and actual consumers for any new event. Do not derive
   serde on interned handles or nest rules objects into kernel hooks. T015's
   hook vocabulary alone does not imply an existing hook dispatcher.
9. Hash all state that can affect subsequent behavior, including queued
   events, RNG streams, resource balances, pending turns, and referenced
   immutable combat definitions or their validated identity. Save/load uses
   symbolic forms, validates liveness and references, and preserves future
   behavior across different interning orders. No filesystem or OS logic in
   sim, rules, or core.

## Content and replay delivery

T016a must produce a real ruleset package under `rulesets/minimal-d6/` and a
valid campaign under `campaigns/fixtures/combat_basic/`, with stable authored
ULIDs, valid references, locale data where required, and reviewed locks.
Loading must use the production data path. The content task must explicitly
extend any fixture inventories its new campaign participates in; it must not
silently invalidate T011a/T011b's exact-root checks.

T016c provides `combat_basic.replay`, using the existing replay envelope and
input → tick → hash ordering. Initialization must be a defined part of playback,
not an unrecorded warm-up tick. The replay runs a bounded fixed number of ticks
and includes trailing ticks after the terminal action. All gameplay commands
go through the same public sim operations used by future authoritative hosts.
Caller adapters may decode and bind inputs; they may not implement combat.

The generic replay harness must remain payload-agnostic. Cross-layer tests
live in testkit, never through a sim/rules/data dev-dependency on testkit.
Use existing replay and golden machinery; do not build a second playback loop.
T016c must define how tests inspect terminal state using public operations
while independently verifying the full sequence, without adding a private
World access path or changing the interleaving.

T016d retains verify-only CLI behavior and exit codes: 0 on exact verification,
1 on domain/I/O/divergence failure, 2 on usage. Its child task must publish the
exact campaign/ruleset selection syntax and compatibility handling for old
reference replays. There is no path-name special case for `combat_basic` and
no CLI-owned resolver, damage formula, turn loop, or rebless mode.

The spec's shorthand `crpgc replay combat_basic.replay` means the ordinary
verify path with a sibling `.golden`. For checked-in target-scoped artifacts,
acceptance supplies `--golden` explicitly; a black-box test may install the
correct compile-time-selected golden beside a private replay copy to test the
default. Never use runtime OS detection to choose a checked-in baseline.

## Required acceptance coverage

- Production load/validation and canonical round trip of the ruleset and
  campaign; malformed/unknown/duplicate references, integer conversion
  boundaries, and every new limit at largest-valid/first-invalid values.
- Independently expected roll-under results at attribute minus one, equal,
  and plus one; trace-based damage and resource assertions. Pin expected faces
  and both success/failure cases for the authored replay seed.
- Two-creature turn sequence, initiative ties, round refresh, rejected second
  action, dead-target/out-of-turn errors, terminal scheduling, and exactly one
  death notification. Zero and overkill damage cannot wrap health.
- Full-world rollback for representative invalid inputs, including no new
  RNG stream and unchanged event sequence; despawn cleans up new stores and
  turn references without weakening the existing no-dangling tests.
- Save/load midway through combat, then replay the same remaining inputs:
  identical subsequent behavior and native hash sequence. Different interner
  insertion order preserves symbol meaning.
- Same seed/content/inputs repeats every hash. Mutating an attack input or
  authored damage/threshold changes the independently expected behavior;
  mutating health, resources, turn state, or pending events changes the hash.
- Exactly one retained creature has zero health and dead status; the other
  has positive health and alive status. Hash equality alone is insufficient.
  Trailing ticks perform no further attacks, damage, or death notifications.
- CLI black-box success, default and explicit goldens, malformed inputs,
  missing files, unknown abilities, and exact-tick divergence. Existing replay
  and CLI regression suites keep passing without weakened assertions.
- Review the complete `crpg-rules` and `crpg-sim` diff for ruleset-specific
  knowledge. Names and numeric policy belong in content; neutral kernel/sim
  tests may exercise generic numeric cases. T017 must be able to change the
  ruleset without encountering a branch for this package.
