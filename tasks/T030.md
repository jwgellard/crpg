## Patch contract

Audit all packet-window operations in the selected source, including:

- insertion/duplicate detection, highest packet storage and eviction;
- width-dependent shifts/masks and shift-by-word/full-window boundaries;
- missing packet queries, lower/upper ranges, largest missing, iteration;
- ACK/loss consumers that interpret the window and exhaustion arithmetic;
- all constants/assumptions tied to u128, 128 or effective window 129.

Target a 2048-history-bit representation with highest packet stored separately
(effective span 2049 if the selected representation retains that design). A
different effective span requires an explicitly explained correction, not a
claimed 2048-bit patch consisting of a typedef change. Keep the patch minimal:
no congestion-control, ACK-frequency or #2711 policy change without separate
evidence/decision. Preserve upstream public API and native support.

Produce a clean patch against the verified original, with file hashes before
and after and exact application/reversal commands. Use checksum-pinned local
vendoring as the **proposed** later integration mechanism, never an unknown git
source. Include notices and upstream licenses; do not add a vendor directory
to the product tree yet.

## Required independent tests and measurements

Create an independent ordered-set reference model in the isolated test harness.
Assert implementation results against it, not against a copy of the same mask
arithmetic. Explicit cases: empty/first packet, identical duplicate, in-window
reordering, ages 127/128/129 and 2047/2048/2049, advancement by 0/1/word/window/
window+1, packet-number range limits, wholly missing/partially missing/full
ranges, disjoint holes, duplicates after eviction and all missing-packet queries.
Use fixed-seed reproducible generated schedules as additional coverage.

Run the same reproduction against **unpatched and patched** source, retaining
the expected failing assertion/output for the old window and a clean positive
control for both. If the original defect does not reproduce, report that result;
do not forge an old failure or claim a fix from patch-side success alone.

On genuine Windows/MSVC and Linux/GNU with the pinned toolchain:

1. Upstream affected-crate unit suites plus the patch regression harness.
2. Real UDP/QUIC loopback through an injected impairment harness: 150 ms RTT,
   ±15 ms jitter and 3% scheduled loss; zero-loss reorder control; no-impairment
   positive control; raw UDP path control through the same impairment schedule.
3. Record injected versus observed packet loss, duplicate/reorder counts and
   application progress; distinguish kernel/socket drops from window accounting.
   Specify send rate, duration, seed, payload size and packet-space population
   in the report before interpreting throughput. No unmeasured latency promise.
4. Measure size/allocation delta per packet space and connection (state whether
   values are layout counts or runtime allocations); include population/scaling
   formula. Do not quote issue-reported bytes as a project measurement.

The report must give literal commands and exact harness source for reproduction,
not “run upstream tests”. Deterministic unit oracles must not depend on sleeps;
real network timing measurements are observations with provenance and timeouts,
not deterministic replay goldens. Keep #2711 a separate interpretation caveat.

Record approval as `pending` until an explicit approval is actually received.
