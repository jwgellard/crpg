## What the ADR decides (one line each; item numbers are the ADR's)

1. **Personas (P):** module authors first, agents equal, the user's game
   after; every capability is an operation first and the GUI emits the same
   operations; agents screen designs but never prove human usability.
2. **Vocabulary (V):** the GUI never shows ids, paths, pointers, raw fixed
   point, locale keys or Godot terms; a fixed table maps data terms to author
   terms.
3. **Layout (I):** spec §11.4's window; explorer grouped by what authors
   make; generated forms with pickers, decimals and text; Problems with a Fix
   button; Apply plan… for agent work in an open editor; Play never forces a
   save.
4. **Intent layer (C, T103):** thirteen operations in `crpg-edit` (`create`,
   `delete`, `rename`, `set`, `add`, `remove`, `text`, `place`, `move`,
   `start`, `connect`, `on`, `import`) compiled purely to `EditCommand`s and
   applied as one batch; references by `@handle`, `kind:slug` or ULID;
   scaffold recipes; decimal author units via `Fx16_16::from_str`; closed
   error codes with hints.
5. **Wire (W, T059):** `crpg.plan/1` and `crpgc apply <root> <plan> [--dry-run]
   [--json]`, all-or-nothing writes, ids from host entropy, `crpgc help`
   with tested examples, `crpgc schema` for all 23 stems.
6. **Creation (K):** no blank campaigns — `crpgc new campaign --template`
   (`starter-d6`, `starter-srd`); new rules from a template are an
   independent copy; per-campaign overrides stay the spec's diff (T110).
7. **Events (E, unblocks T053):** event pages "When X … if … do …" stored as
   valid `EventGraph`s; six requirements on T053's IR; typed conditions in
   dialogue and quests (T054); the MVP quest completes by a page.
8. **Assets (A):** one import flow (GUI and `import` op); Godot-free checks
   over bytes in `crpg-data`; a new `RecordAsset` command keeps both locks in
   step as one undo step; no 16-character name limit.
9. **Data prerequisites (D, S-set):** schema annotations (fixed point, locale
   key, reference kind), a prop kind, an appearance reference; terrain stroke
   limits for T063.
10. **Flows (F1–F17):** one per §17.2 item plus new campaign, new rules from
    a template, per-campaign override, asset import and agent plans.
11. **Measurement (M):** fix the T100 scorer, re-score the stored logs, then
    T103 + T059 pass only if no cell is worse, ≥ 48/50 valid and playable
    (≥ 9/10 per brief), ≤ 1 timeout, ≤ 70% of baseline mean steps on the
    four from-nothing briefs, ≤ 50% failed `crpgc` calls, and a held-out
    sixth brief.
12. **Human method and criteria (H, U):** five-tester think-aloud rounds
    (4/5 without help), walkthroughs, heuristic screens; numbered criteria for
    T102, T103, T059, templates, D1, T060–T068, Apply plan…, asset import,
    T053/T054 and T110.

## Questions for the user

Each has a recommendation; the contracts proceed on it unless the user
answers otherwise. The manager files them as the next D-number.

**Q1 — Are props their own kind?** *What:* a prop is scenery you place: a
barrel, a tree, a cart. Today the engine can place only creatures and items,
and nothing in the data says what a thing looks like. *Why it matters:*
§17.2 item 1 asks for "a few placed props". *(a)* A new "Prop" kind with its
own list in the explorer: clear for authors, one more schema kind. *(b)*
Props are items marked as scenery: no new kind, but scenery would show among
pick-up-able things and in item lists. **Recommend (a).**

**Q2 — Is "new rules from a template" a copy or a live child?** *What:* when
an author starts their own rules from `minimal-d6`, either they get an
independent copy, or their rules keep pointing at `minimal-d6` and inherit
its later changes. *Why it matters:* a module built on a live child can
change under the author when the template is updated; a copy cannot, but
does not get fixes. *(a)* Copy, with the origin remembered so the editor can
show "what you changed": predictable, simple. *(b)* Live child: smaller
files, fixes flow down, but modules can break silently and the engine has no
inheritance today. **Recommend (a).** (Changing one ruleset for one campaign
stays a stored difference either way, as the spec says.)

**Q3 — What happens when you delete something that is still used?**
*What:* for example deleting a creature that a fight and a dialogue use.
*(a)* Refuse and list the users, with a one-click "remove it from those too"
that is a single undo step. *(b)* Delete and leave broken references for
the Problems panel. *(c)* Always remove it from the users silently. *Why it
matters:* (b) and (c) break content without the author seeing it first.
**Recommend (a)** (the spec's "offers to fix or block").

**Q4 — Spend Go quota on a sixth, held-out benchmark brief?** *What:* a
story brief (an NPC, a dialogue that starts a quest, an event that completes
it), kept out of the help text so the new commands are not tuned to the five
known briefs. *Why it matters:* without it, a good score could come from
tailoring to the test. It costs 10 baseline runs now plus 10 in each later
comparison (about 1–2 hours of Go time each at `--par 2`). *(a)* Yes.
*(b)* No: compare on the five briefs only. **Recommend (a).**

**Q5 — Does the MVP's quest complete by an authored event or a built-in
hook?** *What:* "the quest completes when the goblin dies" can be an event
the author writes in the editor ("When Goblin dies → set quest to
Completed"), or a special case coded into the engine. The spec allows
either for the MVP. *Why it matters:* the authored event is what every real
module needs, and proving it in the MVP tests the event path early; it
requires T053's interpreter to handle that one page before M6 ends. The hook
is quicker but is thrown away. *(a)* Authored event. *(b)* Built-in hook.
**Recommend (a).**
