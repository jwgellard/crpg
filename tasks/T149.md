## Task
ADR-0036 X1–X3 (`:466–477`), measured through S2 (`:317–325`):

- **X1.** An ability may declare `range: Fx16_16`; absent means unlimited,
  so existing data is unchanged.
- **X2.** `validate_action` rejects a `UseAbility` whose target is farther
  than the ability's range, measured by `route_measure(measure, [actor
  position, target position])`; either side without a mover is
  `OutOfRange`; `legal_actions` omits out-of-range targets.
- **X3.** In RT, a due order whose target is out of range neither executes
  nor ends; it stays due (amends ADR-0029 T7 for this case only).

**T149a** adds the optional field, its read-time rule, one authoring warning
and the regenerated ability schema. **T149b** copies the field into the
persisted ability definition, adds `CombatError::OutOfRange`, the last
admission stage of `validate_action`, a pure `within_range` export, and the
X3 branch in stage 3.

## Readings of the ADR
Each needs the user's approval with the contract.
1. **Two parts, data then sim** (the ADR's table, `:543`; one task = one
   crate). T149b waits for T036c because the measure lives on
   `CombatDefinition.movement` (S2 `:319–320`), which T036c adds.
2. **`range` joins `crpg.ability/2` with no version bump** (D32c, as T148
   Reading 1). It is optional-missing, absence is exactly today's
   behaviour, and every existing document decodes to the same value with
   unchanged canonical bytes.
3. **The wire is the raw `i32`** (`Fx16_16` is transparent serde,
   `crates/crpg-core/src/fixed.rs:22–36`), a constant only. X1 names
   `Fx16_16`, not T148's constant-or-stat `LengthWire`.
4. **Authored range must be positive** (raw `>= 1`), a read-time
   `Malformed` rule, matching T148's positive step. Zero would admit only
   coincident targets; it is far more likely a mistake. There is no upper
   bound: any raw above the coordinate box's diagonal (`1518500250`) is
   unlimited in effect.
5. **Sim semantics are total and need no new error at start or load.** A
   range copied into sim from a document that bypassed read-time checks
   (a test literal, a hand-edited save) still has one meaning: raw `0`
   admits only measured `0`, and a negative raw admits nothing. The
   comparison is `measured <= raw` with a negative raw never satisfied.
6. **The range stage is the last stage of `validate_action`**, after
   derived-stat evaluation (`crates/crpg-sim/src/combat.rs:3497–3500`). X2's
   "after target liveness" is the earliest legal point; last keeps every
   existing precedence, including the pinned ladders in
   `crates/crpg-sim/tests/legal_actions.rs:337` and
   `crates/crpg-sim/tests/rt_orders.rs`. Consequence: an out-of-range target
   for an unaffordable ability reports `InsufficientAction`, and in RT such
   an order ends rather than waits (Reading 9).
7. **The measure** is `definition.movement`'s `measure`, or
   `Measure::Euclidean` when `movement` is `None` (only reachable from a
   hand-edited save, since a ruleset without `movement` creates no movers).
   Positions are `Mover::position()`, never the `f32` mirror (U2).
8. **The range applies whatever `requires_target` says.** Every
   `UseAbility` names a live combatant target
   (`crates/crpg-sim/src/combat.rs:3548–3550`). A self-target measures `0`.
9. **X3 retains exactly `Err(CombatError::OutOfRange)`.** Every other
   failure still clears the order and reports `OrderEnded`
   (`crates/crpg-sim/src/combat.rs:4410–4417`). A retained order keeps its
   timeline key (already `<= elapsed`), so it is due again on every later
   tick, at most once per tick (the due set is taken once,
   `:4386–4391`). Nothing is spent, re-keyed, journaled or drawn.
10. **An out-of-range RT order is refused when issued** (Question 2). The RT
    `perform_action` path runs `validate_action` before storing an order
    (`crates/crpg-sim/src/combat.rs:3648`, `:3679–3694`), so X2 applies at
    issue time; X3 covers only an order that was in range when accepted.
11. **`OutOfRange` is fieldless** (as `SelfTarget`); its `Display` follows
    `<Code> at <location>` (`crates/crpg-sim/src/combat.rs:956–960`) with the
    location `combat/target`.
12. **A pure `within_range` export** holds the comparison, so the client's
    range preview (G3) computes exactly the server's answer (A5, `:83–86`).
13. **One authoring warning** (Question 3): an ability with a range listed
    by a ruleset that has no `movement` can never be used (X2: no movers),
    so `walk_combat` warns, in the style of
    `real_time_fields_without_round_ticks`
    (`crates/crpg-data/src/validation.rs:738–757`). It never fails
    validation.

## Behaviour

### T149a: data (X1)
1. **B-A1 (read and write).** A document without `range` decodes to
   `range: None` and writes byte-identically. `"range": 98304` decodes to
   `Some(Fx16_16::from_raw(98304))` and `write_document` writes
   `"range": 98304` in canonical key order (after `outcome_table`, before
   `requires_target`). `"range": null` decodes to `None` and is not written.
   The tag stays `crpg.ability/2`; no migration edge is added.
2. **B-A2 (structure).** A `range` that is not a JSON integer within `i32`
   (a string, `1.5`, `2147483648`, `-2147483649`) is `Malformed` (serde's
   text, not pinned).
3. **B-A3 (read-time rule).** A `range` with raw `< 1` fails exactly
   `ability range must be positive`. It is the last check of the `Ability`
   arm, so any earlier failure wins.
4. **B-A4 (warning).** In `walk_combat`'s per-ability loop, directly after
   the real-time warning (`crates/crpg-data/src/validation.rs:738–757`) and
   before the cost checks (`:758`): when `ability.range.is_some()` and
   `ruleset.movement.is_none()`, `push_warning` at the ability's file,
   pointer `/range`, code `RangeWithoutMovement`, message
   `ability {ability_id} declares a range but ruleset {ruleset.id} has no movement`
   (both ULIDs by `Display`), fix
   `add movement to the ruleset or remove the range`. No other finding
   changes.
5. **B-A5 (schema).** `generated_schemas()["ability.schema.json"]` gains the
   optional `range` property (not in `required`) with the doc comment as its
   `description`; the checked-in file equals it; no other schema changes.
6. **B-A6.** No sim code, inventory site, migration, fixture or shipped
   document changes.

### T149b: persistence
7. **B-S1.** `AbilityDefinition.range` is written only when `Some`. A world
   whose abilities all have `range: None` serializes exactly as before. A
   ranged ability makes the definition non-legacy, so it is written with the
   `abilities` vector and survives a save and reload.

### T149b: X2 admission
8. **B-S2 (`within_range`).** Exactly the formula in Interface, with T036's
   `route_measure` (`tasks/T036.md:449–453`): `y` never counts, the root
   rounds up, and a point outside `COORD_LIMIT_RAW` gives `false`.
9. **B-S3 (range stage).** For `UseAbility { actor, ability, target }`,
   after every existing stage has passed: `entry.range == None` is `Ok`.
   Otherwise, with `measure = definition.movement.map_or(Measure::Euclidean,
   |m| m.measure)`: if `world.movers().get(actor)` or
   `world.movers().get(target)` is `None`, or
   `!within_range(measure, range, actor_mover.position(),
   target_mover.position())`, the result is `Err(OutOfRange)`; else `Ok`.
   The stage reads no `f32`, interns nothing, draws nothing and changes
   nothing (`crates/crpg-sim/src/combat.rs:3322–3324`).
10. **B-S4 (callers).** `legal_actions` lists exactly the candidates
    `validate_action` accepts, so out-of-range targets are omitted and the
    closing action is unchanged. `perform_action` and
    `HistoryWorld::perform_action` reject an out-of-range action with
    `OutOfRange` (`HistoryError::Combat(OutOfRange)`) and change nothing, in
    both modes; an RT order is therefore never stored for an out-of-range
    target (Reading 10).

### T149b: X3 stage 3
11. **B-S5.** In `execution_stage` (`crates/crpg-sim/src/combat.rs:4410`),
    `validate_action(world, &action)` returning `Err(CombatError::OutOfRange)`
    is followed by `continue` with nothing else: the order stays, the
    timeline entry and key stay, no `TickEvent` is pushed, nothing is spent.
    Any other `Err` keeps today's branch (order cleared, `OrderEnded`).
    `Ok` keeps today's execution and re-key (`:4419–4458`).
12. **B-S6 (docs in code).** `validate_action`'s precedence doc
    (`:3311–3331`) ends with "then the range stage (`OutOfRange`, ADR-0036
    X2)"; `execution_stage`'s doc (`:4367–4374`) and `OrderEnded`'s doc
    (`crates/crpg-sim/src/history.rs:142`) say an `OutOfRange` failure stays
    due (ADR-0036 X3); `legal_actions`' doc notes the omission.

## Questions for the user
1. **Build range in two steps, data first, game rules second, and the second
   only after the turn-based move (T036c) lands?** Step one lets an ability
   file say "range 10 m"; step two makes the game enforce it. The rules step
   needs T036c because the encounter's way of measuring distance lives
   there. The rules step is a "serialized-state" change (saved fights store
   the range), so it gets the human review those always get. One step would
   cross two crates, which the project rules forbid. *Recommend: two steps.*
2. **In real time, refuse an attack order on a target that is already out of
   range?** The ADR says the admission check rejects out-of-range targets,
   and real-time orders go through that check when given. So clicking a
   far enemy is refused at once, while an order given in range that later
   falls out of range waits until the target is back in range (the ADR's
   X3). The alternative, accepting far orders and letting them wait,
   changes the admission check for RT only and makes "legal actions" list
   attacks that cannot happen yet. *Recommend: refuse (the ADR as written).*
3. **Warn authors about a ranged ability in a ruleset with no movement
   rules?** Without movement there are no positions, so the ADR makes every
   use of a ranged ability fail. A warning (never an error) in campaign
   validation points at the `range` field and says to add movement or remove
   the range. It costs one new diagnostic code, `range_without_movement`.
   Without it, the author only finds out in play. *Recommend: add it.*
4. **Approve eight one-line edits to existing data tests and one new row in
   a sim unit test?** Six test files build abilities field by field and must
   name the new field; two tests pin the exact list of ability schema
   properties and must list `range`; one table of "non-legacy" ability
   shapes gains the range row. Nothing they check is weakened.
   *Recommend: approve.*
