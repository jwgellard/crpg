## Task
Let a client receive protocol v3. Today the receiver stops at v2:
`ReassemblyPool` decodes only v1/v2 deltas and `0x81` transfers
(`crates/crpg-net/src/reassembly.rs:249–253`, `:602`, `:773`, `:905–908`), and
`ReplicaWorld` applies only `protocol_v2::DeltaFrame`s and `0x81` bodies
(`crates/crpg-net/src/replica.rs:16–17`, `:188`, `:220`). T140 defined the v3
wire, the `0x82` snapshot and the receiver sizing, but no receiver.

- **T140r1 — the v3 pool.** A new module `pool_v3` with
  `ReassemblyPoolV3`: T024's reassembly and cutover gate
  (`tasks/T024.md:694–884`, S§10) for one v3 session, built on
  `TransferAssemblyV3`, `TransferLimitsV3`, `transfer_v3::decode_down`/
  `decode_body` and `codec_v3::decode_delta`. It releases
  `PublicationV3`s (decoded `0x82` bodies) and decoded v3 `DeltaFrame`s in
  T024's FIFO cutover order.
- **T140r2 — the v3 replica.** A new module `replica_v3` with
  `ReplicaWorldV3`: T046's client replica (`tasks/T046.md:193–287`) for v3,
  applying every v3 op (tags 0..=20, `crates/crpg-net/src/protocol_v3.rs:753`)
  and `PublicationV3`s, and holding what v3 adds: each entity's fact set, the
  encounter, the timeline, the pause state and the host facts.

Neither part edits an existing module. v1, v2, `0x81`, `ReassemblyPool`,
`ReplicaWorld`, every T140 module and every existing test stay byte for byte.

## Readings
Design decisions this contract makes. Each needs the user's approval with
the contract (Question 1 covers 1 and 11).

1. **New types in new modules, not extensions of the v1/v2 receiver.**
   Rejected: a `DeltaWire::V3` arm with `GatedDelta::V3` and a widened
   `Publication`. Four reasons. (a) `GatedDelta` and `ReplicaUpdate` are
   matched exhaustively outside this crate
   (`crates/crpg-server/tests/host_transfer.rs:561–572`,
   `crates/crpg-server/tests/host_quic_transfer.rs:525–535`) and in a frozen
   suite (`crates/crpg-net/tests/reconnect_wire.rs:1509–1515`), so a new
   variant stops `crpg-server` compiling: a second crate and frozen-test
   edits. (b) `Publication.body` is the `0x81` `SnapshotBody`
   (`crates/crpg-net/src/reassembly.rs:276–282`); a v3 body there changes a
   public struct that `ReplicaWorld::apply_snapshot` and its tests build by
   literal. (c) One pool holds one limits value, and `TransferLimits` refuses
   every v3 size (T140 E-5, `crates/crpg-net/src/reassembly.rs:171–190`), so
   v3 receivers in a v1 pool would need two staging regimes. (d) T140 chose
   new modules every time (`codec_v3` duplicates `codec_v2`'s helpers,
   `TransferAssemblyV3` duplicates `TransferAssembly`). Also rejected: making
   `reassembly.rs` generic over the wire. It rewrites reviewed T024 code that
   T024's and T025a's suites pin, for no v1 gain. **Cost:** about 560 lines of gate
   logic exist twice. P-1's transliteration rule, the P8 mirror test and an
   `AGENTS.md` trap ("a fix to one pool is a fix to both") contain it.
2. **The pool reuses T024's vocabulary and adds a V3 type only where the v1
   type cannot serve.** Re-exported unchanged: `TransferOutcome`,
   `DeltaOutcome`, `TransferError`, `FailReason`, `GateMode`,
   `InFlightStatus`, `PublishedBase`, `Rebound`
   (`crates/crpg-net/src/reassembly.rs:255–417`), and `TransferLimitsV3`,
   `LimitsError`. New: `PublicationV3` (v3 body), `ReplicaUpdateV3` (v3
   delta), `ReceiverStatusV3` (no `wire` field, `:422`), and `ReceiverIdV3`.
   `ReceiverId`'s field is private to `reassembly` (`:290–291`), so another
   module cannot mint one; a separate id type also makes passing a v1
   receiver to a v3 pool a compile error.
3. **One wire per pool; no `DeltaWire`.** A `ReassemblyPoolV3` takes only
   `0x82` transfer frames and v3 delta frames. A v1/v2 session keeps
   `ReassemblyPool`. T141 picks per session.
4. **Sizing is T140e's, unchanged.** The pool takes `TransferLimitsV3`;
   `v3()` gives 8 receivers, 20,000 ms, 4,194,304 / 33,554,432 staging bytes,
   128 frames and 2,097,152 / 16,777,216 held-delta bytes
   (`tasks/T140.md:1097–1109`, E-4; confirmed by the user, `:1747–1749`).
   Nothing here re-sizes them; Question 2 raises one interaction for T141.
5. **The replica is a new type too.** `ReplicaWorld::apply_delta` takes
   `protocol_v2::DeltaFrame` (`crates/crpg-net/src/replica.rs:188`), the bridge
   calls it that way (`crates/crpg-godot/src/core/client.rs:322–329`), and
   `ReplicaEntity` is built by struct literal in the frozen suite
   (`crates/crpg-net/tests/replica.rs:65`, `:239`), so adding a `facts` field
   breaks it. `ReplicaWorldV3` copies `ReplicaWorld`'s state and rules and
   adds the v3 state.
6. **`ReplicaError` is reused unchanged.** Every v3 refusal is an existing
   kind: an op or body naming an id that is not live (or not in the body) is
   `UnknownEntity`. So the bridge's fatal-53 mapping (ADR-0033) needs no new
   case and the `Display` strings stay T046's.
7. **Every id a v3 op names must be live when the op applies (T046 D7
   extended).** This holds for legal pages because of T140c's emission
   order: the fact ops follow the whole interest page, enters and removals
   included (`crates/crpg-net/src/facts_v3.rs:204–205`), and every `NetId`
   in them is resolved against the ids live after that page (`:323–344`
   timeline, `:348–372` order target). History goes at `PageV3.enters`,
   after the enters and before the removals (`:192`, T140 H-4). So the
   checked ids are: `EntityFacts.entity`, its order's `target`, every
   `Timeline` entry's `entity`, `OrderEnded.actor`, `Joined.entity`,
   `Left.entity`, plus T046's.
8. **References are checked once, when the op applies; stored ones may go
   stale.** A later removal does not touch a stored order target, timeline
   entry or `turn.active` (T046 item 8 already allows this for `active`). The
   host re-sends the changed image after the removal in the same page, so the
   staleness lasts only until the end of that page.
9. **Facts are images.** `Encounter`, `Timeline` and `EntityFacts` each
   replace their subject's image whole; an all-withheld image is stored as
   such, which is "forget" (T140 Reading 4). The replica re-runs no codec
   value check (counts, `current ≤ max`, ordering, duplicates): those belong
   to the decoder (T140 B-1..B-3), as T046 stores health verbatim.
10. **Notices change no state.** `RoundStarted`, `ModeChanged`,
    `OrderEnded`, `Joined`, `Left` and `EncounterEnded` are checked for ids
    and then dropped (T046 D3, D12). The round lives in `Turn`, the mode in
    `Encounter` (T140 Readings 3, 4).
11. **`Clock` and `HostFacts` are host state, kept across a snapshot.** They
    are not in the `0x82` body (T140 Reading 14) and the host re-sends both
    after every publication (T140 H-2). So `apply_snapshot` leaves them as
    they are, and they are `None` until their first op.
12. **No new ADR.** ADR-0028 (transfer) and ADR-0035 (replica) apply
    unchanged to v3; the v3 vocabulary is ADR-0029 N1–N4's. The manager
    appends dated notes to both ADRs (Routing and size).
13. **Split: T140r1 (pool) before T140r2 (replica).** `apply_snapshot` takes
    `PublicationV3`, and R10 drives the pool end to end. Each part is one
    module, one implementer run.

## Behaviour
Normative. Each item names the tests that prove it. "Refused" means the stated
error and no state change. **First failure wins** in every list.

### T140r1: the v3 pool
P-1. **Transliteration rule.** `ReassemblyPoolV3`'s private types and every
method body are `crates/crpg-net/src/reassembly.rs:438–1105` with exactly
these substitutions and nothing else:

| In `reassembly.rs` | In `pool_v3.rs` |
|---|---|
| `TransferLimits` | `TransferLimitsV3` |
| `TransferAssembly` (type, `::new`, `accept`, `into_bytes`) | `TransferAssemblyV3` |
| `codec_transfer::decode_down` (`:602`) | `transfer_v3::decode_down` |
| `codec_transfer::decode_body` (`:773`) | `transfer_v3::decode_body` |
| the `match wire { V1 => …, V2 => … }` decode (`:905–909`) | `codec_v3::decode_delta(bytes)` |
| `GatedDelta` / `gated.event_seq()` | `protocol_v3::DeltaFrame` / `frame.event_seq` |
| `Publication`, `ReplicaUpdate`, `ReceiverId`, `ReceiverStatus` | `PublicationV3`, `ReplicaUpdateV3`, `ReceiverIdV3`, `ReceiverStatusV3` |
| `Receiver.wire`, the `wire` parameter of `add_receiver`, `ReceiverStatus.wire` | removed |

Check order, saturating arithmetic, the clamp-then-sweep prologue, the
`BTreeMap` iteration order, FIFO queue handling and every returned value stay
as they are. The stray working notes at `:852–855` and `:1011` are not
copied. P-2..P-14 restate the result so that the tests have numbered items;
where they and the transliteration disagree, stop and report it. *Tests:* P8,
and every P test.

P-2. **Construction.** `new(limits)` returns `limits.validate()`'s error
unchanged, else a pool with no receivers, `now_ms` 0 and both totals 0.
`limits()` returns a value equal to the one given. *Tests:* P1.

P-3. **Receivers** (`tasks/T024.md:704–709`). `add_receiver` is
`ReceiversFull` when `max_receivers` receivers exist or the `u32` counter is
at `u32::MAX`; otherwise the next id (`get()` 1, 2, 3, …, never reused, also
after a removal) with status `{ epoch, mode: start, in_flight: None,
retired_through: 0, published: None, next_event_seq: 1, held_frames: 0,
held_bytes: 0, queued_updates: 0, resync: None }`. `remove_receiver` frees
the receiver's staging reservation and its held and queued delta bytes; an
unknown id changes nothing. *Tests:* P1, P8.

P-4. **`offer_transfer` precedence** (S§10.2, `tasks/T024.md:711–722`):
(1) clamp `now_ms` up to the pool's last value and sweep (P-9); (2) unknown
receiver: `UnknownReceiver`; (3) `transfer_v3::decode_down(bytes)` error `e`:
`Codec(e)`, so a `0x81` frame is `Codec(UnsupportedVersion)`; (4) the
message's epoch ≠ the receiver's: `WrongEpoch`; (5) the message names the
transfer that this call's sweep expired for this receiver: `Failed(Expired)`;
(6) by message, P-5..P-7. *Tests:* P6, P8.

P-5. **Begin** (S§10.3): (1) same id as the in-flight transfer: identical
Begin `Ok(Duplicate)` with the deadline unchanged, any field different
`Failed(Conflict)`; (2) id ≤ `retired_through`: `StaleTransfer`; (3) another
transfer in flight: `InFlight`; (4) `cursor + 1 < next_event_seq`, or
`base_tick` below the published `base_tick`: `BehindReplica`; (5)
`total_bytes > staging_bytes_per_receiver`: `StagingFull`; (6) pool staging
+ `total_bytes > staging_bytes_total`: `AggregateFull`; (7) reserve
`total_bytes`, build `TransferAssemblyV3::new(&begin)` (its error, unreachable
after decode, is `Codec(e)`), set the deadline to
`now_ms.saturating_add(limits.deadline_ms)`, clear `resync`, return
`Ok(Begun)`. *Tests:* P3, P4, P8.

P-6. **Chunk:** for the in-flight id, `TransferAssemblyV3::accept`;
`WrongTransfer`, `OutOfRange`, `WrongLength` and `Conflict` become
`Failed(Conflict)`; `Duplicate` becomes `Ok(Duplicate)` (no deadline change);
`Stored` becomes `Ok(Stored { received, chunk_count })`; `Complete` runs
publication (P-10). Otherwise id ≤ `retired_through` is `StaleTransfer`, else
`UnknownTransfer`. Indexes 32..=127 behave as any other (the `u128` bitmap).
*Tests:* P2, P5, P8.

P-7. **Cancel `t`:** if a transfer with id ≤ `t` is in flight, discard it
(free its reservation), `retired_through = max(retired_through, t)`, mode
`AwaitSnapshot`, `resync` untouched, `Ok(Cancelled { discarded: true })`;
otherwise only the retirement and `Ok(Cancelled { discarded: false })`. A
queued snapshot is never withdrawn. *Tests:* P3, P8.

P-8. **Failure** (S§10.4): discard the in-flight transfer (if any) and free
its reservation; retire its id; mode `AwaitSnapshot` and
`resync = Some(reason.resync_reason())`; for `Overflow` also drop every held
(not queued) delta. Queued updates stay. *Tests:* P5, P8.

P-9. **Deadline** (S§10.5). Time is the caller's `now_ms`, clamped up, never
backwards. A transfer begun at `t` is live while `now < t + deadline_ms` and
expired from `now ≥ t + deadline_ms`; at `TransferLimitsV3::v3()` that is
live through `t + 19,999` and expired from `t + 20,000`. Every
`offer_transfer`, `offer_delta`, `poll` and `rebind_receiver` call first
sweeps every receiver in ascending id order and fails each overdue transfer
with `Expired` (P-8). `poll` returns the receivers this call expired,
ascending. The sweep is the only change a refused call can make.
*Tests:* P4, P8.

P-10. **Publication** (S§10.6), on the chunk that completes the assembly:
(1) `into_bytes`, then `transfer_v3::decode_body`; its error `e` is
`Failed(InvalidBody(e))`; `body.entities.len() != entity_count` is
`Failed(InvalidBody(Malformed))`; (2) free the reservation, retire the id,
clear the in-flight transfer; (3) if the queue holds a `Snapshot`, clear the
whole queue (and its delta bytes); (4) drop held deltas with
`event_seq ≤ cursor`; (5) `published = { transfer, base_tick, cursor }`,
`next_event_seq = cursor + 1` (saturating), mode `Live`, `resync = None`;
(6) push `ReplicaUpdateV3::Snapshot(PublicationV3 { transfer, base_tick,
cursor, body })`; (7) move held deltas from `next_event_seq` upward to the
queue while contiguous; (8) `Ok(Published { transfer, released })`, where
`released` counts step 7's moves. On a step-1 failure the receiver's state

## Questions for the user
1. **Approve building the v3 receiver as new, separate pieces, in two
   parts.** The "receiver" is the client-side code that puts a downloaded
   reconnect package back together and keeps the client's copy of the game
   up to date. Two ways to add v3: (a) **new pieces beside the old ones**
   (`ReassemblyPoolV3`, `ReplicaWorldV3`), leaving the v1/v2 code untouched.
   About 560 lines of the old download logic are copied with small, listed
   substitutions, and a test runs the old and new versions side by side to
   prove they behave the same. (b) **Extend the old pieces** with a v3 mode.
   That changes types that the server's tests and the Godot client use
   directly, so it would need edits in two other crates and to frozen tests,
   and it risks breaking the working v1/v2 path. *Recommend (a):* nothing
   that works today can break, and the copy is held to the original by the
   side-by-side test. The cost is that a future fix to the download logic
   must be made in both copies; a rule in the crate's agent notes says so.
   The parts are (1) the download gate, then (2) the client's copy of the
   game. Players see no change until the Godot client switches to v3 in a
   later task.
2. **Can a slow reconnect in a real-time fight keep failing? (A limit in the
   approved T140, raised here, not changed.)** While the client downloads a
   reconnect package (up to 2.85 MB, allowed up to 20 seconds), it holds
   the live updates that arrive meanwhile, up to 128 of them, as you
   confirmed in T140. The server ticks 20 times a second
   (`docs/CRPG_ENGINE_SPEC.md:318`). In a real-time fight the round clock
   changes every tick, so if the server sends an update every tick, 128
   updates arrive in 6.4 seconds. A player on a slow link (the 20-second
   budget assumes as little as about 200 KB/s, which takes about 14 seconds
   for the largest package) would overflow, the download would restart, and
   the next attempt would overflow the same way: they could never rejoin
   that fight. The server's own outgoing queue has the same 128-update
   limit, so the server hits this too. Options: (a) **make it a server rule
   for T141:** while a player's package is downloading, the server sends
   that player at most one update every few ticks (for example every 10
   ticks, 2 per second, about 40 in 20 seconds). Each update still carries
   the latest state, because the server only sends what changed since the
   last one. (b) **Raise the limit** to, for example, 512 updates. That
   reopens the approved T140 sizing and adds up to 4 MiB of memory per
   player on the client and the server. (c) **Leave it.** *Recommend (a):*
   it removes the failure at its source, costs no memory, and changes
   nothing in this task or in T140. A player who reconnects during a
   real-time fight sees the clock jump in larger steps for those seconds and
   then play continues normally.
