## Mechanism

The assertion at `host_quic.rs:2255` reads `closes` out of
`report.transport_closes` across exactly the steps
`pump_until` (`tests/support/quic_host_rig.rs:596-616`) returned before its
`UnbindPeer` predicate held. But `QuicPumpReport.transport_closes` is
documented as "`ServerEvent::Closed` events polled" (`src/quic.rs:99-100`)
and is populated in exactly one place — phase 1 of `run_phases`, when
`poll_event` yields `ServerEvent::Closed` (`src/quic.rs:486-496`). A close
can instead be *detected*, not polled, in phase 2: `drain_bound` calls
`server.try_recv(conn)` and on `ServerError::Closed(reason)` sets
`bound.transport_closed` and `bound.drained` directly (`src/quic.rs:737-742`)
without touching `report.transport_closes`. Phase 6 then retires any bound
connection with `transport_closed.is_some() && drained && held.is_none()` and
emits `HostCall::UnbindPeer` (`src/quic.rs:530-535`).

The two detection points race with the async I/O thread. In `crpg-net-quic`,
`try_recv` reports `Closed` only once the close is `published`
(`src/server.rs:332-338`), and `try_publish` sets `published = true` and
pushes the `Closed` event into the queue under the same mutex
(`src/queue.rs:410-428`) — so a close visible to `try_recv` has already
queued its event, but the host's phase 1 (`poll_event`) may already have run
for this pump. In the blackholed-relay case the server receives nothing after
the welcome, so the only path is `drain_bound` → `try_recv` →
`Closed(IdleTimeout)` (`reason_from` maps `ConnectionError::TimedOut` to
`IdleTimeout`, `src/queue.rs:77`).

Therefore, when the I/O thread publishes the close in the window between a
pump's phase 1 and its phase 2, that pump emits `UnbindPeer` (phase 6) with
`transport_closes` still empty; the `Closed { conn, IdleTimeout }` event is
polled and reported only in the *next* pump, after `pump_until` has already
returned. The collected `closes` is `[]` and the assertion fails exactly as
CI showed, even though the peer was correctly unbound by the idle-timeout
path and the close is not lost.

## Verdict

**Test-side.** The test assumes the `IdleTimeout` close is polled into
`transport_closes` in the same step as, or a step before, the `UnbindPeer`,
but the product does not promise that ordering: an unbind can be triggered by
the drain-phase `try_recv` close detection, with the `Closed` event reported
one pump later. The product correctly unbinds on idle timeout and reports the
close; nothing is lost.

## Recommended fix (not applied)

In part (c) (`host_quic.rs:2248-2250`), change the `pump_until` predicate
from `report.calls.contains(&HostCall::UnbindPeer { peer })` to
`report.transport_closes.contains(&(conn, CloseReason::IdleTimeout))`, then
assert `HostCall::UnbindPeer { peer }` is present in the returned steps (the
unbind happens no later than the poll of the close event). That waits on the
observable state the test actually cares about and is order-independent; it
changes no limit, close semantic, wire byte, public surface or other case.
