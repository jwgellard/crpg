## Task

D12 says a player whose connection drops keeps their session for 30 seconds
of host time and gets it back by proving who they are, with no double
execution and no combat reset. T025a built the mechanism (the `0x91` wire,
`SessionFence`, `rebind_receiver`) and T024q the transport
(`bind_resumable`, `poll_notice`, `accept_resume`). Nothing in `crpg-server`
uses them: `unbind_peer` discards a session at once
(`crates/crpg-server/src/host.rs:1290–1298`), the QUIC adapter unbinds a
closed peer (`crates/crpg-server/src/quic.rs:567–585`) and refuses a
resumable server by precondition (`:462–465`).

- **T025b-i — the host.** Proof storage and the ticket, the grace (start,
  frozen session, expiry on injected time), the resume decision with fencing
  and the resume snapshot, all on `Host`, provable in memory.
- **T025b-q — the QUIC route.** `QuicHost::start_resumable`: `poll_notice`,
  a ticket after each `/2` welcome, fence tags on every inbound frame, the
  resume answer, grace on a silent connection loss, and the invitation rules
  that end a grace.

## Readings

1. **A graced session leaves the live map.** `Host` gains a private
   `graces: BTreeMap<PeerHandle, Grace>`; every existing per-peer path reads
   `sessions` (`crates/crpg-server/src/host.rs:818`) and so sees a graced
   handle as unbound with no new branch. *Rejected:* a grace flag on
   `Session` (draft a): every path needs a branch, and a graced log would
   still count in `accepted_room` (`:2244–2270`), blocking every peer's
   admission.
2. **The grace starts with a new `begin_grace`; `unbind_peer` keeps
   discarding.** *Rejected:* changing `unbind_peer`: SeqConflict, narrowing,
   operator kicks, T154's link retirement (`tasks/T154.md:433`) and every
   existing suite rely on immediate discard.
3. **Resumable = a live snapshot session (`bind_snapshot_peer` or
   `bind_v3_peer`) holding a proof, and not v4.** A `bind_peer` session has
   no transfer channel, so no resume snapshot. A v4 session (T037b) is not
   resumable here: the resume v1 wire reports lane-0 progress only
   (`crates/crpg-net/src/protocol_resume.rs:303`), no transport carries a v4
   session yet (`tasks/T037.md:1351`), and its pending lane-1 slots would be
   decided 30 s late or dropped without a receipt, against T037 D-3/D-10
   (`:743`, `:792`). *Rejected:* draft b's "v4 rides opaquely".
4. **The proof is a caller fact to the host.** `issue_resume_ticket` takes a
   `ResumeProof`; the host stores it and builds the `Ticket`. The host has no
   entropy and no key (crate invariant 7, `crates/crpg-server/AGENTS.md:87`);
   the QUIC adapter derives the bytes (Question 1). *Rejected:* host-made
   proofs.
5. **One ticket per session, sent after the welcome; no rotation** (H7
   makes rotation optional). *Rejected:* rotating after `Accepted`: a client
   whose new connection dies before it reads the new ticket still presents a
   fence inside `[confirmed, current]` but an old proof, and would be denied
   a session it may resume.
6. **The grace clock is injected `now_ms`; expiry is a lazy sweep** at the
   head of `pump`, each `bind_*`, `begin_grace` and `resume_peer`
   (`< 30,000` resumes, `>= 30,000` expires, D12 `:294–295`). T154's loop
   runs a cycle every 50 ms (B-1, `tasks/T154.md:443–452`) and its intake
   pumps the host once per cycle (B-6, `:478`; B-14, `:608`), so expiry is
   checked every cycle in both hostings. *Rejected:* ticks (a paused host
   never ticks); `advance` (draft a; not every embedding advances while
   paused); a public sweep call (one more call to forget).
7. **The delivery log is discarded when the grace starts**, releasing its
   egress bytes; H5's resume snapshot replaces it anyway. *Rejected:*
   keeping it (draft b): up to 2 MiB of host egress held for 30 s per
   graced peer, then thrown away.
8. **The peer's staged commands are purged when the grace starts**, with no
   result and no sequence consumed; the client resends them after
   `Accepted` (T025a C4). *Rejected:* leaving them staged: `release_ingress`
   (`crates/crpg-server/src/host.rs:1535–1541`) skips a session it cannot
   find, so the retained session's ingress counters would never fall, and a
   resume before the pump would decrement them below the commands it never
   counted.
9. **A live session may be resumed too.** The QUIC idle timeout is 60 s
   (`crates/crpg-net-quic/src/limits.rs:27`), so a client that lost its
   network usually reconnects while the server still holds the old
   connection; `resolve` moves the fence and the old connection's frames fail
   `check_frame`. *Rejected:* resume from a grace only (that client would be
   denied and lose its session).
10. **`resume_peer` takes the decoded request and finds the session by
    epoch.** *Rejected:* a peer argument (draft b): the QUIC adapter learns
    only bytes, and the handle is the epoch's low half (`:1120–1126`).
11. **Refusals are `Denied` except one `Busy`.** After the proof and the
    fence check pass, a staging that has no egress room answers `Busy`
    (ADR-0032 item 7: "retained, retry"), changing nothing. It cannot occur
    at today's caps (seven other peers hold at most 7 × 2 MiB of the 16 MiB
    host cap, `crates/crpg-net/src/protocol.rs:141–143`, and a snapshot is a
    few frames), so it is named, not tested. *Rejected:* never `Busy` (both
    drafts).
12. **The fence lives in the host session; `Host::check_frame` is H2's
    call.** One `resume_peer` call authenticates, checks the fence, plans
    the snapshot, resolves and commits, or changes nothing. *Rejected:* an
    adapter-owned fence (a two-phase decision in which the fence can move
    while the staging fails).
13. **A graced session holds its `MAX_PEERS` slot** (`:96`); no separate
    cap (both drafts).
14. **`QuicHost::start` is unchanged; a new `start_resumable` turns the
    route on.** *Rejected:* changing `start`: every existing `/2` suite
    would gain a ticket frame and see `BeginGrace` where it pins
    `UnbindPeer`.
15. **Only a silent loss starts a grace over QUIC:** a close reason of
    `IdleTimeout`, `Transport` or `Reset`. A peer's own close (a client
    that quits; `QuicClient`'s `Drop` closes `Normal`,
    `crates/crpg-net-quic/src/client.rs:528`), a local close and
    `EndpointFailed` unbind as today. *Rejected:* a grace on every close
    (a quitting player holds a seat for 30 s).
16. **Operator changes and a new hello end a grace.** Revoking the
    invitation, changing its grants or control, or a new hello with it
    unbinds the graced session (D12's "fresh grant/revocation checks").
    This also meets H3's "invitation still registered": a revoked
    invitation has no session left to resume. *Rejected:* applying grants to
    a graced session (new host paths for a frozen session).
17. **The trace stays complete.** Every host call a resumable pump makes is
    a `HostCall` (`crates/crpg-server/src/quic.rs:17–19`). The two existing
    exhaustive replays (`crates/crpg-server/tests/host_quic.rs:713`,
    `crates/crpg-server/tests/host_quic_transfer.rs:1501`) gain one arm that
    fails on the new variants, which `start` never produces. *Rejected:*
    untraced resume calls.
18. **T154.** `LocalHost` keeps retiring a departed link with `unbind_peer`
    (`tasks/T154.md:433`, `:512`): an in-process link cannot lose a network,
    and the `0x91` route exists only over QUIC `/2` (ADR-0032 item 2,
    `docs/adr/0032-resume-subprotocol-and-connection-fencing.md:23`);
    `LocalHost::attach` refuses a graced handle (its `epoch` is
    `UnknownPeer`). `QuicHosting` (T154d) wraps whichever `QuicHost` it is
    given, so a resumable adapter brings the grace to the dedicated loop
    with no `run.rs` change. T025b-q and T154d both edit `quic.rs`
    (`tasks/T154.md:614`): whichever lands second carries the other's edits,
    and phases 4 and 6 below sit in `flush`'s body if T154d is first.
19. **An accepted resume whose connection is lost before the answer is a
    new disconnect.** The adapter binds it as closed and phase 6 decides
    (Reading 15). D12's "attempts do not extend the deadline" is about
    refused attempts; an `Accepted` ended the earlier grace.

## Behaviour
Normative. Each item names the tests that prove it. **First failure wins**
in every ordered list. "Refused" means the stated result and no state
change except, where an item says so, the recorded `now_ms` and the sweep.

### T025b-i — the host
G-1. **Fence (H1, H2).** Every `bind_*` gives the session
`SessionFence::new(epoch)`, kept for the session's life and never
re-created. `check_frame(peer, tag)`: (1) closed → `Closed`; (2) no live
session (a graced handle included) → `UnknownPeer`; (3) the session fence's
`check_frame(tag)` errs (`Fenced` or `UnknownFence`,
`crates/crpg-net/src/resume.rs:127–135`) → `SessionFenced`, nothing changes;
(4) `Ok(())`, `tag` confirmed. Every session kind has a fence; only a resume
moves it. *Tests:* G6, G7, G13.

G-2. **Ticket (H7).** `issue_resume_ticket(peer, proof)`: (1) `Closed`;
(2) no live session → `UnknownPeer`; (3) not resumable (Reading 3) →
`NotResumable`; (4) store `proof`, replacing any earlier one, and return
`codec_resume::encode_down(&ResumeDown::Ticket(ResumeTicket { epoch, proof
}))` (an encode error is `Invariant("resume ticket failed to encode")`).
The proof is never in a checkpoint, save, error, report or trace;
`Session`'s `Debug` shows it as `ResumeProof(<redacted>)`
(`crates/crpg-net/src/protocol_resume.rs:131–135`). *Tests:* G1.

G-3. **Grace start.** `begin_grace(peer, now_ms)`: (1) `Closed`; (2)
`now_ms` below the last accepted → `TimeRegression`, nothing changes; (3)
record `now_ms`, sweep (G-5); (4) no live session → `UnknownPeer`; (5) not
resumable, or no proof stored → `NotResumable`; (6) commit: remove every
staged command of `peer` from the ingress queue, in place, releasing the
host and session ingress counters, with no result and no sequence consumed
(Reading 8); discard the delivery log exactly as `stage_snapshot`'s commit
does (`egress_bytes -= log_bytes`, log cleared, `delivered = next_ordinal −
1`, `crates/crpg-server/src/host.rs:2391–2394`); move the session to
`graces` with `deadline_ms = now_ms.saturating_add(POLICY_RECONNECT_GRACE_MS)`;
return `Ok(deadline_ms)`. Nothing else in the session changes: epoch,
fence, proof, control, grants, map, `next_net`, `next_new_seq`, cache,
the four token buckets, `next_event_seq`, `generation`, `next_ordinal`,
`next_transfer`, `in_flight`, and a v3 session's views, outbox and throttle.
*Tests:* G2, G5, G13.

G-4. **Frozen.** While graced, a handle is not bound: every per-peer method
other than `unbind_peer`, `grace_deadline` and `resume_peer` answers exactly
as for an unbound handle (`ingest` `Refused { Rejected(Unauthenticated) }`,
`ingest_transfer` `Refused(Unbound)`, the rest `UnknownPeer`). The session
gets no publication, receipt or capture post-state and holds no egress; it
holds one `MAX_PEERS` slot (Reading 13). *Tests:* G5, G12.

G-5. **Expiry (D12).** `sweep_graces(now)` removes every grace with
`deadline_ms <= now`; a removed session is gone as by `unbind_peer` (handle
and epoch retired for ever). It runs in `pump` right after its
`TimeRegression` check, in each `bind_*` right before its `ServerBusy`
check, and in `begin_grace` and `resume_peer` at step 3.
`grace_deadline(peer)` is `Some(deadline_ms)` while the grace is held, a
past deadline included until a sweep, else `None` (and `None` on a closed
host). *Tests:* G3, G12.

G-6. **Resume decision (H3, H4, H8).** `resume_peer(request, now_ms)`:
(1) `Closed`; (2) `TimeRegression`, nothing changes; (3) record `now_ms`,
sweep; (4) no live or graced session whose epoch is `request.epoch` →
`Rejected { epoch: request.epoch, reason: Denied }`; (5) no proof stored,
or `!request.proof.ct_eq(stored.as_bytes())` → `Denied`; (6)
`fence.check_request(request)` errs → `Denied`; (7) plan the resume
snapshot, reading only (G-7): `QueueFull` → `Busy` (Reading 11),
`CounterExhausted` → `Denied`, `Invariant` → that `Err`; (8)
`fence.resolve(request, &ResumeDecision::Accept { progress: vec![LaneProgress
{ lane: LANE_COMBAT, finalized_through: next_new_seq − 1 }] })`; an `Err`
here is `Invariant("resume resolve after check")`; (9) commit (G-7) and
return `Accepted { peer, accepted }`. Every `Rejected` carries
`request.epoch`. The request's claims are never read. A refusal never
moves the fence or a deadline; no attempt extends a deadline. *Tests:* G2,
G3, G4, G7.

G-7. **Resume commit (H5, H6).** A graced session returns to `sessions`
under the same handle (its grace is removed); a live one stays. A snapshot
session commits `stage_snapshot`'s step 6 (`:2385–2414`) for its current
grants, map and `next_net` with cause `Resume`: `Cancel(in_flight,
Superseded)` if one is in flight, a `Begin` with id `next_transfer`,
`cursor` = the last issued `event_seq`, `base_tick` = `server_tick()`, the
body from the current grants, the log cleared first. A v3 session commits
`plan_v3_stage(.., Resume)` with `commit_v3_stage(.., None)` (`:2432`,
`:4086`), which keeps its `InterestView` (ids are not re-minted). Nothing
H6 lists is reset: epoch, cache, `next_new_seq`, `next_event_seq`,
ordinals, transfer ids, token buckets. *Tests:* G2, G6, G8, G9.

G-8. **Retry identity (D12).** After `Accepted`, the stored bytes of a seq
at or below `finalized_through` are a cache hit with the original receipt
and no execution; a seq above it is admitted as new on its original
`observed_tick`. *Tests:* G2, G5.

G-9. **The world continues.** `begin_grace`, the sweep and `resume_peer`
call no sim operation and touch no turn, timer, pause, setting, capture or
other session; `tick`, `advance`, host operations and other peers run
unchanged during a grace; no turn ends because a player is away.
*Tests:* G10.

G-10. **Budgets are not refilled** by `begin_grace` or `resume_peer`: the
buckets carry on, refilling only with time as before. *Tests:* G11.

G-11. **Restart (D10, D12).** Graces, fences and proofs are never in a
checkpoint; `save_checkpoint` bytes do not depend on them; a loaded host has
none, so an old epoch is `Denied` by `resume_peer` and its command bytes
`SessionExpired` in `pump` (`crates/crpg-server/src/checkpoint.rs:3–10`).
*Tests:* G14.

G-12. **Unbind and shutdown.** `unbind_peer` on a graced handle drops the
grace; `shutdown` drops every grace. *Tests:* G14.

### T025b-q — the resumable adapter
N-1. **Start.** `start_resumable` has `start`'s precedence (`HostClosed` →
`HostInUse` → `TimeRegression`, `crates/crpg-server/src/quic.rs:471–486`);
`HostInUse` counts graces (`session_count`). `start` keeps every byte and
call it has today; the rest of N-2..N-9 applies only to a resumable adapter.
*Tests:* N6.

N-2. **Phase 1** reads `poll_notice` until `None`: `Event(e)` is handled as
today's loop (`:522–540`); `Resume(r)` is N-5.

N-3. **Ticket.** After a `/2` hello's `accept` succeeds and the binding is
recorded (`:694–718`): `host.issue_resume_ticket(peer, resume_proof(&record
credential, epoch)?)`, traced `IssueResumeTicket { peer, result }`
(the bytes are not traced); `Ok(bytes)` → `try_send_channel(conn,
Channel::Resume, &bytes)`, a send error counted in `frames_discarded`; an
`Err` from the host returns from the pump (poison). A `/1` binding gets no
ticket. The ticket is therefore the first frame after the welcome.
*Tests:* N1.

N-4. **Fence tags (H2).** A hello-bound connection holds

## Questions for the user
Answered by the user on 2026-11-17 (D68): **Question 1 (b)** — the proof is the keyed BLAKE3 derivation of N-10, and T025b-q adds the `blake3` workspace edge to `crpg-server`. **Question 2 (b)** — a refused resume closes at once with code 5 or 7; ADR-0032 H4 gets the addendum. The original questions follow for the record.

1. **Where does the "reconnect password" come from?** When a player joins,
   the server gives their game a secret (a "ticket"); if the connection
   drops, the game shows the ticket to get the same seat back. The server
   has no source of random numbers of its own, so the ticket must be made
   from something it already has.
   (a) **Reuse the player's invitation secret as the ticket.** No new code
   library. But the ticket is then the invitation itself: anyone who copies
   a ticket can join as that player at any time, not just reclaim one
   dropped seat.
   (b) **Mix the invitation secret with the session number using a
   standard keyed hash (BLAKE3, already used by the engine for save-state
   hashing).** One existing library becomes available to `crpg-server`
   (nothing new is downloaded). A copied ticket only reclaims that one
   session, and only within its 30 seconds.
   (c) **Use the operating system's random numbers.** Needs a new library
   and makes tickets differ run to run; no gain over (b) here.
   *Recommend (b):* D12 asks for a session-bound proof, and (b) gives one
   with a library already in the build.
2. **How should the server say "no" to a reconnect?** ADR-0032 says: send a
   short "rejected" message, then close after it arrives. Waiting for it to
   arrive stops the server's game loop for up to 2 seconds per refusal (the
   transport's close-flush timeout), and anyone can send fake reconnects.
   (a) **Message, then wait** (as the ADR says): the loop can stall.
   (b) **Hang up at once with a reason code** (5 = "start a new session",
   7 = "busy, try again"); the client reads the code instead of a message.
   Instant; ADR-0032 H4 gets an addendum, and the client task (T046) maps
   the two codes.
   *Recommend (b).* Under (a), N-5 step 3 becomes `accept_resume(conn,
   encode_down(Answer(Rejected)))` then `close(conn, code, Flush)` and a
   retiring entry, N4 expects the 20-byte `[0x91, 0x03, 0x32] ++ epoch ++
   [0x01]` answer, and crate invariant 7's "never blocks" gains an
   exception.
