## Task
Make the host run what T138 and T140 built: pause, rights, auto-pause, the
turn timer, mode requests, real-time ticks with their events, and protocol
v3 sessions with the `0x82` snapshot. Today the host has none of it:
`Host::tick` maps every error to `"zero-event tick failed"` and delivers
nothing (`crates/crpg-server/src/host.rs:2022–2029`), the six T138d/T036c
event arms are withheld (`:2484–2489`), every session speaks the host-wide
v1/v2 (`:83–109`, `:1082–1087`), and a snapshot plan is refused unless it fits
the egress queue whole (`:1690–1694`). Two defects T138 left in the host are
fixed here (Readings 1–3, both confirmed by the contract review): a peer
command can journal four events against a bound of three, and a real-time
tick's events are acknowledged uncaptured, so the checkpoint's evidence rule
refuses to load a save made during a real-time fight.

- **T141s — host records and checkpoint version 2 (S-set).** A second kind
  of capture-journal entry, `HostRecord`, for events the host makes itself;
  checkpoint version 2 that saves them, while version 1 still loads and is
  still written when no host record is retained; the host-operation tail;
  `tick` as the first host operation; the four-event bound.
- **T141a — host actions.** `host_action` (AI, timer), the operator's
  `request_mode`, and `awaiting_orders` for the RT AI.
- **T141b — pause, auto-pause and the turn timer** (ADR-0029 P1–P8), the
  operator settings and the pause-aware tick driver `advance`.
- **T141c — v3 sessions and the `0x82` sender.** `bind_v3_peer`, fact and
  host-fact grants, reading `World` into T140c's contexts, the `0x82`
  snapshot at bind, narrowing and `Resync`, paced into the egress queue
  (H-7).
- **T141d — v3 publication.** v3 intents (`Stop`, `Pause`, `Unpause`,
  `RequestMode`) with rights and the new codes (H-5), the v3 event mapping
  (H-3, H-4), and one page per operation cut by `frame_spans` (H-6).
- **T141e — v3 timing.** The `Clock` heartbeat (H-1) and the in-flight
  throttle (H-8, D54).

v1 and v2 sessions keep every byte and rule they have today, and a host
that never runs a real-time tick or a host action writes today's checkpoint
bytes.

## Readings
Design decisions this contract makes. Each needs the user's approval with
the contract. Items marked **Q** follow the user's answers of 2026-11-13.

**Decided already (not reopened).** D30c accepted ADR-0029 with its nine
recommendations: pause is host state (P1), commands run while paused (P2,
open question 6), rights default as P4 (question 4), auto-pause defaults as
P6 (question 5), mode switches apply at the next boundary (question 1), AI
runs outside tick order (T15, question 9). D32i–p settled T138: `OrderEnded`
only for an invalid due order (D32l), an unaffordable due order clears
(D32m), setting an order checks affordability (D32n), RT terminal reuses
`OutOfTurn` (D32p). D52 settled T140: rolls stay off the wire, the pause
reason goes to every player and the pauser is never named (T140 Question 3),
the 20 s deadline and the held-delta budgets. D54: T141's host tests drive v3
through `ReassemblyPoolV3`/`ReplicaWorldV3`, and H-8 throttles a peer's deltas
while its `0x82` transfer is in flight. D55/D56 approved T140r.

1. **Host operations are a second journaled path beside peer commands.** A
   tick, a host action (AI, the turn timer) and an operator mode request
   change the authority with no originating peer, no intent sequence and no
   receipt. They run through one private tail (S-3). Today `Host::tick`
   "journals nothing" (`crates/crpg-server/AGENTS.md:47–50`); T138 made an RT
   tick journal events (`crates/crpg-sim/src/history.rs:716–766`), and the
   next peer command's `acknowledge(after)` acknowledges them uncaptured
   (`crates/crpg-server/src/host.rs:1544–1546`). Host operations never move
   `executions()` and never block on egress room.
2. **Q1 (a) — host operations get their own record.** The capture journal
   becomes a sequence of entries, each a `CapturedRecord` (peer command,
   unchanged) or a new `HostRecord` (host operation with at least one event),
   numbered by the one `capture_seq`, retired by the one
   `acknowledge_captures`, bounded by the one `MAX_CAPTURE_RECORDS` /
   `MAX_CAPTURE_BYTES`. The checkpoint's evidence rule ("each record starts
   where the previous ended", `crates/crpg-server/src/checkpoint.rs:246–248`)
   is kept and now holds over every entry, so every envelope after the wrap
   is evidenced again. *Rejected:* a separate host-record journal with its own
   acknowledgement: the two retained suffixes would leave history gaps the
   rule cannot check.
3. **Checkpoint version 2 is read beside version 1, not migrated.** A
   version-1 checkpoint is exactly a version-2 checkpoint with no host
   record, so a loader that accepts both needs no transformation. The writer
   emits version 1 (today's bytes) when no host record is retained and
   version 2 otherwise, so turn-based hosts, every existing test and every
   save made today stay byte-identical. *Rejected:* always writing version 2
   (moves every checkpoint byte and length assertion), and a one-way
   migration step (nothing to transform).
4. **A peer command may journal four events.** With an RT-capable turn-based
   encounter, a killing `UseAbility` that ends the last turn of a round with a
   pending switch to RT journals `ActionResolved`, `Died`, `ModeChanged`,
   `RoundStarted` (`tasks/T138.md:649–659`). The host bound is three
   (`crates/crpg-server/src/capture.rs:40`), checked after the sim has
   committed (`crates/crpg-server/src/host.rs:1411–1415`), so today that
   command returns `Invariant` with the authority moved. New
   `MAX_NEW_EVENTS_PER_COMMAND_RT = 4` replaces the three in reservation,
   commit and checkpoint validation; the old constant keeps 3 and its
   turn-based meaning, which existing tests pin
   (`crates/crpg-server/tests/host_capture.rs:1588`, `:1713`). v2 delivery
   stays within `MAX_DELIVERY_OPS_PER_COMMAND` because `ModeChanged` and
   `RoundStarted` have no v2 form (receipt + 2 events + 3 `Health` + `Turn` =
   7 ≤ 8).
5. **After the sim commits, nothing undoes it, and every fallible step is
   ordered before any host ledger moves** (review finding 10). A host
   operation and a peer command alike: auto-pause and the timer (infallible),
   then the record (a size or encode failure is `Invariant`), then each v3
   session's page or restage plan (a failure fences that session only, as
   `unbind_peer`; the operation still succeeds), then the appends, then the
   sim acknowledgement, which always runs. A record that could not be built
   is the only way evidence goes missing, and the next checkpoint then fails
   to load, so it fails closed and visibly.
6. **The sim never chooses a mode; the operator's settings do.** Settings
   (initial mode, auto-pause toggles, turn timer) and pause state are
   operator-owned host state, never in `World`, the journal or the checkpoint
   (P1, P7). A restored host starts paused with `Restore` and multiplayer
   settings. `HostSettings.initial_mode` is the T11 session setting that
   T040's `start_encounter` will read (Question 2).
7. **Per-session wire, and v1/v2 sessions are frozen.** A session bound with
   `bind_v3_peer` speaks v3 whatever `HostConfig.protocol` says; `bind_peer`
   and `bind_snapshot_peer` keep the host-wide v1/v2 (ADR-0021 Decision 2,
   `docs/adr/0021-authoritative-host-capture.md:39`, gains a dated note).
   v1/v2 sessions receive exactly what they receive today: deliveries for
   peer commands only. Host operations publish to v3 sessions only, so RT
   play, timers and AI need v3 clients.
8. **A v3 session's ids come from its `InterestView`.** T140c's `FactView`
   resolves keys through the epoch's one `InterestView`
   (`crates/crpg-net/src/facts_v3.rs:3–10`), so a v3 session has no
   `plan_map` map: `InterestView` mints its `NetId`s (ascending `EntityKey`,
   which for one area is ascending `EntityId`, as `plan_map` does) and retires
   them when an entity leaves view. The key's area is `World::area()`, or
   `HOST_UNBOUND_AREA` (`Ulid` 0) for an unbound world.
9. **The `order` grant follows control (N2, H-3).** No operator grant type
   holds an `order` flag: a row's `FactMask.order` is set exactly when the
   session's control list holds the entity. `OrderEnded` reaches only the
   same peers.
10. **Event grants reuse the existing per-field grants.** `RoundStarted.round`
    needs `turn_round`; `ModeChanged` needs `EncounterGrants.mode` for the mode
    and `turn_round` for the round; `OrderEnded.actor` needs control and
    `present`; `Joined` needs `present && spawn`, `Left` `present && despawn`;
    `Moved` stays withheld (H-4). The six arms at
    `crates/crpg-server/src/host.rs:2484–2489` (`RoundStarted`, `ModeChanged`,
    `OrderEnded`, `Joined`, `Left`, `Moved`) stay `None` for v2 sessions.
11. **A v3 page is one operation's frames**: the originator's receipt, the
    `InterestView` enters, the operation's events in journal order, the rest
    of the page (health, turn, removals, fact ops), then any due `Clock` and
    `HostFacts`; cut by `codec_v3::frame_spans`, one `event_seq` per span
    (H-6). Events sit after the enters and before the removals (T027b D6), and
    their ids resolve against the ids live before the page plus those it
    minted. The page is built after auto-pause and the timer (Reading 5), so
    its `Clock` and `HostFacts` are current (review finding 1).
12. **v3 never blocks admission; overflow restages.** A v3 page is computed
    after execution on clones of the two views and committed only if it fits;
    otherwise the session gets a fresh `0x82` snapshot. v3 sessions take no
    part in `accepted_room`, and a rejected v3 intent never returns `Blocked`:
    its receipt is logged if it fits, else dropped and recovered by the
    client's retry (review finding 9).
13. **Every v3 first delivery is an `0x82` snapshot.** A first page of 1,024
    fully disclosed rows is about 2.8 MB (`tasks/T140.md:952–957`), above the
    2 MiB per-peer egress. `bind_v3_peer` stages transfer 1 at cursor 0, and
    staging is followed by one delta holding `[Clock, HostFacts]` (H-2).
14. **Pacing (H-7).** A staged plan goes to a per-session outbox (at most one
    plan: 90 entries, 2,852,148 bytes, retired by pacing or the next staging,
    unbind or shutdown); entries move to the delivery log in order while the
    egress caps allow. The caps do not change.
15. **Q4 (a) — notices and receipts during a reconnect download are
    dropped (H-8).** While a session's transfer is in flight it gets at most
    one page per `POLICY_V3_THROTTLE_TICKS` (10) ticks and at most 128 frames
    and 2,097,152 bytes of deltas, state folded by the views' change
    detection; event ops and receipts for that session are not sent in that
    window. Its state is exact after publication.
16. **Q3 (a) — a mode request needs the `pause` right.** The client already
    knows its `pause` right (`HostFacts.rights`), so no new wire fact.
17. **v3 receipt codes reach the trusted API through a projection.**
    `AdmissionResult.status` and `cached_status` keep the frozen v1 type
    (`crates/crpg-server/src/host.rs:282–293`; built by literal in
    `crates/crpg-godot/src/core/authority/tests.rs:257`). The retry cache
    stores the v3 status for every session (v1 statuses convert losslessly),
    a cache hit re-sends the exact code, and `AdmissionResult`/`cached_status`
    report 21..=29 as `IllegalAction` and 30 as `NotAuthorized`;
    `cached_status_v3` gives the exact one (review finding 8).
18. **RT AI is the caller's.** `awaiting_orders` lists the combatants AI must
    decide for (T15: RT due with no order; TB the head), and `host_action`
    executes the decision. Which combatants are AI-controlled is the caller's
    fact; no AI policy and no dependency is added.

### T141s — `capture.rs`, `checkpoint.rs`, `host.rs` (S-set)
```rust
// capture.rs, after MAX_NEW_EVENTS_PER_COMMAND (which keeps the value 3):
/// Maximum history envelopes one peer command journals once an encounter is
/// real-time capable: ActionResolved + Died + ModeChanged + RoundStarted.
pub const MAX_NEW_EVENTS_PER_COMMAND_RT: usize = 4;
/// Maximum envelopes in one host record: one sim journal's worth.
pub const MAX_HOST_RECORD_EVENTS: usize = crpg_sim::MAX_HISTORY_EVENTS;          // 4,096
/// Maximum compact `serde_json` length of one host record: one sim journal's
/// canonical bytes plus 64 KiB for brackets, commas and the record's fields.
pub const MAX_HOST_RECORD_BYTES: usize = crpg_sim::MAX_HISTORY_BYTES + 65_536;   // 1,114,112
const _: () = assert!(MAX_HOST_RECORD_BYTES >= crpg_sim::MAX_HISTORY_BYTES
    + 2 * crpg_sim::MAX_HISTORY_EVENTS + 1_024);

/// What made a host record (serde `snake_case`: "tick", "action", "turn_timer").
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum HostOp {
    /// `Host::tick` or `Host::advance`'s tick.
    Tick,
    /// `Host::host_action` (T141a).
    Action,
    /// The turn timer's `EndTurn` (T141b).
    TurnTimer,
}

/// One host operation's captured evidence. Field order is the JSON order.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct HostRecord {
    /// Shares the journal's numbering with `CapturedRecord`.
    pub capture_seq: u64,
    pub op: HostOp,
    /// `(history_start, history_end]`, never empty.
    pub history_start: u64,
    pub history_end: u64,
    /// `server_tick()` after the operation.
    pub processed_tick: u64,
    /// The operation's envelopes, 1..=MAX_HOST_RECORD_EVENTS.
    pub events: Vec<crpg_sim::HistoryEnvelope>,
}

/// One capture-journal entry.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CaptureEntry {
    /// An accepted peer command.
    Command(CapturedRecord),
    /// A host operation that journaled at least one event.
    Host(HostRecord),
}

// checkpoint.rs, after CHECKPOINT_VERSION (which keeps the value 1):
/// The checkpoint version written when at least one host record is retained.
pub const CHECKPOINT_VERSION_HOST_RECORDS: u32 = 2;

// host.rs
pub enum HostError {
    // … every existing variant, unchanged …
    /// The capture journal has no room for a host record; the trusted
    /// consumer must `acknowledge_captures` first.
    CaptureFull,
}
impl Host {
    /// Up to `limit` entries with `capture_seq > after`, in order; the same
    /// cursor rules and errors as `read_captures`.
    pub fn read_capture_entries(&self, after: u64, limit: usize)
        -> Result<Vec<CaptureEntry>, HostError>;
}
```

## Behaviour
Normative. Each item names the tests that prove it. "Refused" means the

### T141s: host records and checkpoint version 2 (S-set)
S-1. **Entries** (Reading 2). The host's capture journal holds
`CaptureEntry`s. `capture_seq` runs from `capture_acknowledged + 1` to
`last_capture` over both kinds; `acknowledge_captures(through)` retires the
prefix of both kinds; `MAX_CAPTURE_RECORDS` counts entries and
`MAX_CAPTURE_BYTES` sums both kinds' compact `serde_json` lengths. A peer
command's `CapturedRecord` is exactly today's. *Tests:* S1, S6.

S-2. **Reads.** `read_capture_entries(after, limit)` applies
`read_captures`' checks in its order (`InvalidPageLimit`, then
`StaleCaptureCursor`, then `FutureCaptureCursor`) and returns up to `limit`
entries with `capture_seq > after`. `read_captures(after, limit)` returns the
`Command` entries of that same page, in order (so a page may hold fewer than
`limit` records). *Tests:* S1.

S-3. **The host-operation tail** (Readings 1, 5), after a host operation's
sim call commits with events `E` (`history_start = s`, `history_end = e`):
(1) auto-pause, then timer observation (T141b; nothing before it); (2) if `E`
is not empty, build `HostRecord { capture_seq: last_capture + 1, op, s, e,
processed_tick: server_tick(), events: E }`; a record over
`MAX_HOST_RECORD_BYTES` or `MAX_HOST_RECORD_EVENTS` is `Invariant("host
record exceeds its bound")`; (3) publish (T141d; per-session failures fence
that session, D-9); (4) append the record; (5) `history.acknowledge(e)`,
always, even after step 2's `Invariant`, which is then returned. A
zero-event operation makes no record. *Tests:* S1, S2, S7 (unit).

S-4. **`tick`** (Reading 1): (1) `Closed`; (2) if the encounter is
real-time (`combat.mode == RealTime`, the only mode whose ticks journal),
reserve one host record: `entries + 1 > MAX_CAPTURE_RECORDS` or
`capture_bytes + MAX_HOST_RECORD_BYTES > MAX_CAPTURE_BYTES` is
`CaptureFull`, refused; (3) `HistoryWorld::tick()`; any `Err` is
`Invariant("tick refused by the history caps")`, refused (the sim commits
nothing, `tasks/T138.md:677–681`); (4) the tail with `HostOp::Tick`. `tick`
ignores pause (B-4). A turn-based, TB-only or no-encounter tick reserves
nothing and journals nothing: exactly today's behaviour. *Tests:* S1, S2,
S6.

S-5. **Writing** (Reading 3). `save_checkpoint` writes `"version":1` and
today's exact JSON when no `HostRecord` is retained. Otherwise it writes
`{"version":2,"incarnation":…,"protocol":…,"server_tick":…,"history":{…},
"captured":[…],"host_records":[…],"capture_acknowledged":…}`: `captured`
holds the retained `CapturedRecord`s and `host_records` the retained
`HostRecord`s, each list ascending by `capture_seq`, each element in its
struct's field order. *Tests:* S1, S2.

S-6. **Reading** (Reading 3), `load_checkpoint`: `version` other than 1 or
2 is `UnsupportedVersion { version }`; version 1 with a `host_records` key,
or version 2 without one, is `Malformed` (the existing unknown/missing-key
rule); then the existing checks, with these changes: (a) a `CapturedRecord`
with more than `MAX_NEW_EVENTS_PER_COMMAND_RT` events is `Malformed`; (b)
each `HostRecord`: `history_start < history_end`, `history_end − history_start
== events.len() ≤ MAX_HOST_RECORD_EVENTS`, envelope sequences contiguous from

### T141d: v3 publication
D-1. **Intent decode and cache.** A v3 session's staged bytes decode with
`codec_v3::decode_intent`, its canonical bytes are `codec_v3::encode_intent`,
and every receipt it gets is a v3 frame. `CacheEntry.status` stores a
`protocol_v3::ReceiptStatus` for every session (a v1/v2 status converts by

### T141e: v3 timing
E-1. **Heartbeat** (H-1). At every `tick` publication of a running host, a
session whose `server_tick − last_clock_tick >= POLICY_CLOCK_HEARTBEAT_TICKS`
(100) gets `Clock` in that tick's page, even when the page is otherwise
empty. `last_clock_tick` becomes `server_tick` whenever a `Clock` op is
logged for the session (C-6, D-12, heartbeat). A paused host does not tick,
so it sends no heartbeat; its pause change already sent one. *Tests:* E1, E2.

E-2. **Throttle** (H-8, D54, Reading 15, Question 4). From a staging at server tick `s`
until `in_flight` becomes `None`: a publication at server tick `t` produces
frames for the session only if `t >= last_page + POLICY_V3_THROTTLE_TICKS`
(`last_page` starts at `s` and becomes `t` when frames are logged) and the
frames keep the delta frames and bytes logged since `s` (C-6's frame
included) within `POLICY_V3_IN_FLIGHT_FRAMES` and `POLICY_V3_IN_FLIGHT_BYTES`.
A publication that is not allowed logs nothing and leaves both views and the
sent host facts unchanged, so the next allowed page carries every change;
its event ops and receipt are dropped. A page refused by the budget ends
deltas until the transfer ends. A new staging restarts the throttle. *Tests:*
E3, E4.

## Errors
Four new `HostError` variants, appended after `Invariant` in this order:
`CaptureFull` (T141s), `Combat(CombatError)` (T141a), `InvalidSettings`
(T141b), `NotV3Peer` (T141c). `Display`: `<VariantName> at host/admission`;
`source()` stays `None`. Every existing variant, payload and text is
unchanged, and so are `CheckpointError`'s. New `Invariant` texts: `"tick
refused by the history caps"`, `"host record exceeds its bound"`, `"history
refused a host operation"`, `"v3 snapshot projection failed"`, `"v3 page
projection failed"`, `"v3 frame failed to encode"`.

| Refusal | Result |
|---|---|
| no journal room for a host record (RT `tick`, `host_action`) | `Err(CaptureFull)`, nothing changes |
| sim refuses a host operation (`host_action`, `request_mode`) | `Err(Combat(e))`, nothing changes |
| `turn_timer_ms: Some(0)` | `Err(InvalidSettings)` |
| v3-only call on a v1/v2 session | `Err(NotV3Peer)` |
| a v3 session's page or restage cannot be built | that session is fenced; the operation succeeds |
| v3 intent: actor or target unmapped, not granted or not controlled | receipt `Rejected(NotAuthorized)` (17) |
| v3 `Pause`/`Unpause` without the right | receipt `Rejected(NoPauseRight)` (30); `AdmissionResult` `NotAuthorized` |
| v3 `RequestMode` without the `pause` right | receipt `Rejected(NotAuthorized)` (17) |
| v3 sim refusal | receipt `Rejected(code(e))` (D-4); `AdmissionResult` `IllegalAction` for 21..=29 |
| checkpoint: version not 1 or 2 | `CheckpointError::UnsupportedVersion { version }` |
| checkpoint: a command record with more than 4 events, a bad host record, a numbering gap or duplicate across the two lists, or a history range that does not start at the previous entry's end | `CheckpointError::Malformed` |

## Questions for the user
1. **Does the host keep a separate record of what happens on its own?**
   Today the server keeps a short-lived "evidence" record of every command a
   player sends (what it did, which events it caused), and a save is refused
   unless every event since start-up belongs to such a record. Real-time
   fights break that: the clock produces attacks and deaths with no player
   command behind them, and so do the turn timer and computer-controlled
   characters. As things stand, a save made during a real-time fight usually
   cannot be loaded again. (a) **Add a second kind of record** for events the server makes
   itself, with a new save-format version that still reads old saves. Most
   complete; about 300 more lines, and it becomes protected (S-set) work.
   (b) **Keep records for player commands only**, and let a save have gaps
   where the server acted on its own. The events themselves stay in the game
   state either way; only this side record skips them. One existing test
   changes from "a gap is refused" to "a gap loads" (X1), and a new test
   still refuses overlaps. *Recommend (b):* the only reader of these records
   today discards them immediately, the game's own history already holds
   every event, and (a) can still be added later if a tool needs it. Players
   and authors see no difference.
   *Answered 2026-11-13 (user): (a), not the recommendation. Applied as the
   S-set part T141s (Readings 2, 3, 5; S-1..S-8; X1, X2); the gap reading and
   the first draft's X1 are withdrawn.*
2. **May the server's tests build small encounters from game data?** The
   server code cannot start an encounter without the encounter, creature and
   ability documents, and its tests are not allowed to read those document
   types today. (a) **Allow it for tests only** (a "dev-dependency" on
   `crpg-data`, which the network crate's tests already have). Nothing ships
   differently. (b) **Don't**: the "start an encounter in the session's mode"
   method moves to the dedicated-server task (T040), and T141 tests use
   saved-game files only. *Recommend (a):* starting a fight in real time or
   turn-based from the session setting is part of this work, and without (a)
   it would ship untested.
   *Answered 2026-11-13 (user): delay; no dependency. `start_encounter` moves to
   T040 (Out of scope); T141 tests use saved-game JSON and the existing
   fixture.*
3. **Who may switch a fight between real time and turn-based?** A switch
   applies at the next round for everyone. (a) **Whoever may pause** (in
   single player, the player; in multiplayer, the session owner and anyone
   the owner grants pause to). Players already see whether they may pause, so
   the game can show or hide the switch button correctly. (b) **A separate
   permission**, which players could not see until a later protocol version,
   so a button might appear and then be refused. (c) **Anyone who controls a
   character in the fight**, which in multiplayer lets any player change the
   pace for everyone. *Recommend (a).*
   *Answered 2026-11-13 (user): (a). Reading 16, D-2.*
4. **What does a reconnecting player miss in a real-time fight?** While a
   player downloads the fight (up to 20 seconds), the server sends that player
   at most two updates a second (you chose this in T140r, D54). Each update
   carries the latest state, so health, turn order and the clock are always
   right once the download ends. The question is the combat-log lines ("A
   hits B for 3", "round 5 started") from those seconds. (a) **Skip them** for
   that player; they see the state but not the log lines of the download
   window. (b) **Keep up to 256 of them** and send them after the download;
   about 150 more lines, and in a large fight some are still lost.
   *Recommend (a):* it is simple and cannot overflow, and a player
   reconnecting mid-fight was not watching those seconds anyway.
   *Answered 2026-11-13 (user): (a). Reading 15, E-2.*
