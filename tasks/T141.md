## Task
Make the host run what T138 and T140 built: pause, rights, auto-pause, the
turn timer, mode start and requests, real-time ticks with their events, and
protocol v3 sessions with the `0x82` snapshot. Today the host has none of it:
`Host::tick` maps every error to `"zero-event tick failed"` and delivers
nothing (`crates/crpg-server/src/host.rs:2022–2029`), the five new history
events are withheld (`:2484–2489`), every session speaks the host-wide
v1/v2 (`:83–109`, `:1082–1087`), and a snapshot plan is refused unless it fits
the egress queue whole (`:1690–1694`).

- **T141a — host operations.** Ticks, a trusted `host_action` (AI and the
  turn timer use it) and the operator's `request_mode` become *host
  operations*: journaled, not peer commands. Fixes two defects T138 left in
  the host: a peer command can journal four events (the bound is three), and
  a real-time tick's events break checkpoint loading. `awaiting_orders` reports
  who the RT AI must order.
- **T141b — pause, auto-pause and the turn timer** (ADR-0029 P1–P8), the
  operator settings, the pause-aware tick driver `advance`, and
  `start_encounter` in the session's mode (T11).
- **T141c — v3 sessions and the `0x82` sender.** `bind_v3_peer`, fact and
  host-fact grants, reading `World` into T140c's contexts, the `0x82`
  snapshot at bind, narrowing and `Resync`, paced into the egress queue
  (H-7).
- **T141d — v3 publication.** v3 intents (`Stop`, `Pause`, `Unpause`,
  `RequestMode`) with rights and the new codes (H-5), the v3 event mapping
  (H-3, H-4), and one page per operation cut by `frame_spans` (H-6).
- **T141e — v3 timing.** The `Clock` heartbeat (H-1) and the in-flight
  throttle (H-8, D54).

v1 and v2 sessions keep every byte and rule they have today.

## Readings
Design decisions this contract makes. Each needs the user's approval with
the contract; the four marked **Q** are the "Questions for the user".

**Decided already (not reopened).** D30c accepted ADR-0029 with its nine
recommendations: pause is host state (P1), commands run while paused (P2,
open question 6), rights default as P4 (question 4), auto-pause defaults as
P6 (question 5), mode switches apply at the next boundary (question 1), AI
runs outside tick order (T15, question 9). D32i–p settled T138: `OrderEnded`
only for an invalid due order (D32l), an unaffordable due order clears
(D32m), setting an order checks affordability (D32n), RT terminal reuses
`OutOfTurn` (D32p). D52 settled T140: rolls stay off the wire, the pause
reason goes to every player and the pauser is never named (T140 Question 3),
the 20 s deadline and the held-delta budgets. D54: T141's host tests drive v3
through `ReassemblyPoolV3`/`ReplicaWorldV3`, and H-8 throttles a peer's deltas
while its `0x82` transfer is in flight. D55/D56 approved T140r.

1. **Host operations are a second journaled path beside peer commands.** A
   tick, a timer `EndTurn`, an AI action, an operator mode request and an
   encounter start change the authority with no originating peer, no intent
   sequence and no receipt. They run through one private routine
   (`host_op`): execute on `HistoryWorld`, publish (v3 sessions only,
   Reading 5), evaluate auto-pause (T141b), observe the turn timer (T141b),
   then acknowledge the sim journal through its last sequence. They create
   no capture record, never move `executions()`, and never block on egress
   room. Today `Host::tick` "journals nothing" (`crates/crpg-server/AGENTS.md:47–50`);
   T138 made an RT tick journal events (`crates/crpg-sim/src/history.rs:716–766`),
   and the next peer command's `acknowledge(after)` silently acknowledges
   them uncaptured (`crates/crpg-server/src/host.rs:1544–1546`).
2. **Q1 — evidence for host operations: (b), captures stay per peer
   command.** The capture journal is "one `CapturedRecord` per accepted
   command" (`crates/crpg-server/src/capture.rs:3–4`); its one consumer
   acknowledges every poll (`crates/crpg-godot/src/core/authority.rs:594–597`).
   Host operations are deterministic consequences of the authority and are
   kept in it (`history_hash`). So the checkpoint rule "each record starts
   where the previous ended" (`crates/crpg-server/src/checkpoint.rs:246–248`),
   which assumed every envelope after the wrap comes from a command
   (`:205–207`), becomes "each record starts at or after the previous end":
   gaps (host operations) load, overlaps stay `Malformed`. Without this, a
   checkpoint whose retained records straddle a real-time tick's events fails
   to load. Alternative (a) adds a
   host-operation record kind and checkpoint version 2 (Question 1).
3. **A peer command may journal four events.** With an RT-capable
   turn-based encounter, a killing `UseAbility` that ends the last turn of a
   round with a pending switch to RT journals `ActionResolved`, `Died`,
   `ModeChanged`, `RoundStarted` (`tasks/T138.md:649–659`). The host bound
   is three (`crates/crpg-server/src/capture.rs:40`), checked after the sim
   has committed (`crates/crpg-server/src/host.rs:1411–1415`), so today that
   command returns `Invariant` with the authority already moved. New
   `MAX_NEW_EVENTS_PER_COMMAND_RT = 4` replaces the three in reservation,
   commit and checkpoint validation; the old constant keeps its value and its
   turn-based meaning, because existing tests pin it as the turn-based worst
   case (`crates/crpg-server/tests/host_capture.rs:1588`, `:1713`). v2
   delivery stays within `MAX_DELIVERY_OPS_PER_COMMAND` because `ModeChanged`
   and `RoundStarted` have no v2 form (receipt + 2 events + 3 `Health` +
   `Turn` = 7 ≤ 8).
4. **The sim never chooses a mode; the operator's settings do.**
   `HostSettings.initial_mode` is the T11 session setting. Settings (mode,
   auto-pause toggles, turn timer) and pause state are operator-owned host
   state, never in `World`, the journal or the checkpoint (P1, P7). A
   restored host starts paused with `Restore` and multiplayer settings; the
   operator re-applies its own.
5. **Per-session wire, and v1/v2 sessions are frozen.** A session bound with
   `bind_v3_peer` speaks v3 whatever `HostConfig.protocol` says; `bind_peer`
   and `bind_snapshot_peer` keep the host-wide v1/v2 (ADR-0021 Decision 2,
   `docs/adr/0021-authoritative-host-capture.md:39`, gains a dated note:
   "per session for v3"). v1/v2 sessions receive exactly what they receive
   today: deliveries for peer commands only. Host operations publish to v3
   sessions only, so a v2 client does not see an RT tick, a timer `EndTurn`
   or an AI action. Real-time play, timers and AI therefore need v3 clients;
   the QUIC route (`/3`) and the Godot bridge come later (Out of scope).
6. **A v3 session's ids come from its `InterestView`.** T140c's `FactView`
   resolves keys through the epoch's one `InterestView`
   (`crates/crpg-net/src/facts_v3.rs:3–10`), so a v3 session has no
   `plan_map` map: `InterestView` mints its `NetId`s (ascending `EntityKey`,
   which for one area is ascending `EntityId`, as `plan_map` does) and retires
   them when an entity leaves view. `replica_id`, intent resolution,
   `legal_intents` and event candidates read it. The key's area is
   `World::area()`, or `HOST_UNBOUND_AREA` (`Ulid` 0) for an unbound world, the
   same value in every row and in the viewer's interest.
7. **The `order` grant follows control (N2, H-3).** No operator grant type
   holds an `order` flag: a row's `FactMask.order` is set exactly when the
   session's control list holds the entity. Revoking control withholds the
   order on the next page. `OrderEnded` reaches only the same peers.
8. **Event grants reuse the existing per-field grants.** `RoundStarted.round`
   needs `turn_round`; `ModeChanged` needs `EncounterGrants.mode` for the mode
   and `turn_round` for the round; `OrderEnded.actor` needs control (Reading
   7) and `present`; `Joined` needs `present && spawn`, `Left` `present &&
   despawn` (T139's notices treated as the spawn and despawn notices of the
   encounter); `Moved` stays withheld (H-4). The five T138d `None` arms
   (`crates/crpg-server/src/host.rs:2484–2489`) stay `None` for v2 sessions.
9. **A v3 page is one operation's frames.** For each v3 session and each
   operation: the originator's receipt, then the `InterestView` enters, then
   the operation's events in journal order, then the rest of the page
   (health, turn, removals, fact ops), then any due `Clock` and `HostFacts`;
   cut by `codec_v3::frame_spans`, one `event_seq` per span (H-6). Events sit
   after the enters and before the removals (T027b D6), and their ids are
   resolved against the ids live before the page plus those it minted, so an
   entity removed by the same page is still named.
10. **v3 never blocks admission; overflow restages.** A v3 page is computed
    after execution, on clones of the two views, and committed only if it fits
    the session's egress room; otherwise the session gets a fresh `0x82`
    snapshot (`Cancel(Superseded)` first if one is in flight). v3 sessions take
    no part in `accepted_room`'s worst-case reservation, which stays the v1/v2
    rule. A lost receipt is recovered by the client's retry, as for a pending
    resync today (`crates/crpg-server/src/host.rs:1385–1388`).
11. **Every v3 first delivery is an `0x82` snapshot.** A first page of 1,024
    fully disclosed rows is about 2.8 MB (`tasks/T140.md:952–957`), above the
    2 MiB per-peer egress. `bind_v3_peer` therefore stages transfer 1 at
    cursor 0, like a narrowing, and the client starts in `AwaitSnapshot`.
    Staging is followed by one delta holding `[Clock, HostFacts]` (H-2).
12. **Pacing (H-7).** A staged plan goes to a per-session outbox; frames move
    from the outbox to the delivery log, in order, while the egress caps
    allow, at staging, at `take_delivery`/`take_delivery_entries` and after
    `acknowledge_delivery`. The caps do not change.
13. **Q4 — notices during a reconnect download are dropped (H-8).** While a
    session's transfer is in flight it gets at most one page per
    `POLICY_V3_THROTTLE_TICKS` (10) ticks and at most 128 frames and
    2,097,152 bytes of deltas in total (`TransferLimitsV3::v3()`'s receiver
    budget), state folded by the views' change detection; event ops and
    receipts for that session are not sent in that window. Its state is exact
    after publication; a few combat-log lines are lost (Question 4).
14. **Q3 — a mode request needs the `pause` right.** Whoever may pause
    everyone may also switch everyone's mode, and the client already knows its
    `pause` right (`HostFacts.rights`), so no new fact goes on the wire
    (Question 3).
15. **v3 receipt codes reach the trusted API through a projection.**
    `AdmissionResult.status` and `cached_status` are the frozen v1 type
    (`crates/crpg-server/src/host.rs:282–293`; `AdmissionResult` is built by
    literal in `crates/crpg-godot/src/core/authority/tests.rs:257`), which
    holds codes 1..=20. A v3 rejection with code 21..=29 reports
    `IllegalAction` there and 30 reports `NotAuthorized`; the wire receipt and
    the new `cached_status_v3` carry the exact code.
16. **RT AI is the caller's.** The host has no AI policy and adds no
    dependency. `awaiting_orders` lists the combatants AI must decide for (T15:
    RT due with no order; TB the head), and `host_action` executes the
    decision. Which combatants are AI-controlled is the caller's fact.

## Behaviour
Normative. Each item names the tests that prove it. "Refused" means the
stated error and no state change: authority, sessions, logs, captures,
counters, pause state and timer as before the call. **First failure wins** in
every list. "Running" means `paused() == None`.

### T141a: host operations

commits nothing, `tasks/T138.md:677–681`). (3) The host-operation tail: publish
(T141d), auto-pause and timer (T141b), then `history.acknowledge(last_sequence)`.
`tick` ignores pause (T141b B-4). A turn-based, TB-only or no-encounter tick
journals nothing, so it is exactly today's: no capture, no delivery, the same
authority as a mirror's `tick`. *Tests:* A1, A5.

A-2. **`host_action(action)`**: (1) `Closed`; (2) `validate_action(world,

refused a host operation")`, refused; (4) the host-operation tail; return the

never moves `executions()`, consumes no intent sequence and delivers nothing
to a v1/v2 session. It runs while paused (P2). *Tests:* A1, A4.

A-3. **`request_mode(mode)`**: (1) `Closed`; (2) `history.request_mode(mode)`:

### T141b: pause, auto-pause, turn timer
B-1. **Settings.** `single_player()` is `{ TurnBased, bits 0x19, None }`,
`multiplayer()` and `Default` are `{ TurnBased, bits 0x00, None }`.
`new`, `from_history` and a restored host start with `multiplayer()`.
`set_settings`: (1) `Closed`; (2) `TimeRegression`; (3) `turn_timer_ms ==
Some(0)`: `InvalidSettings`; then record `now_ms`, store, and if
`turn_timer_ms` changed, disarm the timer and observe it (B-7). *Tests:* B1,
B6.

B-2. **Pause state** (P1, P5, P7). `new` and `from_history` start running; a
host from `load_checkpoint` (and so `load_host_file`) starts
`Some(Restore)`. `pause(now_ms)`: (1) `Closed`; (2) `TimeRegression`; record
`now_ms`; if running, `paused = Some(Operator)` and the timer freezes (B-9);
if paused, nothing changes (the reason stays). `unpause(now_ms)`: (1)
`Closed`; (2) `TimeRegression`; record `now_ms`; if paused, `paused = None`
and the timer resumes (B-9), whatever the reason; if running, nothing.
Pause is never in `World`, the journal, a capture or the checkpoint.
*Tests:* B2, B3.

B-3. **`advance(now_ms)`**: (1) `Closed`; (2) `TimeRegression`; record
`now_ms`; (3) if running, the timer step (B-8); (4) if paused now, return
`{ ticked: false, timer_ended_turn, paused }`; (5) `tick` (A-1), whose error
is returned as is (a timer `EndTurn` from step 3 stays committed); (6) return
`{ ticked: true, timer_ended_turn, paused }`. One call ticks at most once.
*Tests:* B2, B4, B5.

B-4. **`tick` ignores pause.** It is the operator's primitive; `advance` is
the cadence (P1: "a paused host does not call `tick`"). A restored,
`Restore`-paused host still ticks through `tick`, so gate 10
(`crates/crpg-server/tests/host_save.rs:428`) is unchanged. *Tests:* B3.

B-5. **Auto-pause** (P6). After every committed operation that journaled at
least one event (peer command, `tick`, `host_action`, timer `EndTurn`,
`start_encounter`), if running: walk its events in journal order and map
each to a trigger: `RoundStarted` → `RoundStarted`; `ModeChanged` →
`ModeChanged`; `OrderEnded` → `OrderEnded`; `Died { entity }` with `entity`
in the party → `PartyMemberDied`. The party is the union of every bound
session's control list at that moment. For `start_encounter`,
`EncounterStarted` is checked before its events. The first trigger whose
toggle is on sets `paused = Some(Auto(trigger))` and freezes the timer; later
events are not inspected. If paused already, nothing changes. Zero-event
operations (`request_mode`, an RT order, `Stop`, `Pause`, `Unpause`) never
auto-pause. *Tests:* B4.

B-6. **Commands while paused** (P2). `ingest`/`pump`, `host_action`,
`request_mode` and `start_encounter` run unchanged while paused; only
`advance`'s tick stops. *Tests:* B2.

B-7. **Timer observation** (P8). After every peer command commit, host
operation and `set_settings`: let `key` be `Some((head, round))` when the
encounter is turn-based with `active == Some(head)`, else `None`. If
`turn_timer_ms` is `None` or `key` is `None`, disarm. Otherwise, if no timer
is armed or the armed key differs, arm for `key` with the full length: when
running the deadline is the last accepted `now_ms` + length; when paused the
frozen remainder is the length. *Tests:* B5, B6.

B-8. **Timer expiry**, `advance` step 3: armed, running and `now_ms >=
deadline` → `host_action(EndTurn { actor: head })` (A-2). `Ok` →
`timer_ended_turn = Some(head)` (B-7 then re-arms for the next head from this
`now_ms`); `Err` → disarm, `timer_ended_turn = None`, and the error is not
returned. At most one expiry per call. *Tests:* B5.

B-9. **Freezing.** Pause stores `remaining = deadline − now` (saturating);
unpause sets `deadline = now + remaining`. `turn_timer_remaining_ms()` is
`None` when disarmed, the frozen remainder when paused, else
`deadline − last accepted now_ms` (saturating at 0). *Tests:* B5.

B-10. **`start_encounter(spec)`** (Question 2 (a) only): (1) `Closed`; (2)
`history.start_encounter_in_mode(spec, settings.initial_mode)`:
`Err(Combat(e))` is `Combat(e)`, any other `Err` is `Invariant`, refused; (3)
the host-operation tail with `EncounterStarted` (B-5). *Tests:* B7.

### T141e: v3 timing
E-1. **Heartbeat** (H-1). At every `tick` publication of a running host, a
session whose `server_tick − last_clock_tick >= POLICY_CLOCK_HEARTBEAT_TICKS`
(100) gets `Clock` in that tick's page, even when the page is otherwise
empty. `last_clock_tick` becomes `server_tick` whenever a `Clock` op is
logged for the session (C-6, D-12, heartbeat). A paused host does not tick,
so it sends no heartbeat; its pause change already sent one. *Tests:* E1, E2.

E-2. **Throttle** (H-8, D54, Reading 13). From a staging at server tick `s`
until `in_flight` becomes `None`: a publication at server tick `t` produces
frames for the session only if `t >= last_page + POLICY_V3_THROTTLE_TICKS`
(`last_page` starts at `s` and becomes `t` when frames are logged) and the
frames keep the delta frames and bytes logged since `s` (C-6's frame
included) within `POLICY_V3_IN_FLIGHT_FRAMES` and `POLICY_V3_IN_FLIGHT_BYTES`.
A publication that is not allowed logs nothing and leaves both views and the
sent host facts unchanged, so the next allowed page carries every change;
its event ops and receipt are dropped. A page refused by the budget ends
deltas until the transfer ends. A new staging restarts the throttle. *Tests:*
E3, E4.

## Errors
Three new `HostError` variants, appended after `Invariant` in this order:
`Combat(CombatError)` (T141a), `InvalidSettings` (T141b), `NotV3Peer`
(T141c). `Display`: `Combat at host/admission`, `InvalidSettings at
host/admission`, `NotV3Peer at host/admission`; `source()` stays `None`.
Every existing variant, payload and text is unchanged. New `Invariant`
texts: `"tick refused by the history caps"`, `"history refused a host
operation"`, `"v3 snapshot projection failed"`, `"v3 page projection
failed"`, `"v3 frame failed to encode"`.

| Refusal | Result |
|---|---|
| sim refuses a host operation (`host_action`, `request_mode`, `start_encounter`) | `Err(Combat(e))`, nothing changes |
| `turn_timer_ms: Some(0)` | `Err(InvalidSettings)` |
| v3-only call on a v1/v2 session | `Err(NotV3Peer)` |
| v3 intent: actor or target unmapped, not granted or not controlled | receipt `Rejected(NotAuthorized)` (17) |
| v3 `Pause`/`Unpause` without the right | receipt `Rejected(NoPauseRight)` (30); `AdmissionResult` `NotAuthorized` |
| v3 `RequestMode` without the `pause` right | receipt `Rejected(NotAuthorized)` (17) |
| v3 sim refusal | receipt `Rejected(code(e))` (D-4); `AdmissionResult` `IllegalAction` for 21..=29 |
| checkpoint record with more than 4 events, or a history range below the previous record's end | `CheckpointError::Malformed` |

## Questions for the user
1. **Does the host keep a separate record of what happens on its own?**
   Today the server keeps a short-lived "evidence" record of every command a
   player sends (what it did, which events it caused), and a save is refused
   unless every event since start-up belongs to such a record. Real-time
   fights break that: the clock produces attacks and deaths with no player
   command behind them, and so do the turn timer and computer-controlled
   characters. As things stand, a save made during a real-time fight usually
   cannot be loaded again. (a) **Add a second kind of record** for events the server makes
   itself, with a new save-format version that still reads old saves. Most
   complete; about 300 more lines, and it becomes protected (S-set) work.
   (b) **Keep records for player commands only**, and let a save have gaps
   where the server acted on its own. The events themselves stay in the game
   state either way; only this side record skips them. One existing test
   changes from "a gap is refused" to "a gap loads" (X1), and a new test
   still refuses overlaps. *Recommend (b):* the only reader of these records
   today discards them immediately, the game's own history already holds
   every event, and (a) can still be added later if a tool needs it. Players
   and authors see no difference.
2. **May the server's tests build small encounters from game data?** The
   server code cannot start an encounter without the encounter, creature and
   ability documents, and its tests are not allowed to read those document
   types today. (a) **Allow it for tests only** (a "dev-dependency" on
   `crpg-data`, which the network crate's tests already have). Nothing ships
   differently. (b) **Don't**: the "start an encounter in the session's mode"
   method moves to the dedicated-server task (T040), and T141 tests use
   saved-game files only. *Recommend (a):* starting a fight in real time or
   turn-based from the session setting is part of this work, and without (a)
   it would ship untested.
3. **Who may switch a fight between real time and turn-based?** A switch
   applies at the next round for everyone. (a) **Whoever may pause** (in
   single player, the player; in multiplayer, the session owner and anyone
   the owner grants pause to). Players already see whether they may pause, so
   the game can show or hide the switch button correctly. (b) **A separate
   permission**, which players could not see until a later protocol version,
   so a button might appear and then be refused. (c) **Anyone who controls a
   character in the fight**, which in multiplayer lets any player change the
   pace for everyone. *Recommend (a).*
4. **What does a reconnecting player miss in a real-time fight?** While a
   player downloads the fight (up to 20 seconds), the server sends that player
   at most two updates a second (you chose this in T140r, D54). Each update
   carries the latest state, so health, turn order and the clock are always
   right once the download ends. The question is the combat-log lines ("A
   hits B for 3", "round 5 started") from those seconds. (a) **Skip them** for
   that player; they see the state but not the log lines of the download
   window. (b) **Keep up to 256 of them** and send them after the download;
   about 150 more lines, and in a large fight some are still lost.
   *Recommend (a):* it is simple and cannot overflow, and a player
   reconnecting mid-fight was not watching those seconds anyway.
