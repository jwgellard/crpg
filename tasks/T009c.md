## Task
Make Windows the project's primary target platform while retaining Linux as a
fully supported headless server, extensibility, and test platform. Supersede
the Linux-only replay-golden policy, then enforce independent Windows/MSVC and
Linux/GNU replay baselines in the existing CI matrix.

T009c is intentionally scheduled before T009b despite its suffix. It is a
corrective follow-up discovered after T009a was implemented; T009b remains the
already-scoped `crpgc replay` wrapper and must not build on the superseded
platform policy.

## Decision Already Made

The maintainer decided on 2026-09-06:

- **Primary platform:** `x86_64-pc-windows-msvc`. Windows is the primary
  development, product, release-gating, and behavioural-baseline platform.
- **Windows product surface:** client, editor, embedded single-player server,
  dedicated server, and CLI.
- **Supported Linux surface:** `x86_64-unknown-linux-gnu` dedicated server,
  headless CLI/tooling, server-side extensibility, and CI/testing. Supported
  means a platform-specific failure is a defect, not a best-effort caveat.
- **One authoritative implementation:** single-player hosts the same server
  implementation in the Windows process behind the client/server transport
  boundary. Windows and Linux dedicated-server processes wrap that same
  implementation. The client never mutates authoritative state directly.
- **No cross-platform lockstep promise:** Windows and Linux are not required
  to produce equal hashes. Each supported target must reproduce its own
  checked-in replay golden under the pinned toolchain, normal test profile,
  and default feature set.
- **Portable substrate:** platform-specific process, filesystem, service, and
  presentation concerns stay above `crpg-core`, `crpg-rules`, and `crpg-sim`.
  No OS-specific branch may enter those crates as part of this task.

Do not reopen these choices during implementation. If a detail below is
impossible, report that concrete blocker instead of substituting a different
platform policy.

## Purpose

The architecture already says that single-player runs the authoritative
server in-process, but `DAY_ONE.md` later treats the server as Linux and
ADR-0009/T009a make Linux the only real replay-golden gate. That is backwards
for a Windows-primary game and leaves the Windows authoritative runtime with
only a shape/repeatability test.

The correct distinction is authority versus hosting platform. The simulation
always runs under the server role. Windows is the primary host, including
single-player; Linux remains a real supported dedicated-server host. Separate
target-scoped goldens enforce both without pretending cross-platform floating
point and `libm` results must be identical.

## ADR

Add `docs/adr/0012-windows-primary-platform.md` with status **Accepted**. It
must record:

1. Windows/MSVC is the primary product and release target.
2. Linux/GNU is a supported headless server, tooling, extension, and test
   target, not the primary desktop presentation target.
3. The authoritative server is one platform-neutral implementation hosted
   in-process for Windows single-player and by dedicated processes on Windows
   and Linux.
4. The client/server authority boundary is unchanged in-process: transport
   may be in-memory, but the client still cannot mutate authoritative state.
5. Replay determinism remains exact-build rather than cross-platform
   lockstep. Windows and Linux compare independent target-scoped goldens.
6. Windows owns the primary behavioural baseline; Linux owns a supported
   server regression baseline. Neither baseline is compared to the other.
7. Default target tuples for current gates are
   `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`. Adding another
   target requires an explicit support decision and its own build/test scope.
8. T1 campaign data and sandboxed Lua/ruleset content remain portable.
   T0 native extensions require target-specific artifacts; their loading and
   packaging mechanism remains a separately decided implementation concern.

ADR-0012 supersedes **only** ADR-0009 Decision 3's canonical-Linux-only
selection. ADR-0009's exact-build promise, cross-platform non-promise, hash
exclusion governance, and server-authoritative rationale remain in force.
Do not edit ADR-0009: ADRs are immutable and superseded by a new ADR.

## Replay Golden Behaviour

The portable replay fixture remains:

Use two independently generated scoped goldens:

```
crates/crpg-testkit/goldens/replay_basic_rust-1.98.0_x86_64-pc-windows-msvc_test-default.golden
crates/crpg-testkit/goldens/replay_basic_rust-1.98.0_x86_64-unknown-linux-gnu_test-default.golden
```

The names encode the pinned Rust version, complete target triple, normal test
profile, and default feature set. A change to any element is a reviewed
re-baseline event.

In `crates/crpg-testkit/tests/replay_golden.rs`:

- On
  `cfg(all(target_os = "windows", target_arch = "x86_64", target_env = "msvc", debug_assertions))`,
  run a real `play_and_verify` comparison against the Windows golden.
- On
  `cfg(all(target_os = "linux", target_arch = "x86_64", target_env = "gnu", debug_assertions))`,
  run a real `play_and_verify` comparison against the Linux golden.
- On any other target/profile, retain a clearly named portable parse/play
  repeatability and shape check that does not read either scoped golden.
- Select supported-target paths at compile time. Do not inspect
  `std::env::consts::OS` to choose a golden at runtime.
- Do not add fuzzy/tolerant comparison. A mismatch on either supported target
  fails that target's test.
- The supported-target test must fail with `Io(NotFound)` if its baseline is
  absent. A missing baseline must never become a skipped green test.

Update `crates/crpg-testkit/tests/support/mod.rs` so the private path helper is
target-scoped and cannot return the wrong platform's file. Update comments in
`tests/replay.rs`, `src/harness.rs`, and `src/replay.rs` to describe the two
compile-time gates and ADR-0012. Do not change runtime replay semantics.
