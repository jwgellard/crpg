- 0.11.19 is still the newest crates.io release, not yanked. The index
  `cksum` equals the archive SHA-256 `0e750cca…befbe`, re-checked on
  2026-10-05.

The upstream change is one condition in `poll_transmit`, plus a comment and
a regression test:

```rust
if ack_eliciting && self.spaces[space_id].loss_probes == 0 && !close {
```

It is narrower than T023c's evidence one-liner (`if close { ack_eliciting
= false; }`). Both skip the congestion and pacing gate for a close packet.
The one-liner also clears `ack_eliciting` for the packet builder. That has
no effect on tracking: a close packet is never tracked, because
`sent_frames` stays `None`. It does change one thing: a server's
Initial-space close is no longer padded. The upstream form leaves both
untouched.

Consequences:

- The upstream draft in `docs/reviews/` would be a duplicate of #2785.
- The vendored patch can be the upstream commit itself (V§8 Q1).
- Retirement depends on a release that contains `e556fde`. Today that
  means 0.12, or a 0.11.x backport (V§5).

#### V§1.2 Why the fix is correct (RFC 9000 / RFC 9002)

- RFC 9002 §2: "All frames other than ACK, PADDING, and CONNECTION_CLOSE
  are considered ack-eliciting". A packet is *in flight* when it is
  ack-eliciting or contains PADDING.
- RFC 9002 §7: an endpoint "MUST NOT send a packet if it would cause
  bytes_in_flight … to be larger than the congestion window". A packet
  holding only ACK and `CONNECTION_CLOSE` frames adds nothing to
  `bytes_in_flight`, so congestion control has no grounds to hold it.
  quinn also never tracks it.
- In the closed state, `poll_transmit` builds exactly that packet. The
  close branch writes pending ACKs and the `CONNECTION_CLOSE`, then
  `break`s or `continue`s before `populate_packet`. No stream data or other
  frame is ever written.
- `ack_eliciting` was computed from stream data that will never be sent.
  And quinn ignores ACKs once closed (`process_decrypted_packet`, the
  `State::Closed` arm). So the gate could never reopen, and the peer got
  a stateless reset after the 3 × PTO close timer.
- RFC 9000 §10.2.1 requires the closing endpoint to answer incoming
  packets with a `CONNECTION_CLOSE`. The patch makes that possible under a
  full window.
- What does not change:
  - quinn's response cadence (one close per incoming packet from the
    current path) is the same as when the window is not full;
  - the anti-amplification check (RFC 9000 §8.1) still runs before the
    congestion gate, so it still applies;
  - the close timer, ACK handling and loss detection are untouched.

#### V§1.7 Measurement environment and traps

Linux/GNU, rustc 1.98.0 (88d9e12ae 2026-08-18), 4 vCPUs, normal `test`
profile, cargo-deny 0.20.2. Everything was done in a scratch directory
outside the repository. Nothing was committed, and no crate, manifest,
lock, `deny.toml`, `tools/` or `third_party/` file in this repository was
touched.

Traps hit or confirmed:

1. Outside the repository, `rust-toolchain.toml` does not apply; set
   `RUSTUP_TOOLCHAIN=1.98.0` (T030's trap).
2. GNU `patch` writes `*.orig` backups when hunks apply at an offset, and
   the archive *ships* a `Cargo.toml.orig`. So always use
   `--no-backup-if-mismatch`, and never delete `*.orig` files blindly.
3. Two extracted trees of the same package that share one
   `CARGO_TARGET_DIR` give **stale builds**. Path-package fingerprints are
   by mtime, and one run silently tested the wrong tree. Use a fresh target
   directory per tree.

+fn connection_close_while_congestion_blocked() {
+    let _guard = subscribe();
+    let mut pair = Pair::default();

+

+    // client without driving the server, so no ACKs come back and in-flight bytes stay pinned at
+    // the window
+    let s = pair.client_streams(client_ch).open(Dir::Uni).unwrap();

+    // close: check for the event after each packet exchange, before the clock jumps ahead
+    let mut result = None;

```rust
// ---------------------------------------------------------------------------
// 28: a Discard close reaches the peer while congestion blocked (T023v).
// ---------------------------------------------------------------------------

/// Server → client datagrams that must have left the server after the
/// client → server path is cut, before the close is issued. With no ACK
/// arriving, bytes in flight never fall, so the server sends one burst up
/// to its congestion window (7–9 datagrams measured) and then only PTO
/// probes, two per probe timeout. 14 therefore means the window was full
/// for at least one probe timeout before the close.
const CONGESTION_BLOCKED_DATAGRAMS: u64 = 14;

#[test]
fn discard_close_reaches_peer_when_congestion_blocked() {
    let mut server = bind_server(ServerLimits::v1());
    let relay = UdpRelay::start(server.local_addr(), RelayConfig::clean());
    let welcome = Welcome {
        wire_version: 1,
        epoch: epoch(28),
    };
    let (mut client, conn) = connect_via_relay(&mut server, &relay, ClientLimits::v1(), welcome);

    // Positive control: the relay forwards a frame.
    server.try_send(conn, &pattern(28, 0, 1_000)).expect("send");
    assert_eq!(client_recv(&mut client), Ok(pattern(28, 0, 1_000)));

    // Cut client → server: from here on no ACK reaches the server.
    relay.set_blackhole_to_server(true);
    let before = relay.forwarded_to_client();
    let n_frames = 16u32;
    for n in 1..=n_frames {
        server
            .try_send(conn, &pattern(28, n, DELTA_CAP))
            .expect("send");
    }
    until("server congestion blocked", || {
        relay.forwarded_to_client() >= before + CONGESTION_BLOCKED_DATAGRAMS
    });
    let report = server
        .close(conn, CloseCode::SessionFenced, CloseMode::Discard)
        .expect("close");
    relay.set_blackhole_to_server(false);
    assert!(relay.dropped() >= 1, "the client's ACKs were cut");

    let mut k = 0u32;
    loop {
        match client_recv(&mut client) {
            Ok(frame) => {
                k += 1;
                assert_eq!(frame, pattern(28, k, DELTA_CAP), "in-order prefix");
            }
            Err(reason) => {
                // quinn-proto 0.11.19 unpatched: `Reset` (T023c C§1.4).
                assert_eq!(reason, CloseReason::Peer { code: 9 });
                break;
            }
        }
    }
    assert!(
        k as usize + report.outbound_frames_discarded <= n_frames as usize,
        "k = {k}, discarded = {}",
        report.outbound_frames_discarded
    );
    assert_eq!(
        next_closed(&mut server),
        (conn, CloseReason::Local(CloseCode::SessionFenced))
    );
}
```

Design notes:

- **Why 16 frames.** 16 × 65,536 bytes is the server's whole 1 MiB send
  window, so every `try_send` succeeds (`expect("send")`), with 32 frames
  of queue headroom.
- **The waits are guards, not oracles.** The `until` (30 s guard) waits
  for a precondition, and the oracle is the close reason.
- **Lifting the cut after `close`.** Unpatched, the client's next packet
  then reaches the server, which answers with a stateless reset after its
  3 × PTO close timer. So the regression fails fast and names `Reset`,
  instead of running to the 30 s guard.
- **Why the threshold cannot fail a patched build.** It only decides
  *when* to close. A patched build delivers the close whether or not the
  window was full. A host whose congestion window exceeds 14 datagrams
  would only weaken the test's power to catch a regression (V§8 Q10).
- **Positive and negative controls.** The 1,000-byte frame is the
  positive control. `relay.dropped() ≥ 1` shows the ACK path was really
  cut.
