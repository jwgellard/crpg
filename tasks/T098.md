## Hypothesis (not established)
`Flush` waits at most `close_flush_timeout_ms` (v1 2,000 ms,
`src/limits.rs:35`) for the peer's ack. The client closes as soon as it has
its own 1,000 frames back (comment at `tests/quic.rs:1110`: "Wait for the
server to drain our last frames before closing"), so the case uses the 2 s
product bound as a drain wait. If the server's single host loop, which also
sends frames of up to 65,536 bytes to four clients, falls behind in a debug
build on a loaded runner, its inbound queue for that connection parks
(crate invariant 5). The stream window then fills, and the client's last
frames cannot leave within 2 s. The crate's own trap says test waits are
30 s failure guards, never oracles.

The other reading is a product defect: `Flush` gave up early, or
`outbound_frames_discarded` counts frames that were delivered
(`src/client.rs:281`–`326`, `src/close.rs`). That would be data lost on a
normal close, so it must be ruled out, not assumed away.

## What must not change
- Case 13's assertions: every frame exactly once and in order in both
  directions, `outbound_frames_discarded == 0`, and the server sees
  `Closed(Peer { code: 0 })` with nothing extra. No `#[ignore]`, no retry
  around the case, no relaxed assertion, no move to a slower lane.
- The v1 limits, `close_flush_timeout_ms` = 2,000 included. A cap change
  needs an ADR (crate `AGENTS.md`), which makes it a stop, not a fix.
- The public surface, wire bytes, close codes, and the other 29 cases.
- No new dependency or dev-dependency.

## Investigation (session 9)

Environment: Windows 10.0.26300, `x86_64-pc-windows-msvc`,
`rustc 1.98.0 (88d9e12ae 2026-08-18)`, debug profile (default `cargo test`),
16 logical CPUs. Contention = four copies of the test binary started in
parallel. Logs live in `target/t098/` (uncommitted): one `*.log` per batch,
`*.fail*.txt` holding each failing output, and `runs.sh`.

| condition | runs | failures | failure detail |
|---|---|---|---|
| case 13 alone | 20 | 0 | — |
| full `quic` suite alone | 3* | 0 | — |
| case 13, 4× parallel contention | 80 | 3 | `outbound_frames_discarded` = 46, 68, 68 |

\* `suite-alone.log` was interrupted after 3 of its 10 planned runs; those 3
passed. (A manager note claimed 50/50 for the suite, but only 3 runs are on
disk here.)

Every contended failure is the same pair, in log order:

1. a client thread panics at `tests/quic.rs:1112` —
   `assert_eq!(report.outbound_frames_discarded, 0)` with left 46 or 68;
2. the server main thread panics at `tests/quic.rs:1054` —
   `deadline: server traffic` (the 30 s guard).

One earlier run saw `deadline: server frame` at
`tests/support/quic_rig.rs:170` — the same starved-server symptom surfacing
through the `server_recv` helper used by other cases.

Mechanism. Case 13 (`tests/quic.rs:974`) runs 4 clients against one server
whose single main loop both sends 1,000 frames to each client and receives
1,000 from each (`:1016-1058`). The client half (`client_traffic`,
`:1074-1113`) leaves its loop once *its* 1,000 are received (`:1078`), then
closes `(Normal, Flush)` (`:1111`). The comment at `:1110` says it waits for
the server to drain, but nothing does: the close falls straight into `Flush`,
which waits at most `close_flush_timeout_ms` = 2,000 ms
(`src/limits.rs:35`, `src/client.rs:295`) for the writer to empty the
outbound queue, FIN, and the peer's ack (`run_flush` `src/queue.rs:837-876`;
`lane_writer` finish `src/queue.rs:753-756`). Under contention the server's
main loop is starved: it `try_recv`s too slowly, its bounded inbound queue
fills, the reader parks and stops sending window updates (invariant 5), the
client's stream window fills, `write_all` blocks, and the client's last
frames stay queued. At the 2 s deadline `run_flush` records the close →
`discard_outbound` (`src/queue.rs:376-387`) drops the still-queued frames and
adds their count to `record.discarded` (`:384`); the report is that delta
(`src/client.rs:301`, `:326`). The server is still waiting for those frames,
so its 30 s guard fires. One stall, two panics.

Readings.

- Test-harness reading — **supported**. The close at `tests/quic.rs:1111`
  uses the product's 2 s bound as a drain wait; the "wait for the server to
  drain" comment is not implemented. It fails only under load (0/20 alone,
  3/80 contended), and both panics are the test's own guards, never a
  product error.
- Product-defect reading — **ruled out** by code. `outbound_frames_discarded`
  cannot count a frame the peer received: `discarded` is incremented only in
  `discard_outbound` over `conn.outbound`, i.e. frames the writer never
  popped (`pop_outbound` `src/queue.rs:366-374`) and so never handed to QUIC.
  And `Flush` cannot return before its deadline while frames are
  unacknowledged and the peer is healthy: `run_flush` waits for
  `writer_finished` (queue drained + `send.finish()` + `send.stopped().await`,
  `src/queue.rs:753-756, 762-767`) or `reason.is_some()`, else the deadline;
  `stop()` then waits for `close_done || control_done` to
  deadline + `SYNC_GRACE` (`src/client.rs:312-321`). The observed 46/68 are
  frames the server never received, honestly reported.

Recommended fix (not applied). In `client_traffic`
(`tests/quic.rs:1074-1113`), implement the `:1110` comment for real: after
the send/receive loop, before `close`, poll
`client.stats().outbound_frames == 0` under the 30 s `DEADLINE` guard (the
same `assert!(elapsed < DEADLINE)` + 1 ms park pattern already in the
function). Because `write_all` is flow-controlled by the server's receive
windows, an empty client queue means the writer has handed every frame to
QUIC, which can only happen once the server has received them; `close(Flush)`
then has nothing to discard, the assertion holds deterministically, and the
server has already seen all 1,000 so its guard never fires. This changes no
limit, close semantic, wire byte, public surface or other case, and keeps
every assertion in "What must not change".

## T098c measurement (session 11)

Environment: Windows 10.0.26300, `x86_64-pc-windows-msvc`,
`rustc 1.98.0 (88d9e12ae 2026-08-18)`, debug profile (default `cargo test`),
16 logical CPUs. Contention = N copies of the `quic` test binary started in
parallel. Logs live in `target/t098c/` (uncommitted): one `*.log` per batch,
`*.fail*.txt` holding each failing output, and `runs.sh`.

| condition | runs | failures | failure detail | time window (UTC) |
|---|---|---|---|---|
| case alone | 20 | 0 | — | 12:44:26–12:44:39 |
| 4× parallel | 80 | 0 | — | 12:44:55–12:45:06 |
| 8× parallel | 160 | 1 | `deadline: server event` (quic_rig.rs:110) | 12:46:45–12:47:30 |
| 8× parallel, instrumented | 160 | 2 | `hello timeout` → `deadline: server event` | 12:49:35–12:50:35 |

(420 runs total, 3 failures, all under 8× contention. The brief's prescribed
4× protocol — 20 alone + 80 contended — reproduced nothing; the 8× batches are
supplementary and match the original "under load" context.)

Mechanism. Case 23 (`lane0_codec_frames_decode_after_impaired_delivery`,
`tests/quic.rs:1819`) calls `codec_frames_through(impaired())` (`:1821`), which
starts the drop/reorder relay and connects the client **through it**:
`connect_via_relay` (`:1182-1197`) passes `relay.addr()` to `connect_async`
(`:1190`), so the QUIC/TLS handshake and the hello frame travel the same
`drop_every=13, reorder_depth=4` path as the codec frames. The test then waits
on `next_hello` → `next_event` (`tests/support/quic_rig.rs:104-113`), a 30 s
`DEADLINE` guard over `poll_event` (`:110`).

The server emits `ServerEvent::HelloReceived` only once TLS completes **and**
the hello frame is read inside `hello_timeout_ms` = 5,000 (`src/limits.rs:31,
58-59`; `src/server.rs:747-777`). On expiry the server closes with
`CloseCode::HelloTimeout` and `end_handshake` drops the connection, emitting
**no event at all** (`src/server.rs:760-764`): a connection that never produced
`HelloReceived` has no host-visible id, so there is no `Closed` to publish
(`src/server.rs:673`, `src/queue.rs:409`). Under CPU contention the impaired
handshake/hello exceeds the 5 s bound; the server times out and emits nothing;
`next_event` polls for 30 s and panics `deadline: server event`.

Temporary instrumentation (`eprintln!` in the `Err(_elapsed)` arm, reverted
before commit) confirmed every failure is the hello-timeout path — two `hello
timeout after Elapsed(())` lines immediately preceding the two `deadline:
server event` panics — never a stream-loss or close-code path.

Verdict: **test-side**. The exact cause is `tests/quic.rs:1190`
(`connect_via_relay` runs the handshake over `relay.addr()`, the impaired
relay), which makes the test rely on the product's 5 s `hello_timeout_ms`
bound never firing. That bound is a limit, not a delivery guarantee; under
load it fires and the product then correctly stays silent.

- Product-defect reading — **ruled out** by code. `HelloTimeout` + no event
  for a pre-hello connection is correct (`src/server.rs:673, 760-764`;
  `src/queue.rs:409`); nothing was delivered, so nothing is lost, and the
  client's own `connect` is bounded separately by `connect_timeout_ms` =
  10,000 (`src/limits.rs:33`).
- Recommended fix (not applied — out of scope for a measurement task): in
  `codec_frames_through` (`tests/quic.rs:1735-1743`) and
  `ordered_exactly_once_through_impaired_relay` (`:1199`), establish the
  connection over a clean relay (or enable `impaired()` only after
  `HelloReceived`/`accept`), then apply the drop/reorder to the frame
  exchange. That is a wait on observable state (the handshake completing), in
  the shape of T098b — never a longer timeout, retry or `#[ignore]` — and it
  changes no limit, close semantic, wire byte, public surface or other case,
  keeping every assertion in "What must not change" (`dropped >= 1`,
  `reordered >= 1`, decode order, the clean positive control).

## T098e measurement (session 34)

The failure. `v2_send_precedence_and_caps`
(`crates/crpg-net-quic/tests/channel.rs`) failed twice on Ubuntu `check` in
PR #78 at the client `before` comparisons (`channel.rs:1173`/`1185` in that
tree): `left (0,0,0,0,false)`, `right (0,0,1,4096,false)`. The `before`
snapshot was taken while the previous loop iteration's accepted frame was
still in the outbound queue; the writer then handed it to QUIC, so the queue
*shrank* between snapshot and check. The property the test pins is "a
rejected send enqueues nothing", not "nothing drains".

All 11 before-fix panics are the same shape: `left (0,0,0,0,false)` against a
right side holding one queued outbound frame (4,096 bytes on a client, 65,536
on the server). Every failing run failed only `v2_send_precedence_and_caps`;
the other 20 `channel` cases passed in every run. The local rate (9/20 alone)
is far above CI's 2-in-many, but it is the same three assertions and the same
values, so the mechanism is not in doubt — the drain race is simply easier to
hit when the machine has spare cores.

Choice: shape (a), a quiescent `before`. `tests/support/quic_rig.rs` already
has the bounded-wait helper this file uses everywhere (`until`, a 30 s
failure guard with a 1 ms park), so a new
`drained_queue_fields(|| stats)` beside `queue_fields` waits for
`outbound_frames == 0 && outbound_bytes == 0` and then snapshots. Shape (a)
keeps every assertion exact: the `assert_eq!` on the whole tuple and the
`Err(...)` equality checks are untouched, and only the moment of the
snapshot moved. Shape (b) would have replaced the equality with an
`<=`-style property, which is a weaker statement and would no longer catch a
rejected call that both added and dropped a frame. The wait costs nothing
measurable (test run 0.94–1.00 s after, against 0.91–1.03 s before) because
the queue is normally already empty when the snapshot is taken.

Every `before` snapshot in the case got the same treatment — the pending
`p1`/`p2`, the closed `c1`/`c2`, `c3`, `c4`'s empty and too-big loops, the
open `client_v2` Lane0/Transfer and Resume blocks, the `client_v1` block,
and the closed `closed_v2`/`closed_v1` blocks. No assertion was deleted,
relaxed or ignored, and nothing under `crates/crpg-net-quic/src/` changed.

The failure. Case 13
(`ordering_preserved_under_concurrent_traffic`, `tests/quic.rs:974`) failed

So the CI shape (the final wait) did not reproduce locally, even at 16×
contention: the local breaks under gross starvation surface earlier, in the
traffic loops, and the weighted case-13 failures sit in case 23. The
mechanism was then isolated with two temporary probes (removed before
commit; `src/` reverted byte-identical to `master`):

1. `close_flush_timeout_ms = 0` (budget already spent when
   `QuicClient::close(Flush)` is called): the server saw
   `Closed(Peer { code: 0 })` 1.7 µs later. A spent budget alone is not
   enough.
2. Default v1 limits; one client queues 128 × 4,096-byte frames; the server
   drains 10 and then stops; the client closes `(Normal, Flush)`. The client
   spent the whole 2,000 ms flush budget, discarded 48 frames, and
   `close_quinn` logged the close request. The server then drained its queue
   (`reader_parked: false`, inbound/outbound 0), and **never saw
   `Peer { code: 0 }`**: at 60.0 s it published `Closed(IdleTimeout)`.
   `v1.idle_timeout_ms` is 60,000 (`src/limits.rs:27`) — longer than the
   test's 30 s guard.

Mechanism (product-side). `QuicClient::stop` fixes
`close_flush_timeout_ms` as one shared budget *before* flushing:
`let deadline = deadline_after(...)` at `src/client.rs:462`, stored in
`Stop { code, deadline }` after the flush wait. `run_flush`
(`src/queue.rs:968-1011`) may use the entire 2 s waiting for the FIN ack;
it then records the close, discards what is left and calls `close_quinn`
(queuing the CONNECTION_CLOSE). `client_main` then runs
`endpoint.close(...)` followed by
`timeout_at(Instant::from_std(stop.deadline), endpoint.wait_idle())`
(`src/client.rs:680-685`) — with a deadline that has already expired. The
wait returns at once, the I/O thread ends and the runtime is dropped before
the queued CONNECTION_CLOSE is transmitted. The peer records no reason at
all and only idles out at 60 s. That is the reported 30 s guard: after the
join, the server waits on a connection whose close never left the client.
The 16× diagnostics show the same client path (`close=2.009 s`,
`discarded=0`) under load.

`frame_tx.connection_close` is not a usable counter here: it read 0 in both
probes, including probe 1 where the close arrived in 1.7 µs.

Choice: measurement only, no fix. The failing assertion is the product
guarantee (`Flush` ends with a CONNECTION_CLOSE the peer can see, E§3), so
no test-side wait can make a close that never left the client visible inside
the 30 s guard; draining every connection while waiting, or keeping the
client's endpoint alive, would only hide it. The cause is under `src/`,
which this brief forbids changing. The one-line shape of a product fix, for
the follow-up: give close transmission its own budget (or take the
`wait_idle` deadline after the flush rather than before it) so a spent flush
budget cannot drop the close. Nothing under `crates/crpg-net-quic/src/` or
`tests/` changed; no assertion was deleted, relaxed or ignored, and case
23's intermittent `deadline: exchange` (not this task) is left untouched.
