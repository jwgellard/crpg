## Hypothesis (not established)
`Flush` waits at most `close_flush_timeout_ms` (v1 2,000 ms,
`src/limits.rs:35`) for the peer's ack. The client closes as soon as it has
its own 1,000 frames back (comment at `tests/quic.rs:1110`: "Wait for the
server to drain our last frames before closing"), so the case uses the 2 s
product bound as a drain wait. If the server's single host loop, which also
sends frames of up to 65,536 bytes to four clients, falls behind in a debug
build on a loaded runner, its inbound queue for that connection parks
(crate invariant 5). The stream window then fills, and the client's last
frames cannot leave within 2 s. The crate's own trap says test waits are
30 s failure guards, never oracles.

The other reading is a product defect: `Flush` gave up early, or
`outbound_frames_discarded` counts frames that were delivered
(`src/client.rs:281`–`326`, `src/close.rs`). That would be data lost on a
normal close, so it must be ruled out, not assumed away.

## What must not change
- Case 13's assertions: every frame exactly once and in order in both
  directions, `outbound_frames_discarded == 0`, and the server sees
  `Closed(Peer { code: 0 })` with nothing extra. No `#[ignore]`, no retry
  around the case, no relaxed assertion, no move to a slower lane.
- The v1 limits, `close_flush_timeout_ms` = 2,000 included. A cap change
  needs an ADR (crate `AGENTS.md`), which makes it a stop, not a fix.
- The public surface, wire bytes, close codes, and the other 29 cases.
- No new dependency or dev-dependency.

## Investigation (session 9)

Environment: Windows 10.0.26300, `x86_64-pc-windows-msvc`,
`rustc 1.98.0 (88d9e12ae 2026-08-18)`, debug profile (default `cargo test`),
16 logical CPUs. Contention = four copies of the test binary started in
parallel. Logs live in `target/t098/` (uncommitted): one `*.log` per batch,
`*.fail*.txt` holding each failing output, and `runs.sh`.

| condition | runs | failures | failure detail |
|---|---|---|---|
| case 13 alone | 20 | 0 | — |
| full `quic` suite alone | 3* | 0 | — |
| case 13, 4× parallel contention | 80 | 3 | `outbound_frames_discarded` = 46, 68, 68 |

\* `suite-alone.log` was interrupted after 3 of its 10 planned runs; those 3
passed. (A manager note claimed 50/50 for the suite, but only 3 runs are on
disk here.)

Every contended failure is the same pair, in log order:

1. a client thread panics at `tests/quic.rs:1112` —
   `assert_eq!(report.outbound_frames_discarded, 0)` with left 46 or 68;
2. the server main thread panics at `tests/quic.rs:1054` —
   `deadline: server traffic` (the 30 s guard).

One earlier run saw `deadline: server frame` at
`tests/support/quic_rig.rs:170` — the same starved-server symptom surfacing
through the `server_recv` helper used by other cases.

Mechanism. Case 13 (`tests/quic.rs:974`) runs 4 clients against one server
whose single main loop both sends 1,000 frames to each client and receives
1,000 from each (`:1016-1058`). The client half (`client_traffic`,
`:1074-1113`) leaves its loop once *its* 1,000 are received (`:1078`), then
closes `(Normal, Flush)` (`:1111`). The comment at `:1110` says it waits for
the server to drain, but nothing does: the close falls straight into `Flush`,
which waits at most `close_flush_timeout_ms` = 2,000 ms
(`src/limits.rs:35`, `src/client.rs:295`) for the writer to empty the
outbound queue, FIN, and the peer's ack (`run_flush` `src/queue.rs:837-876`;
`lane_writer` finish `src/queue.rs:753-756`). Under contention the server's
main loop is starved: it `try_recv`s too slowly, its bounded inbound queue
fills, the reader parks and stops sending window updates (invariant 5), the
client's stream window fills, `write_all` blocks, and the client's last
frames stay queued. At the 2 s deadline `run_flush` records the close →
`discard_outbound` (`src/queue.rs:376-387`) drops the still-queued frames and
adds their count to `record.discarded` (`:384`); the report is that delta
(`src/client.rs:301`, `:326`). The server is still waiting for those frames,
so its 30 s guard fires. One stall, two panics.

Readings.

- Test-harness reading — **supported**. The close at `tests/quic.rs:1111`
  uses the product's 2 s bound as a drain wait; the "wait for the server to
  drain" comment is not implemented. It fails only under load (0/20 alone,
  3/80 contended), and both panics are the test's own guards, never a
  product error.
- Product-defect reading — **ruled out** by code. `outbound_frames_discarded`
  cannot count a frame the peer received: `discarded` is incremented only in
  `discard_outbound` over `conn.outbound`, i.e. frames the writer never
  popped (`pop_outbound` `src/queue.rs:366-374`) and so never handed to QUIC.
  And `Flush` cannot return before its deadline while frames are
  unacknowledged and the peer is healthy: `run_flush` waits for
  `writer_finished` (queue drained + `send.finish()` + `send.stopped().await`,
  `src/queue.rs:753-756, 762-767`) or `reason.is_some()`, else the deadline;
  `stop()` then waits for `close_done || control_done` to
  deadline + `SYNC_GRACE` (`src/client.rs:312-321`). The observed 46/68 are
  frames the server never received, honestly reported.

Recommended fix (not applied). In `client_traffic`
(`tests/quic.rs:1074-1113`), implement the `:1110` comment for real: after
the send/receive loop, before `close`, poll
`client.stats().outbound_frames == 0` under the 30 s `DEADLINE` guard (the
same `assert!(elapsed < DEADLINE)` + 1 ms park pattern already in the
function). Because `write_all` is flow-controlled by the server's receive
windows, an empty client queue means the writer has handed every frame to
QUIC, which can only happen once the server has received them; `close(Flush)`
then has nothing to discard, the assertion holds deterministically, and the
server has already seen all 1,000 so its guard never fires. This changes no
limit, close semantic, wire byte, public surface or other case, and keeps
every assertion in "What must not change".
