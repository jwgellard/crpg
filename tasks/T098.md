## Task
Find out why `ordering_preserved_under_concurrent_traffic` (T023 case 13)
failed once on Windows CI, and fix the cause without weakening the case.

Status: **open, cause unknown.** Filed by the manager on 2026-10-16 at the

## Crate(s)

## Evidence
- **The failure.** Run 38879365927 (master push, PR #29 merge `48c6578`),
  job `check (windows-latest)`, attempt 1, 2026-10-16 09:20 UTC:
  `quic` 29 passed, 1 failed, 13.73 s. The Linux job was cancelled by
  fail-fast, so that run says nothing about Linux.
- **The panics, in log order:**
  1. a client thread, `tests/quic.rs:1112`:
     `assert_eq!(report.outbound_frames_discarded, 0)` with left 8, right 0;
  2. the server (test main thread), `tests/quic.rs:1037`:
     `server recv: Closed(Peer { code: 0 })`;
  3. two other client threads, `tests/quic.rs:1088`:
     `client send: Closed(Peer { code: 1 })`.
- **Reading of the panics.** One client finished its loop (all 1,000 frames
  sent into its queue and all 1,000 received), closed `Normal, Flush`, and
  the flush gave up with 8 frames not delivered. The server then saw that
  client's normal close while still expecting frames from it and panicked.
  Panic 3 is consistent with the server going away after panic 2. Panic 1 is
  the first fault and the one to explain.
- **Rate.** Since T023d merged (2026-10-06), Windows `check` ran 13 times:
  11 passed, 1 failed (this one), 1 cancelled. This is the case's only

- **Code.** Since 2026-10-06, the only change under `crates/crpg-net-quic`,

  PR #30), merged 20 minutes before the failing run. The S002 PR run, the
  PR #30 merge run and the PR #31 merge run passed with it. Nothing here

## Hypothesis (not established)
`Flush` waits at most `close_flush_timeout_ms` (v1 2,000 ms,
`src/limits.rs:35`) for the peer's ack. The client closes as soon as it has
its own 1,000 frames back (comment at `tests/quic.rs:1110`: "Wait for the
server to drain our last frames before closing"), so the case uses the 2 s
product bound as a drain wait. If the server's single host loop, which also
sends frames of up to 65,536 bytes to four clients, falls behind in a debug
build on a loaded runner, its inbound queue for that connection parks
(crate invariant 5). The stream window then fills, and the client's last
frames cannot leave within 2 s. The crate's own trap says test waits are
30 s failure guards, never oracles.

The other reading is a product defect: `Flush` gave up early, or
`outbound_frames_discarded` counts frames that were delivered
(`src/client.rs:281`–`326`, `src/close.rs`). That would be data lost on a
normal close, so it must be ruled out, not assumed away.

## What must not change
- Case 13's assertions: every frame exactly once and in order in both
  directions, `outbound_frames_discarded == 0`, and the server sees
  `Closed(Peer { code: 0 })` with nothing extra. No `#[ignore]`, no retry
  around the case, no relaxed assertion, no move to a slower lane.
- The v1 limits, `close_flush_timeout_ms` = 2,000 included. A cap change
  needs an ADR (crate `AGENTS.md`), which makes it a stop, not a fix.
- The public surface, wire bytes, close codes, and the other 29 cases.
- No new dependency or dev-dependency.

## Suggested acceptance (for the brief to make exact)
1. **Reproduce first**, on native Windows/MSVC in the normal test profile:
   run the case in a loop (for example 200 runs), alone and with the rest of
   the `quic` suite running alongside it, and record the conditions and the
   failure rate. If it does not reproduce, add CPU contention and record
   that too.
2. **Name the mechanism with evidence** before changing anything. One way is
   instrumentation that stays out of the commit, or a deterministic
   reproduction made by stalling the server loop.
3. **Fix at the cause.** If the cause is the test harness, change how it
   synchronizes so the close no longer depends on scheduler timing. If the
   cause is the product, fix `src/` and add a regression case (case 31).
4. **Show the fix holds.** Run N/N under the conditions that reproduced the
   failure, plus a negative control that fails at a measurable rate with the
   fix reverted. Then the crate's full definition of done on Windows/MSVC
   and Linux/GNU.
