# T024q — transfer and resume channels on the lane stream (`crpg-net-quic`)

Status: **proposed (amended per D39b/D39d), awaits review.** The user
approved the first version on 2026-10-30 ([D39b](DECISIONS-D39.md),
conditional on one Claude `reviewer` pass) and asked for this amendment

## Task / Crate(s) / Purpose

Sole crate: `crpg-net-quic`. This is the transport follow-on to the approved
T024 contract ([T024](T024.md), D35; [ADR-0028](../docs/adr/0028-snapshot-transfer-subprotocol.md))
and the transport half of the T025a resume carriage, row T024q in
[BACKLOG](BACKLOG.md). Under a new ALPN `crpg-lane0/2` (T024 S§16 Q3) the
existing ordered lane stream gets an explicit channel selector in the
framing, and it carries three channels:

- `0x00`, lane 0 (today's intents and deltas);
- `0x81`, the snapshot-transfer frames (T024);
- `0x91`, the resume frames (T025a1).

A `crpg-lane0/2` connection may also open with a resume request instead of
a hello, on a server that opts in. The host answers that request in place of
the welcome (S§4.4–S§4.6).

The crate moves opaque bytes only. Every transfer policy (ids, cursors,
grants, narrowing, `Published`/`Resync`) belongs to [T024h](T024h.md). Every
resume policy (decoding the request, the proof, the session's invitation,
grace, fencing, the answer and its close code, tickets) belongs to
[T025a](T025a.md) and T025b.

Below, S§N cites a section of this contract, "T024 S§N" the T024 contract,
"T025a S§N" / "TR*n*" / "H*n*" the T025a contract, and `path:line` this
branch (`mgr/session-24-batch`, parent `38b1f51`; the first version cited
`task/T024qh-contract-a1`, and the `crpg-net-quic` sources are the same).
"Refused" means the call returns an error and changes no state.

## S§1. Findings (from the code)

1. One ALPN exists, `ALPN_LANE0_V1 = b"crpg-lane0/1"`
   (`src/handshake.rs:11-12`), and both TLS configs advertise only it
   (`src/tls.rs:81`, `:122`). The server re-checks it after TLS
   (`alpn_matches`, `src/server.rs:685-690`); a failure ends the handshake
   through `end_handshake`, which increments `refused_handshakes` with no
   event (`src/server.rs:674-683`, `:728-732`).
2. **An existing test pins `crpg-lane0/2` as foreign.**
   `foreign_alpn_refused` (`tests/quic.rs:692-708`) connects to a server
   built by `bind_server(ServerLimits::v1())` (that is, `QuicServer::bind`)
   offering `b"crpg-lane0/2"` and asserts the handshake fails and is
   counted. If `QuicServer::bind` began accepting `/2`, that test would fail.
   So `bind` must stay `/1`-only, and dual-ALPN must be opt-in (S§4).
3. Framing is a 4-byte big-endian `u32` length (`FRAME_HEADER_BYTES = 4`,
   `src/handshake.rs:16`; `frame_header`/`parse_frame_header`, `:36-60`).
   The direction caps are 4,096 bytes client → server and 65,536 bytes
   server → client, so **the top byte of every valid `/1` header is 0**. A
   `/1` header whose top byte is not 0 declares at least 16,777,216 bytes and
   closes with `FrameTooLarge` (3) before any body read
   (`src/queue.rs:608-625`).
4. The header width is load-bearing: outbound byte accounting subtracts
   `FRAME_HEADER_BYTES` from each queued frame (`src/queue.rs:366-374`), and
   the window floors are `cap + FRAME_HEADER_BYTES` (4,100 / 65,540) with
   compile-time checks (`src/limits.rs:43-49`), which the T023c stall
   formula (crate `AGENTS.md`, "Known traps") also assumes.
5. Queues are one per connection per direction (`Conn.inbound`/`outbound`,
   `src/queue.rs:122-160`), bounded in frames and bytes, accounted in
   payload bytes, and delivered in `try_send` order. A single queue across
   channels is therefore what keeps one total order (T024 S§10.7, S§11
   item 3; T025a TR4).
6. **`crpg-server` matches `SendError` and `ServerError` exhaustively**
   (`crates/crpg-server/src/quic.rs:869-893` and `:720-760`, `:655-672`).
   A new variant on either enum would break `crpg-server`'s build, which
   would make this a two-crate task. New failures need a new error type
   (S§6).
7. `tests/quic.rs:271` builds a `ServerEvent::HelloReceived { .. }` literal,
   so adding a field to that variant would break an existing test. The
   negotiated framing is exposed by an accessor instead (S§7).
8. The T024 transfer frames fit the existing caps: the largest downstream
   frame is 32,815 bytes and the largest upstream frame 30 bytes (T024
   S§1.3). `MAX_DOWN_FRAME_BYTES == MAX_DELTA_FRAME_BYTES` and
   `MAX_UP_FRAME_BYTES == MAX_INTENT_FRAME_BYTES`
   (`crates/crpg-net/src/protocol_transfer.rs:46-48`).
9. Close codes are 0–9 (`src/close.rs:10-70`). No new code is needed.
10. At this tip `tests/quic.rs` has 32 `#[test]` functions (the AGENTS.md
    DoD line still says 30) and `tests/quic_gaps.rs` has 7. Both stay
    byte-identical.
11. **`crpg-server` also matches `ServerEvent` exhaustively, in a
    `while let Some(event) = self.server.poll_event()` loop**
    (`crates/crpg-server/src/quic.rs:481-497`). A resume arrival therefore
    cannot be a `ServerEvent` variant (TR6). A `Closed` for a connection the
    adapter never mapped is tolerated there (the `None => {}` arm at `:493`).
12. The server reads the first lane-stream frame with the `/1` header and
    the 130-byte hello cap (`read_hello`, `src/server.rs:697-716`, through
    `read_frame`). A first header starting `0x91` declares at least
    0x9100_0000 bytes, so today it closes with `FrameTooLarge` (3) before
    any body read and is counted in `refused_handshakes` with no event
    (`src/server.rs:751-755`). That is TR2's "refused as today" on every
    server that has not opted in to resume.
13. Server events are one `VecDeque<ServerEvent>` (`src/queue.rs:242`).
    `Closed` is pushed only for connections past `Phase::Hello`
    (`try_publish`, `src/queue.rs:410-428`). One queue is what makes a
    connection's opening report always precede its `Closed`.
14. `accept` hands the welcome to the connection task, which writes it
    before it spawns the lane writer (`start_lane`, `src/server.rs:851-884`).
    `close(.., Flush)` on an accepted connection lets the writer drain,
    finishes the stream, waits for the peer's acknowledgement, and only then
    sends `CONNECTION_CLOSE` (`run_flush`, `src/queue.rs:837-876`;
    `lane_writer`, `:753-756`). quinn keeps received stream data readable
    after the connection ends (`src/queue.rs:681-685`). So "answer, then
    close" can be built from an accept-like call followed by today's
    `close(.., Flush)`, with no new close path.
15. `QuicClient` stores a `Welcome` and `welcome()` returns it by value, not
    as an `Option` (`src/client.rs:95-101`, `:189-192`). A resumed
    connection receives no welcome on the wire. Resume keeps the session's
    epoch and wire version (D39d Q4; T025a S§2 item 3), so the caller
    supplies the session's welcome (S§4.6).
16. T025a1 adds `crpg_net::protocol_resume::RESUME_VERSION = 0x91` and
    `MAX_RESUME_FRAME_BYTES = MAX_INTENT_FRAME_BYTES` (4,096), plus the
    resume codec (T025a S§9). Neither exists at this tip. The amended
    contract names both constants in compile-time checks, so it cannot
    build before T025a1 merges (S§3.2).

## S§2. Decisions this contract makes

1. **A new ALPN `crpg-lane0/2`, opt-in on the server, in two steps.**
   `QuicServer::bind` is unchanged (`/1` only). `QuicServer::bind_dual`
   advertises `[crpg-lane0/2, crpg-lane0/1]`. `QuicServer::bind_resumable`
   advertises the same list and also lets a `/2` connection open with a
   resume request (S§4.4). A client offers **exactly one** ALPN, chosen by
   the call:
   - `QuicClient::connect` offers `/1`, unchanged;
   - `QuicClient::connect_framed(.., Framing::V2)` offers `/2` only;
   - `QuicClient::connect_resume` offers `/2` only.

   There is no fallback, so a `/2` request never ends up as a `/1`
   connection (S§4.2).
2. **The channel selector is the first byte of the 4-byte header under
   `/2`.** The header becomes `[channel: u8][length: u24 big-endian]`.
   Channel `0x00` is lane 0, `0x81` the transfer subprotocol and `0x91` the
   resume subprotocol. A lane-0 frame therefore has **the same bytes under
   `/1` and `/2`**, the header stays 4 bytes, and every window floor,
   accounting rule and stall formula is unchanged (S§5).
3. **One stream, one queue per direction, shared by all three channels.**
   The order of `try_send_channel` calls is the order of arrival, across
   channels (S§8.1). A resume answer, the resume snapshot's `Begin` and
   every later delta therefore keep the order the host queued them in
   (TR4).
4. **The resume channel is directional.** Downstream, `0x91` frames may
   follow the opening at any time (the answer and tickets, TR3–TR4).
   Upstream, a `0x91` frame is legal only as the opening of a resume-first
   connection. After the opening, the server's reader closes on an upstream
   `0x91` header with `ProtocolViolation` (2), and a client's
   `try_send_channel(Channel::Resume, ..)` is refused (S§6).
5. **The resume-first connection reuses the pending/accept shape, with no
   new `ServerEvent`, `SendError`, `ServerError`, `ConnectError` or
   `CloseCode` variant (TR6).**
   - A resume opening is reported as `ServerNotice::Resume(ResumeReceived)`
     through a new `poll_notice`. `ServerNotice` is a new enum that also
     carries every `ServerEvent` in the same single order.
   - The host answers with `accept_resume(conn, answer)`. The answer is
     written as one `0x91` frame in place of the welcome. The host can also
     `refuse(conn, code)` with no answer, or `accept_resume` then
     `close(conn, code, Flush)` to send a `Rejected` answer and then close
     (TR3).
   - The resume connection presents the session-bound proof, inside the
     opaque request, instead of the invitation credential. The transport
     checks neither: the host decodes the request and authenticates it, and
     still checks that the session's invitation is registered and not
     revoked (T025a H3).
6. **Resume is opt-in at bind** (`bind_resumable`), so a server driven only
   by `poll_event` never holds a resume notice. `poll_event` is a view that
   returns `None` while a resume notice is at the head of the queue
   (S§8.3, the S§8.3 `try_recv` rule applied to notices). If `bind_dual`
   accepted resume openings, a `poll_event`-only adapter (today's
   `QuicHost`, and T024h2's on `bind_dual`) would stop at the first one
   (S§1 item 11).
7. **Purely additive API.** No existing signature, variant, field, cap,
   close code or `Display` text changes. New items:
   - `ALPN_LANE0_V2`, `Framing`, `Channel` (three values), two header
     functions, and `FrameError::UnknownChannel`;
   - `ChannelSendError`, `ResumeReceived` and `ServerNotice`;
   - seven `QuicServer` methods (`bind_dual`, `bind_resumable`,
     `poll_notice`, `accept_resume`, `framing`, `try_send_channel`,
     `try_recv_channel`) and five `QuicClient` methods (`connect_framed`,
     `connect_resume`, `framing`, `try_send_channel`, `try_recv_channel`).

   Some existing doc comments gain a sentence (S§7, "Doc-only changes").
8. **The crate stays policy-free.** It never decodes a payload, a resume
   request or a resume answer. It never looks at a payload byte to choose a
   channel, and it never mints or checks a transfer id, a proof, an epoch or
   a fence. A selector byte outside `{0x00, 0x81, 0x91}` closes the
   connection with `ProtocolViolation` (2), and so does an upstream `0x91`
   after the opening.

## S§4. ALPN, negotiation and the connection opening

### S§4.1 Constants and configs

- `pub const ALPN_LANE0_V2: &[u8] = b"crpg-lane0/2";` beside
  `ALPN_LANE0_V1`, which is unchanged.
- `QuicServer::bind(config)`: TLS `alpn_protocols = [crpg-lane0/1]`, and
  `alpn_matches` accepts only `/1`. **Byte-for-byte today's behaviour.**
- `QuicServer::bind_dual(config)`: the same `ServerConfig` validation and
  `BindError`s in the same order as `bind`, then TLS
  `alpn_protocols = [crpg-lane0/2, crpg-lane0/1]` in that order (rustls
  picks the first entry of the server's list that the client offered), and
  `alpn_matches` accepts `/1` or `/2`. Every opening is read as a hello
  (S§4.4 step 3).
- `QuicServer::bind_resumable(config)`: exactly `bind_dual`, and in
  addition a `/2` connection may open with a resume request (S§4.4 step 2).
  A `/1` connection on this server opens with a hello only.
- `QuicClient::connect(config, server, hello)` is exactly
  `connect_framed(config, server, hello, Framing::V1)`, and offers only
  `/1` as today.
- `QuicClient::connect_framed(.., Framing::V2)` offers only `/2` and opens
  with the hello.
- `QuicClient::connect_resume(config, server, session, request)` offers only
  `/2` and opens with the resume request (S§4.6).
- The TLS profile (TLS 1.3, ring, no 0-RTT, no resumption, no client
  certificate, SNI `crpg.invalid`), the certificate pin, the stream mapping
  (one bidi, zero uni, no DATAGRAM), the limits and the windows are the same
  under both ALPNs and for both openings. The hello and welcome layouts are
  unchanged.

### S§4.2 The negotiation matrix (no silent downgrade)

| Client call (ALPN offered) | `bind` server (`/1`) | `bind_dual` server (`/2`, `/1`) | `bind_resumable` server (`/2`, `/1`) |
|---|---|---|---|
| `connect` (`/1`) | `/1`, as today | `/1`; `framing(conn) == V1` | `/1`; `framing(conn) == V1` |
| `connect_framed` V2 (`/2`) | TLS fails: client `ConnectError::Handshake`; server `refused_handshakes += 1`, no event | `/2`, hello opening; `V2` | `/2`, hello opening; `V2` |
| `connect_resume` (`/2`) | TLS fails, as the row above | `/2`, but the `0x91` opening is read as a hello header: server closes `FrameTooLarge` (3), `refused_handshakes += 1`, no event; client `ConnectError::Refused { code: 3 }` | `/2`, resume opening: `ServerNotice::Resume`; `V2` |
| anything else (raw client) | TLS fails, counted (today's `foreign_alpn_refused`) | TLS fails, counted | TLS fails, counted |

The server records the negotiated ALPN and the opening kind on the
connection record when each becomes known (ALPN at record creation,
`src/server.rs:739-742`; opening after the first frame) and never changes
them. The client's `framing()` is the framing it asked for, because it
offered no other.

### S§4.3 Client check under `/2`

After TLS completes in `connect_framed(.., V2)` or `connect_resume`, the
client reads the negotiated protocol from `handshake_data()`. If it is not
exactly `Some(b"crpg-lane0/2")`, the client closes with
`ProtocolViolation` (2) and the call returns `Err(ConnectError::Handshake)`.
The `/1` path gets no new check (it stays byte-identical). This case cannot
be produced by this crate's servers, so it has no test; the pinned dispatch
is the evidence, as for the crate's other unreachable branches. The raw
quinn server of S§10 cases 20–21 cannot reach it either: rustls's client
already fails the handshake on an unoffered ALPN, and under QUIC on no ALPN
at all, before this check runs (`process_alpn_protocol`, rustls 0.23.46
`src/client/hs.rs:612-640`). The check is defence in depth.

### S§4.4 The opening (server)

After TLS and the ALPN check, the server reads the first lane-stream frame
under `hello_timeout_ms`, as today:

1. Read the 4-byte header. A FIN before it is complete closes with
   `ProtocolViolation` (2), as today.
2. **Resume opening.** Only if the server is `bind_resumable`, the
   connection negotiated `/2`, and `header[0] == 0x91`:
   `parse_channel_frame_header(header, MAX_RESUME_FRAME_BYTES)` (4,096).
   - `Err(Empty)` closes with `ProtocolViolation` (2).
   - `Err(TooLarge)` closes with `FrameTooLarge` (3), and no body is read.
   - `Ok((Channel::Resume, len))`: read `len` body bytes. A FIN or
     `RESET_STREAM` inside the body closes with `ProtocolViolation` (2).
   - Then the connection becomes pending with opening **resume**, and
     `ServerNotice::Resume(ResumeReceived { conn, remote, request })` is
     queued. No byte of `request` is inspected.
3. **Hello opening.** In every other case, today's hello path runs
   unchanged: `parse_frame_header(header, MAX_HELLO_BYTES)`, then
   `Hello::decode`, with today's codes (2, 3, 6). The connection becomes
   pending with opening **hello**, and
   `ServerEvent::HelloReceived` is queued as
   `ServerNotice::Event(..)`.
4. No complete opening frame within `hello_timeout_ms` closes with
   `HelloTimeout` (4), as today.

Every failure in steps 1–4 happens before the connection is visible:
`end_handshake` runs, `refused_handshakes` goes up by exactly 1, and no
notice is queued. A pending connection of either kind then runs today's
decision timer: no `accept`, `accept_resume` or `refuse` within
`decision_timeout_ms` closes with `AuthTimeout` (8), and its `Closed`
follows its opening notice.

A resume opening holds up to 4,096 request bytes per pending connection
instead of 130 hello bytes. That is bounded by `max_connections` (v1: 64 ×
4,096 = 262,144 bytes), only on `bind_resumable` servers.

### S§4.5 Answering a resume opening (server)

- `accept_resume(conn, answer)`, checked in this order (nothing is sent on
  a refusal):
  1. `UnknownConnection`;
  2. `Closed(reason)`;
  3. `NotPending`;
  4. `InvalidWelcome`: the opening was a hello, or `answer` is empty or
     above 65,536 bytes (`MAX_DELTA_FRAME_BYTES`).

  On success the connection is accepted. The I/O side writes
  `channel_frame_header(Channel::Resume, answer.len(), 65_536)` and the
  answer as the first downstream frame, in place of the welcome. Then the
  lane writer and reader start with `/2` framing. Frames queued by
  `try_send_channel` after `accept_resume` returns follow the answer, in
  call order.
- `accept(conn, welcome)` on a resume opening returns `InvalidWelcome`
  (after the same first three checks), and nothing is sent.
- `refuse(conn, code)` on a resume opening behaves as today: it closes at
  once with `code`, no answer is sent, and `Closed { Local(code) }` follows.
- **Answer, then close (TR3):** `accept_resume(conn, answer)`, then
  `close(conn, code, CloseMode::Flush)`. The answer reaches the client
  before the close (S§1 item 14). T025b chooses the code (T025a TR3
  recommends `AuthRefused` (5) for `Denied` and `ServerBusy` (7) for
  `Busy`).
- `close`, `stats`, `framing` (`Ok(V2)`), `try_send_channel` and
  `try_recv_channel` (`NotAccepted` while pending) and `totals().pending`
  treat a resume-pending connection exactly like a hello-pending one.

### S§4.6 The resume opening (client)

`QuicClient::connect_resume(config, server, session, request)`:

1. Before any I/O, in this order:
   - limits invalid → `Err(ConnectError::Config(_))`;
   - `session.encode()` fails (wire version not 1 or 2) →
     `Err(ConnectError::Handshake)`;
   - `request` empty or above 4,096 bytes (`MAX_RESUME_FRAME_BYTES`) →
     `Err(ConnectError::Handshake)`.

   No socket is bound for any of these.
2. TLS with the pinned verifier, offering `/2` only; then the S§4.3 check.
3. Open the bidi stream and write `[0x91][len24]` + `request`.
4. Read the answer header.
   - Its byte 0 is not `0x91`, or its length is 0 or above 65,536 → the
     client closes with `ProtocolViolation` (2) and returns
     `Err(ConnectError::InvalidWelcome)`.
   - Then read the body; a FIN before it is complete is handled the same
     way.
   - A connection that ends first → `Refused { code }` or `Lost(_)`, as
     today.
   - `connect_timeout_ms` elapsed → `TimedOut`, as today. The one timer
     covers steps 2–4 (TLS, the request write and the whole answer read),
     as `connect`'s covers the welcome read (`src/client.rs:405-418`).
5. On success, return `Ok((client, answer))`:
   - `client.framing() == Framing::V2`;
   - `client.welcome() == session`. The transport does not decode the
     answer; resume keeps the epoch and wire version (D39d Q4), and the
     caller checks the answer itself (T025a C4);
   - lane frames then flow under `/2` with the client caps.

This crate's servers cannot produce the step-4 header failures
(`accept_resume` always writes a valid header), so S§10 case 21 drives
them, the step-3 request bytes and the step-4 timeout from a raw quinn
server written in the test file.

## S§5. Framing under `crpg-lane0/2`

### S§5.1 Header layout

| Bytes | `/1` (unchanged) | `/2` |
|---|---|---|
| 0 | length bits 31–24 (always 0 for a valid frame) | channel selector |
| 1–3 | length bits 23–0 | length bits 23–0 |

Under `/2` the length is `u32::from_be_bytes([0, h[1], h[2], h[3]])`,
at most 16,777,215, and counts payload bytes only (the selector is part of
the header).

The opening is the only frame not covered by this table:

- The hello and the welcome are read and written by today's `/1` code on
  both ALPNs. A hello header whose first byte is not 0 is over the 130-byte
  hello cap and closes with `FrameTooLarge` (3), as today, except for the
  resume opening of S§4.4 step 2.
- The resume request and its answer use the `/2` header with channel
  `0x91` (S§4.4–S§4.6).

### S§5.2 Channel values and directions

| Value | Channel | Payload | Codec the caller picks |
|---|---|---|---|
| `0x00` | `Channel::Lane0` | lane-0 intents/deltas | `crpg_net::codec` or `codec_v2`, as the hello's wire version already fixes for the connection |
| `0x81` | `Channel::Transfer` | snapshot-transfer frames | `crpg_net::codec_transfer` (`TRANSFER_VERSION = 0x81`) |
| `0x91` | `Channel::Resume` | resume frames: the request (upstream), the answer and tickets (downstream) | `crpg_net::codec_resume` (`RESUME_VERSION = 0x91`) |
| any other | — | — | none: the reader closes with `ProtocolViolation` (2) |

| Channel | Client → server | Server → client |
|---|---|---|
| `Lane0` | after the opening | after the opening |
| `Transfer` | after the opening | after the opening |
| `Resume` | **only** as the opening of a resume-first connection on a `bind_resumable` server; afterwards close 2 | the answer (in place of the welcome), then any time after the opening |

- The lane-0 wire version is per connection (the hello, or for a resumed
  connection the session's original hello), so there is one lane-0
  channel, not one per version. A frame cannot claim a version the
  session did not select.
- `0x81` equals `TRANSFER_VERSION` and `0x91` equals `RESUME_VERSION`, so
  each channel value names exactly one codec. A later transfer version
  (`0x82`, T024 S§5.4), a later resume version, or any other subprotocol
  needs its own channel value. That is a framing change and therefore a new
  ALPN (ADR-0025 item 2). No value is reserved here.
- The values are an explicit header field. Nothing reads the payload to
  choose, which is the T024 S§4 rule and TR1.
- Downstream, the transport does not know whether a resume answer was
  `Accepted` or `Rejected`, so it allows `0x91` frames at any time after the
  opening. "Tickets only after a welcome or an `Accepted`" (TR4) is host
  policy.

### S§5.3 Caps

| Channel | client → server (server reader cap) | server → client (client reader cap) |
|---|---|---|
| `Lane0` | 4,096 (`MAX_INTENT_FRAME_BYTES`) | 65,536 (`MAX_DELTA_FRAME_BYTES`) |
| `Transfer` | 4,096 (`MAX_UP_FRAME_BYTES`) | 65,536 (`MAX_DOWN_FRAME_BYTES`) |
| `Resume` | 4,096 (`MAX_RESUME_FRAME_BYTES`), the opening only | 65,536 (the shared direction cap, TR5) |

Every channel has the same cap in each direction, so a reader checks one
cap per direction. No new cap or limit is added. The largest transfer
frames (32,815 down, 30 up) and the largest resume frames (170 up, 148 down,
T025a S§6.4) are well inside. `crpg-net`'s resume decoders refuse anything
above 4,096 (T025a S§7); that refusal is the host's to act on.

### S§5.4 Header functions and their precedence

`channel_frame_header(channel, len, cap)`:

1. `len == 0` → `Err(FrameError::Empty)`;
2. `len > cap` or `len > 0x00FF_FFFF` → `Err(FrameError::TooLarge)`;
3. otherwise `Ok([channel.as_u8(), len bits 23–16, 15–8, 7–0])`.

So `channel_frame_header(Channel::Lane0, n, cap) == frame_header(n, cap)`
for every `n` in `1..=cap` with `cap ≤ 16,777,215`.

`parse_channel_frame_header(header, cap)`, checked in this order:

1. `Channel::from_u8(header[0])` is `None` → `Err(FrameError::UnknownChannel)`;
2. the 24-bit length is 0 → `Err(FrameError::Empty)`;
3. the length is above `cap` → `Err(FrameError::TooLarge)`;
4. otherwise `Ok((channel, len))`.

The channel is checked first, so `[0x05, 0xFF, 0xFF, 0xFF]` is
`UnknownChannel` (close code 2), not `TooLarge` (3). On `/1` the same
header is `TooLarge` (3). Both functions are direction-free: they accept
all three channels. The upstream `Resume` rule is the server reader's
(S§8.2).

Compile-time checks in `handshake.rs`:

```rust
const _: () = assert!(Channel::Transfer as u8 == crpg_net::protocol_transfer::TRANSFER_VERSION);
const _: () = assert!(Channel::Resume as u8 == crpg_net::protocol_resume::RESUME_VERSION);
const _: () = assert!(crpg_net::protocol_transfer::MAX_DOWN_FRAME_BYTES == crpg_net::protocol::MAX_DELTA_FRAME_BYTES);
const _: () = assert!(crpg_net::protocol_transfer::MAX_UP_FRAME_BYTES == crpg_net::protocol::MAX_INTENT_FRAME_BYTES);
const _: () = assert!(crpg_net::protocol_resume::MAX_RESUME_FRAME_BYTES == crpg_net::protocol::MAX_INTENT_FRAME_BYTES);
const _: () = assert!(crpg_net::protocol::MAX_DELTA_FRAME_BYTES <= 0x00FF_FFFF);
```

## S§6. Errors and the close map

### S§6.1 Error types

- `FrameError` gains `UnknownChannel`, `Display` `UnknownChannel at
  quic/frame`. `frame_header` and `parse_frame_header` never return it.
  The existing variants and texts are unchanged.
- New `ChannelSendError`, returned only by the two `try_send_channel`
  methods:
  - `ChannelUnavailable`: `Channel::Transfer` or `Channel::Resume` on a
    connection that negotiated `/1`, or `Channel::Resume` from a client on
    any connection;
  - `Send(SendError)`: the same refusal `try_send` would give, unchanged.
  - `Display`: `ChannelUnavailable at quic/channel`, `Send at
    quic/channel`. `std::error::Error`, no source.
- `SendError`, `ServerError`, `ConnectError`, `CloseReason`, `CloseCode`
  and `ServerEvent` are unchanged (S§1 items 6 and 11). The resume calls
  reuse existing variants:
  - `ServerError::InvalidWelcome` for an answer to the wrong opening, or an
    answer of 0 or more than 65,536 bytes (S§4.5);
  - `ConnectError::Handshake` for an unusable `session` or `request`
    (S§4.6 step 1);
  - `ConnectError::InvalidWelcome` for a malformed answer frame (S§4.6
    step 4).

  Only their doc comments gain a sentence.

### S§6.2 Send precedence (no close is sent)

- `QuicServer::try_send_channel(conn, channel, frame)`:
  `Send(UnknownConnection)` → `Send(NotAccepted)` → `Send(Closed(_))` →
  `ChannelUnavailable` (`Transfer` or `Resume` on `/1`) →
  `Send(EmptyFrame)` → `Send(FrameTooLarge)` (above 65,536) →
  `Send(QueueFull)` (retryable; nothing queued).
- `QuicClient::try_send_channel(channel, frame)`: `Send(Closed(_))` →
  `ChannelUnavailable` (`Resume` always; `Transfer` on `/1`) →
  `Send(EmptyFrame)` → `Send(FrameTooLarge)` (above 4,096) →
  `Send(QueueFull)`.

### S§6.3 Receive-side close map (lane frames after the opening)

Applied through `local_close` (record first, then quinn's close,
first-wins; `src/queue.rs:639-647`).

| What the reader sees on a lane stream | `/1` connection | `/2` server reader (upstream) | `/2` client reader (downstream) |
|---|---|---|---|
| header byte 0 not in `{0x00, 0x81, 0x91}` | `FrameTooLarge` (3) | `ProtocolViolation` (2), no body read | `ProtocolViolation` (2), no body read |
| header byte 0 is `0x91` | `FrameTooLarge` (3) | `ProtocolViolation` (2), no body read, whatever the length | accepted as `Resume` (cap 65,536) |
| channel accepted, length 0 | (n/a: `[00 00 00 00]` is 2) | `ProtocolViolation` (2) | `ProtocolViolation` (2) |
| length above the direction cap | `FrameTooLarge` (3) | `FrameTooLarge` (3), no body read | `FrameTooLarge` (3), no body read |
| FIN inside a header or body, `RESET_STREAM`, `STOP_SENDING` | `ProtocolViolation` (2) | `ProtocolViolation` (2) (unchanged) | `ProtocolViolation` (2) (unchanged) |
| FIN exactly at a frame boundary | clean end | clean end (unchanged) | clean end (unchanged) |

Tests: S§10 case 5 covers the server-reader column. Case 20 covers the
client-reader column, through a raw quinn server, because this crate's
server never writes a bad downstream header. The `/1` column is today's
behaviour (`tests/quic.rs`), with `/1` controls in cases 5 and 20. The
"FIN, `RESET_STREAM`, `STOP_SENDING`" and "FIN at a boundary" rows are
today's reader code, unchanged on both framings, so cases 5 and 20 test
only the FIN-inside-a-body row on `/2`.

### S§6.4 The opening close map (server, before the connection is visible)

Every row closes with the code shown, increments `refused_handshakes` by
exactly 1, and queues no notice (S§4.4).

| First frame on the lane stream | `bind`, `bind_dual`; `bind_resumable` on `/1` | `bind_resumable` on `/2` |
|---|---|---|
| a valid hello frame | hello opening (no close) | hello opening (no close) |
| `91 00 00 00` | `FrameTooLarge` (3) | `ProtocolViolation` (2) |
| `91` + length 1..=4,096 + full body | `FrameTooLarge` (3) | resume opening (no close) |
| `91` + length above 4,096 | `FrameTooLarge` (3) | `FrameTooLarge` (3), no body read |
| `91` + length 1..=4,096, FIN inside the body | `FrameTooLarge` (3) | `ProtocolViolation` (2) |
| any other non-zero byte 0 (for example `81 00 00 1E`) | `FrameTooLarge` (3) | `FrameTooLarge` (3), as today |
| `00 00 00 00` | `ProtocolViolation` (2) | `ProtocolViolation` (2), as today |
| no complete frame within `hello_timeout_ms` | `HelloTimeout` (4) | `HelloTimeout` (4) |

ALPN failures stay pre-opening: no notice, `refused_handshakes += 1` on the
server, `ConnectError::Handshake` on a `QuicClient`. Idle timeout,
transport errors, resets and I/O-thread failure keep their `CloseReason`
mapping. No close code is added; peer codes outside 0..=9 stay raw.

## S§8. Behaviour

### S§8.1 Ordering and queues

- Per connection there is still one outbound queue and one inbound queue.
  Frames on all three channels share them, and their frame/byte caps, per
  connection and host-wide. So, within a connection and a direction,
  frames arrive exactly once and in `try_send`/`try_send_channel` call
  order **across channels**. That is the single total order T024 S§11
  item 3 and TR4 need. On a resumed connection, the answer comes first and
  every frame the host queued after `accept_resume` follows it in order.
- `QueueFull` is retryable and changes nothing, whichever channel the frame
  is on. A transfer burst applies backpressure to lane-0 and resume frames
  behind it, and the reverse. This is intended: separate queues could let a
  delta overtake a `Begin`.
- A full inbound queue parks one complete frame (its channel included) and
  stops reading, as today. Frames received before a close stay drainable,
  with their channels, before `Closed` is published (invariant 7).
- `ConnectionStats` and `QueueTotals` count payload bytes and frames on
  both framings, as today. The selector byte is header, not payload. The
  welcome and the resume answer are written before the lane writer starts,
  and neither is counted in the outbound queue (as the welcome is today).

### S§8.2 Reading and writing

- On a `/1` connection the reader and writer are today's code paths. Every
  inbound frame is tagged `Channel::Lane0`; every outbound frame is a
  lane-0 frame, so its header equals `frame_header`.
- On a `/2` connection, after the opening:
  - **Server reader (upstream, cap 4,096):** if `header[0] == 0x91`, close
    with `ProtocolViolation` (2) and read no body. Otherwise use
    `parse_channel_frame_header(header, 4_096)` and map `UnknownChannel`
    and `Empty` to `ProtocolViolation` (2), `TooLarge` to
    `FrameTooLarge` (3).
  - **Client reader (downstream, cap 65,536):**
    `parse_channel_frame_header(header, 65_536)` with the same mapping. All
    three channels are accepted.
  - The writer frames with `channel_frame_header`. The body is allocated
    only after the header is accepted.

### S§8.3 Legacy entry points (views)

`try_send`, `try_recv`, `ServerLane`, the `Transport` impls and
`poll_event` stay views. A lane-0-only or event-only caller can never see
or send transfer or resume bytes, and can never take a resume notice:

- `try_send(frame)` is `try_send_channel(Lane0, frame)`, with
  `Send(e)` returned as `e` (`ChannelUnavailable` cannot occur for
  `Lane0`).
- `try_recv()`: if the head inbound frame is on `Lane0`, it is popped and
  returned as today. If it is on `Transfer` or `Resume`, `try_recv`
  returns `Ok(None)` and leaves it queued; only `try_recv_channel` can take
  it. While such a frame is at the head, `try_recv` never reports
  `Closed`, and `wait` still returns `true`, because a frame is queued.
  Callers on `/2` use the `_channel` methods (T024h2 does).
- `poll_event()`: if the head notice is an `Event`, it is popped and
  returned as today (including the slot release on `Closed`). If it is a
  `Resume`, `poll_event` returns `None` and leaves it; only `poll_notice`
  can take it. `wait` still returns `true`. A `bind` or `bind_dual` server
  never queues a `Resume` notice, so on those servers `poll_event` is
  exactly today's.
- On a `/1` connection, and on a `bind` server, the legacy methods behave
  exactly as today.

### S§8.4 What the crate never does

It never:

- decodes a payload, a resume request or a resume answer, and never infers
  a channel from payload bytes;
- mints, checks or tracks a transfer id, cursor, epoch, fence or proof;
- authenticates a resume request or looks up a session or invitation;
- sends `Published`, `Resync`, `Cancel`, a resume answer or a ticket on its
  own.

Those belong to `crpg-net` (T024, T025a) and `crpg-server` (T024h, T025b).

### S§8.5 Notices

- A `QuicServer` has one notice queue. `poll_notice` returns every notice
  in queue order. A connection's opening notice (`Event(HelloReceived)` or
  `Resume`) always precedes its `Event(Closed)`, and `Closed` is queued
  exactly once for every connection that produced an opening notice.
- Polling `Event(Closed { conn, .. })` through either `poll_notice` or
  `poll_event` releases `conn`'s slot and forgets the record under today's
  rules (`src/server.rs:239-258`).
- Notices are bounded as events are today: each visible connection holds a
  slot until its `Closed` is polled, and there are at most two notices per
  slot.

## S§9. What T024h2 and T025b do with this (the adapter boundary)

`QuicHost` lives in `crpg-server`, so this task does not change it. The
rules below are inputs to [T024h2](T024h.md) and T025b, and the contracts
state them the same way.

T024h2 (transfer channel):

1. The operator binds the server with `bind_dual` to accept `/2` peers.
   `QuicHost::start` takes a `bind` or `bind_dual` server. A
   `bind_resumable` server must not be given to an adapter that polls only
   `poll_event`, because it would stop at the first resume notice (S§8.3).
2. On `HelloReceived`, the adapter reads `framing(conn)`. A `V2` connection
   is bound as a snapshot session, a `V1` connection as today.
3. Drain uses `try_recv_channel`. `Lane0` frames go to `Host::ingest` with
   today's one-frame hold. `Transfer` frames go to `Host::ingest_transfer`.
   A held lane-0 frame stops the drain, so a transfer frame behind it waits
   in this crate's queue and the order holds. `Channel::Resume` never
   arrives on the server (S§8.2), but `Channel` has three values, so the
   adapter's `match` needs a third arm (S§16 F2).
4. Deliver sends each host delivery entry with `try_send_channel`, on
   `Lane0` for a delta and `Transfer` for a transfer frame, in host order,
   on the one shared queue. The one-frame hold, the slow-consumer fence and
   every close path stay per connection.
5. A `/1` connection's narrowing still fences: it has no transfer channel.

T025b (resume):

6. Bind with `bind_resumable` and drive events with `poll_notice` only.
7. On `ServerNotice::Resume(r)`, decode `r.request` with
   `crpg_net::codec_resume::decode_request` and make the T025a H3 checks:
   the proof by `ct_eq` against the proof issued for that session, grace
   not expired, and the session's invitation still registered and not
   revoked. Then resolve the decision (T025a H4).
8. Send the encoded `ResumeResult` with `accept_resume(r.conn, &bytes)`.
   For `Rejected`, follow it with `close(r.conn, code, Flush)`. Or use
   `refuse(r.conn, code)` when no answer is to be sent. Then run H5 on the
   accepted connection, which is an ordinary `/2` connection
   (`try_send_channel`, `try_recv_channel`).
9. Tickets go out as `try_send_channel(conn, Channel::Resume, ticket)`
   after a welcome or an `Accepted` (TR4, H7).

    - **`NotPending` before `InvalidWelcome`.** Now that `R` is accepted,
      `accept_resume(R, b"x")`, `accept_resume(R, b"")`,
      `accept(R, Welcome { wire_version: 2, .. })` (the wrong opening) and
      `refuse(R, ServerBusy)` each return `NotPending`. `accept(H,
      Welcome { wire_version: 2, .. })` is `Ok`, and then
      `accept_resume(H, b"")` (the wrong opening and an empty answer) is
      `NotPending`.
    - **`Closed` before `NotPending` and `InvalidWelcome`.** A second
      resume opening `R2`: `refuse(R2, ServerBusy)` is `Ok`. Its client gets
      `Err(Refused { code: 7 })`. Before the `Closed` is polled,
      `accept_resume(R2, b"x")`, `accept_resume(R2, b"")` and `accept(R2,
      Welcome { wire_version: 2, .. })` each return
      `Err(Closed(Local(ServerBusy)))`. A second `/2` hello opening `H2`,
      refused with `ServerBusy`, gives the same error for
      `accept_resume(H2, b"x")`. After `close(R, Normal, Discard)` on the
      accepted `R`, and before its `Closed` is polled, `accept_resume(R,
      b"x")` is `Err(Closed(Local(Normal)))`, not `NotPending`.
    - The notices for `R2` are `Resume(R2)`, then `Event(Closed { R2,
      Local(ServerBusy) })`.
    - **`UnknownConnection` first.** Once `R2`'s `Closed` is polled (its
      record is released but still stored, `src/server.rs:592-595`),
      `accept_resume(R2, b"x")`, `accept_resume(R2, b"")` and `accept(R2,
      Welcome { wire_version: 2, .. })` each return `UnknownConnection`, not
      `Closed`. So does `accept_resume(f, b"x")` for `f = forgotten(server,
      /2)`.
    - On a server with `decision_timeout_ms = 200`, a resume opening left
      unanswered gives `Resume(r)`, then `Event(Closed { r.conn,
      Local(AuthTimeout) })`, and its client gets `Err(Refused { code: 8
      })`.

    *Fails if* a welcome can answer a resume opening (or the reverse), the
    answer cap is not 65,536, the decision timer skips resume openings, or
    any two of the four S§4.5 checks (`UnknownConnection`, `Closed`,
    `NotPending`, `InvalidWelcome`) swap places in `accept_resume` or, on a
    resume opening, in `accept`.
17. `resume_answer_then_close_reaches_client`: for `(l6_denied(),
    AuthRefused)` and `(l7_busy(), ServerBusy)` in turn, on a
    `bind_resumable` server, a `connect_resume_async` opening `R` is
    answered with `accept_resume(R, &answer)` and then
    `close(R, code, Flush)`.
    - The client's call returns `Ok((client, got))` with `got == answer`.
    - The client's `try_recv_channel` (guarded) then returns
      `Err(Peer { code })` with the code's number.
    - The server's notices are `Resume(R)`, then
      `Event(Closed { R, Local(code) })`.

    Control: `refuse(R, AuthRefused)` with no `accept_resume` gives the
    client `Err(Refused { code: 5 })` and no answer.
    *Fails if* the close overtakes the answer or `Flush` drops it.
18. `resume_channel_direction_rules`:
    - On a `/2` hello connection (`bind_dual`), the server's
      `try_send_channel(conn, Resume, b"tk")` is `Ok`, and the client's
      `try_recv_channel` returns `(Resume, b"tk")`.
    - The client's `try_send_channel(Resume, b"x")` is
      `Err(ChannelUnavailable)` on a `/2` hello connection, on a resumed
      connection (from `bind_resumable`) and on a `/1` connection. With an
      empty frame it is also `ChannelUnavailable` (before `EmptyFrame`).
      Stats are unchanged each time.
    - On the server's `/1` connection, `try_send_channel(conn, Resume,
      b"x")` and the same call with an empty frame are both
      `Err(ChannelUnavailable)`.
    - Control: `Lane0` sends succeed on every one of these connections.

    *Fails if* a client can send `0x91` after the opening or `/1` carries
    `Resume`.
19. `notices_keep_one_order`: on a `bind_resumable` server, three openings
    in sequence, each waited for with `until(totals().pending == n)`: a `/2`
    hello `A`, a resume `R`, then a `/1` hello `C`.
    - `poll_event()` returns `HelloReceived { conn: A, .. }`.
    - Then `poll_event()` is `None` while `server.wait(Duration::ZERO)` is
      `true`.
    - `poll_notice()` returns `Resume(R)`.
    - `poll_event()` returns `HelloReceived { conn: C, .. }`.

    After `refuse(R, ServerBusy)`, `poll_event()` returns
    `Closed { conn: R, .. }`, and `totals().connections` drops by exactly 1
    when it is polled. Control: on a `bind` server, `poll_notice()` returns
    `Event(HelloReceived)` and later `Event(Closed)` for one `/1`
    connection, and `poll_event()` sees nothing after them.
    *Fails if* `poll_event` returns or skips a resume notice, or notices
    use two queues.
20. `v2_client_reader_close_codes` (raw quinn server): the client-reader
    column of S§6.3. One `raw_server(&[ALPN_LANE0_V2, ALPN_LANE0_V1])`, and
    one new client connection per probe.
    - **Setup per probe.** `connect_framed_async(.., &hello(1), V2)`. The
      raw server reads the hello frame (the 4-byte header, then the length
      it declares) and writes `00 00 00 11` + `Welcome { wire_version: 1,
      epoch: epoch(7) }.encode()`. The client's call returns `Ok` with
      `framing() == V2`. The raw server then writes `00 00 00 02 61 62`,
      `81 00 00 03 78 79 7A`, `91 00 00 01 74`, then the probe, and keeps
      the stream open unless the row says FIN.
    - **Probes:**
      - `x 00 00 01` for each `x` in `{01, 02, 80, 82, 90, 92, FF}` → 2;
      - `05 FF FF FF` → 2 (the channel comes before the length);
      - `00 00 00 00`, `81 00 00 00` and `91 00 00 00` → 2;
      - `00 01 00 01`, `81 01 00 01` and `91 01 00 01`, each with nothing
        after → 3;
      - `91 00 00 05` + `41 42` + FIN → 2.
    - **Each time,** the client's guarded `try_recv_channel` returns
      `(Lane0, b"ab")`, `(Transfer, b"xyz")`, `(Resume, b"t")`, then
      `Err(Local(code))` with the row's code, and the raw server's
      `closed_code(conn)` is `Some(code)`. A header-only row with no FIN
      can close only if the reader decides on the header alone: a reader
      that read the body first would wait past the 30 s guard.
    - **Controls:**
      - On a fresh `/2` client, `00 01 00 00`, `81 01 00 00` and `91 01 00
        00`, each followed by 65,536 `pattern` bytes, arrive whole and in
        order with their channels. Only after the client has drained all
        three does the raw server close with code 0 (an earlier close could
        discard unsent stream data), and the client then reports
        `Err(Peer { code: 0 })`.
      - A `/1` client (`connect`) on the same raw server reads `00 00 00
        02 61 62` as `(Lane0, b"ab")`, and then `81 00 00 1E` closes it
        with 3. On a second `/1` client, `91 00 00 01` also closes with 3.

    *Fails if* the client reader maps an unknown channel to 3, refuses a
    downstream `0x91`, reads a body before it checks the header, applies
    the 4,096 upstream cap downstream, or changes the `/1` reader.
21. `connect_resume_answer_checks_and_timeout` (raw quinn server): the
    S§4.6 steps 3–4 that this crate's server never produces. One
    `raw_server(&[ALPN_LANE0_V2])`, and one `connect_resume_async(..,
    SESSION, &l1_request())` per row.
    - **Request bytes (every row).** The raw server reads exactly 44
      bytes: `91 00 00 28` followed by `l1_request()`.
    - **Malformed answers.** Each answer below makes the call return
      `Err(ConnectError::InvalidWelcome)`, and the raw server's
      `closed_code(conn)` is `Some(2)`:
      - `00 00 00 11` + 17 welcome bytes (a welcome is not an answer);
      - `81 00 00 01 00` and `05 00 00 01 00` (byte 0 is not `0x91`);
      - `91 00 00 00` (length 0);
      - `91 01 00 01` with nothing after, the stream held open (above
        65,536; no body read, or the call would end `TimedOut` instead);
      - `91 00 00 05` + `41 42` + FIN (a body cut short).
    - **Control.** The answer `91 00 00 02 78 79` gives `Ok((client,
      b"xy"))` with `framing() == V2` and `welcome() == SESSION`. The raw
      server then writes `00 00 00 01 7A`, and the client's
      `try_recv_channel` returns `(Lane0, b"z")`.
    - **Timeout.** With `ClientLimits { connect_timeout_ms: 300, ..v1 }`,
      the raw server reads the 44 request bytes and then writes nothing,
      with the stream held open. The call returns `Err(TimedOut)`, and the
      raw server's `closed_code(conn)` is `Some(0)` (the client's
      `finish_endpoint` close with `Normal`, `src/client.rs:414-417`).

    *Fails if* the request gets a `/1` header, the answer's header check
    is skipped or reads a body first, a short body is accepted, or the
    answer is read outside `connect_timeout_ms`.

## S§16. Amendment readings and follow-ups

T025a S§20 and this contract agree on TR1–TR6. Where T025a left a point
open or the two contracts could be read two ways, this amendment takes the
reading below. None needs a new user decision, so there are **no new open
questions**. A reviewer who disagrees with a reading should raise it; the
user is asked only then (D39).

- **R1, opt-in resume (`bind_resumable`).** T025a Q2 did not say whether
  `bind_dual` takes resume openings. Here it does not, for two reasons.
  First, `crpg-server`'s pump drains `poll_event` until `None`, and with a
  resume notice at the head it would stop there for good (S§1 item 11).
  Second, it follows D39b Q1's opt-in rule. The cost is one more
  constructor.
- **R2, TR6 "its own poll method or event type".** Both are provided: a
  `poll_notice` method and a `ServerNotice` enum. They form one queue with
  `poll_event` as a view. Two queues would let a resume connection's
  `Closed` overtake its arrival.
- **R3, TR3 "after a `Rejected` it closes".** The transport does not know
  `Accepted` from `Rejected`. Closing after an answer is the host's
  `close(.., Flush)`, and TR4's "tickets after a welcome or an `Accepted`"
  is host policy (S§5.2).
- **R4, ADR numbers.** T025a S§26 Q9 says "the next free number when
  filed: 0032 if T024q's 0030 and T024h's 0031 are filed first". The
  landing order puts T025a1 first, so "next free" would give T025a 0030.
  This contract keeps D39b's ADR-0030. T025a's ADR should be 0032 as D39d
  Q9 lists, whatever the landing order (F1).
- **R5, `connect_resume` takes the session's `Welcome`.** This keeps
  `QuicClient::welcome()` truthful without changing its signature. The
  transport cannot verify the welcome; the client checks the answer
  (T025a C4).
