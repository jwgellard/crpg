# T138 — encounter mode and real-time policy; history v2 (`crpg-sim`)

## Task
ADR-0029 Follow-on 5 (`docs/adr/0029-kernel-range-and-time-model.md:484`):
the per-encounter mode and the real-time (RT) policy, items T1–T16
(`:179–277`), and history v2, item N5 (`:347–349`). It consumes the T136a
fields on this branch: `Ruleset.round_ticks`
(`crates/crpg-data/src/combat.rs:245–247`), `Ability.recovery_ticks` and
`Ability.repeats_in_real_time` (`:318–323`). Data rejects a zero value for
either (`:774–776`, `:821–823`). D31i fixes the meaning: an absent repeat
flag and `false` mean the same thing.

## Crate(s)
**`crpg-sim` only.** The work is two packages run one after the other,
T138a and T138b (see "Size budget"). Three companion packages, T138c, T138d
and T138e, each one crate, must land in the same batch. Adding enum
variants breaks exhaustive `match`es in `crpg-script`, `crpg-server` and
`crpg-net`'s tests ("Companion packages"). **S-set:** the `World` struct and
the tick order. Serialized, human-reviewed.

## Decision
- **D1. Mode is one `EncounterMode` field on `CombatState`.** It defaults to
  `TurnBased` and is omitted from JSON when turn-based (T1). *Rejected:* a
  mode per World, area or campaign, and a host-held mode (ADR alternatives:
  ADR-0013 Decision 1 requires a behaviour-changing mode to be hashed).
- **D2. RT capability and the clock are one `Option<EncounterClock>` on
  `CombatState`.** `None` means TB-only. *Rejected:* `round_ticks` inside
  `CombatDefinition`, whose serializer is hand-written (`combat.rs:391–424`)
  and has a legacy-shape test. Also rejected: a `clock: u64` skipped at 0,
  because then "RT-capable at clock 0" and "TB-only" would encode the same.
- **D3. The initial mode comes in through a new
  `start_encounter_in_mode(world, spec, mode)`.** `start_encounter` keeps
  its signature and means turn-based (T11). *Rejected:* a field on
  `EncounterSpec`. Struct literals of that type sit in `crpg-cli/src/combat_apply.rs:159`, two
  `crpg-net` tests, two `crpg-script` tests and two `crpg-testkit` supports,
  so a field would turn four more crates into companions.
- **D4. The clock is bounded by `RT_CLOCK_MAX = 2_147_483_647`
  (`i32::MAX`, the largest `InitiativeKey`, `timeline.rs:25`), and it
  freezes there.** The tick that reaches the bound does nothing else. After
  that, stages 2 and 3 do nothing at all. No key wraps, reorders or becomes
  due early (T5). *Rejected:* letting stage 3 run while saturated, as
  draft A does. A re-key saturates to the bound, which is at or below the
  clock, so the actor is due on every tick: that fails open. Also rejected:
  a `ClockExhausted` error, because `tick` returns `()`.
- **D5. One legality source.** In RT, `validate_action` replaces only its
  turn stage. `UseAbility` and `Stop` get a terminal gate, `EndTurn` gets
  `WrongMode`, and `Stop` in TB gets `WrongMode`. Order admission and due
  execution both call `validate_action` unchanged (`crates/crpg-sim/AGENTS.md`
  invariant 12). *Rejected:* a second RT predicate, and admission without the
  affordability check (open question 3).
- **D6. `Stop { actor }` is a `CombatAction` variant.** This lets
  `legal_actions` list it and scripts propose it. *Rejected:* a free
  `stop_order`, which would need its own admission path and could not be
  listed. Cost: companion packages T138c and T138d.
- **D7. `request_mode(world, mode)` is a free function, not a
  `CombatAction`.** A mode request has no actor, and AI enumeration must not
  offer it (T9). *Rejected:* a `RequestMode` action variant.
- **D8. RT is executed by a new stage-2 clock step plus the filled stage-3
  `timeline_system` body.** Both use one `resolve_use` extracted unchanged
  from `perform_action` (T6, T7). *Rejected:* a second
  resolution/cost/damage/effect pipeline.
- **D9. A pending switch replaces the round-start schedule of its boundary.**
  The switch is not applied after the schedule, which would refresh twice in
  that round (T10). RT→TB runs the TB round start. TB→RT runs the RT round
  start. *Rejected:* applying a switch immediately (ADR alternatives, open
  question 1 of the ADR).
- **D10. `RoundStarted` is journaled exactly when a round starts in RT:**
  at each steady RT boundary and at a TB→RT switch, never at RT→TB or a TB
  rollover. A TB round is announced by `TurnStarted`, as it is today.
  *Rejected:* journaling every round, which moves every TB history golden.
  Also rejected: journaling `RoundStarted` at RT→TB, because that round
  starts in TB.
- **D11. `OrderEnded` is journaled only when a due order fails validation
  and the sim clears it** (T7, literally). A completed one-shot order is
  shown by its `ActionResolved`. `Stop` and replacement are the caller's own
  commands. The RT→TB clear is implied by `ModeChanged`, and a dead holder's
  order by `Died`. *Rejected:* journaling every `Some → None` transition
  (open question 1).
- **D12. Ability RT fields.** `AbilityDefinition` gains
  `recovery_ticks: Option<u32>` (the authored value, resolved when used) and
  `repeats_in_real_time: bool` (skipped when false, D31i). Both are
  `None`/`false` in a TB-only encounter, whatever the author wrote, because
  T2 requires every new field to be absent in TB-only worlds. *Rejected:*
  copying the authored values as dormant data in TB-only encounters, and
  keeping `Option<bool>`, where `Some(false)` and `None` would hash
  differently for the same meaning.
- **D13. `ability_is_legacy` (`combat.rs:303–310`) also requires
  `recovery_ticks == None && !repeats_in_real_time`.** Without this, a
  single-ability RT-capable encounter would serialize in the legacy shape,
  which drops the vectors. A save and reload would then lose the RT fields
  and change behaviour. Both drafts missed this.
- **D14. An `OnTick(p)` pool is refreshed by the encounter clock.** It gets
  one `RefreshEvent::Tick(Tick::new(new - new % p))` per clock advance
  `old → new` with `new / p > old / p`, in RT and across TB rollover jumps.
  The tick passed is the last multiple crossed, because the kernel matches
  only `count > 0 && count % period == 0` (`crpg-rules/src/resource.rs:211–214`).
  *Rejected:* `Tick(new)`, as draft A proposes. It never refreshes when a TB
  jump crosses a multiple without landing on one.
- **D15. RT terminal is derived: fewer than two non-dead combatants.**
  `active` is always `None` in RT. RT actions and `Stop` are then rejected
  with the TB terminal error, `OutOfTurn { actor, active: None }`.
  *Rejected:* a new `EncounterOver` variant, and a stored terminal flag.
- **D16. History version is lazy and sticky.** A wrapper starts at 1. It
  becomes 2 at the first commit whose staged world holds an RT-capable
  encounter or whose events include a v2 variant. It never goes back to 1.
  *Rejected:* always writing 2, as draft A proposes. That moves both
  `history_v1` goldens and every `history_hash`, against N5 and the
  Compatibility section (`:425`).
- **D17. Load coherence lives in `World::deserialize`**, beside the existing
  combat check (`world.rs:149–522`), so an incoherent RT save fails at load
  and never at action time. *Rejected:* a new validation API.
- **D18. No hash exclusion.** New state is hashed through ordinary serde,
  using absence forms only (ADR-0009). *Rejected:* any exclusion.

## Tick order
One `tick(world)` after T138. TB, TB-only and no-encounter ticks are
byte-identical to today (ADR `:417`).

0. **Unchanged.** `advance_tick` adds one to the world tick, saturating
   (`world.rs:711`). No encounter rule reads the world tick (T3). Spec §10
   stage 1 (intents) and stage 5 (AI) run in the host between ticks, not
   here (T15).
1. **NEW, stage 2, `encounter_clock_system` → `clock_stage`.**
   a. Return unless all of these hold: `combat` is `Some`, `mode ==
      RealTime`, `rt_alive >= 2` and `elapsed < RT_CLOCK_MAX`.
   b. Set `old = elapsed` and `elapsed = old + 1`. If `elapsed ==
      RT_CLOCK_MAX`, return: the encounter freezes (D4).
   c. Call `deliver_clock_advance(old, elapsed)` (D14).
   d. If `elapsed % round_ticks != 0`, return. Otherwise this is the
      boundary: set `pending = pending_mode.take()`. If `pending ==
      Some(TurnBased)`, apply RT→TB (B25). Otherwise run `rt_round_start`
      (B13).
2. **CHANGED, stage 3, `timeline_system`.** The existing no-op iteration
   runs first, unchanged. Then `execution_stage` returns unless `combat` is
   `Some`, `mode == RealTime`, `rt_alive >= 2` and `elapsed < RT_CLOCK_MAX`.
   After an RT→TB switch in step 1 the mode is TB, so nothing runs.
   Otherwise the due snapshot is processed (B14–B18).

Outside `tick` (CHANGED, T4 policy kept): the TB rollover branch of
`advance_tracked` (`:2158–2216`) does this when `clock` is `Some`:
set `old = elapsed` and `elapsed = min(old + round_ticks, RT_CLOCK_MAX)`;
call `deliver_clock_advance(old, elapsed)`; then, if
`pending_mode.take() == Some(RealTime)`, apply TB→RT (B26), otherwise run
`tb_round_start`. When `clock` is `None`, the branch is exactly today's
code. `end_turn` (`tick.rs:33–36`) is untouched.

## Hash and history
Each new value is hashed by `state_hash`'s full-`World` serde
(`hash.rs:37–49`). The code of `state_hash` does not change, and nothing is
excluded.

| Value | JSON key and encoding | Present when |
|---|---|---|
| `CombatState.mode` | `"mode":"real_time"` (`"turn_based"` is never written) | `RealTime` |
| `CombatState.clock` | `"clock":{"round_ticks":<u32>,"elapsed":<u64>}` | RT-capable |
| `CombatState.pending_mode` | `"pending_mode":"turn_based"` or `"real_time"` | `Some` |
| `Combatant.order` | `"order":{"ability":"<ULID>","target":{"index":<u32>,"generation":<u32>},"repeat":<bool>}` | `Some` |
| `AbilityDefinition.recovery_ticks` | `"recovery_ticks":<u32>` | `Some` |
| `AbilityDefinition.repeats_in_real_time` | `"repeats_in_real_time":true` | `true` |

A TB-only `CombatState` therefore still writes exactly
`{"definition":…,"round":…,"active":…}`, and a TB-only combatant's keys do
not change. Absence is a compatibility shape, not an exclusion. An RT
`CombatState` writes `"active":null`.

**History v2 (T138b).** The new events use the existing adjacent tags,
with `type` written before `value`. Payload field order is the order in the
table below. On input, payload keys may come in any order, but a duplicate,
unknown or missing key fails. Each new payload has a manual visitor, as in
`history.rs:1117–1244`; `order_ended` uses its own `actor` visitor and not
`EntityRef`.
```json
{"type":"round_started","value":{"round":3}}
{"type":"mode_changed","value":{"mode":"real_time","round":3}}
{"type":"order_ended","value":{"actor":{"index":1,"generation":1}}}
```
**Version 1 still decodes.** The loader (`:1446–1448`) accepts `version` 1
or 2. Any other value fails with `unknown history version`. Payloads decode
with both vocabularies, whatever the version, because `version` may follow
`pending` on input. After all keys are read, a version-1 wrapper is rejected
if any retained payload is a v2 variant (`history v1 journal holds a v2
event`) or if its world holds `combat.clock: Some`
(`history v1 wrapper holds a real-time-capable encounter`). Every input
that is valid today decodes, re-encodes and hashes exactly as today.

## Behaviour
"Alive" means a combatant with `dead == false`. A boundary is the tick at
which `elapsed % round_ticks == 0` after stage-2 step b. The items are for
T138a unless marked (T138b).

1. **B1 (T1).** `CombatState.mode` is the only mode in the crate. Nothing
   on `World`, an area or a campaign holds a mode, and outside an encounter
   no mode exists. `end_encounter` drops the mode, clock and pending mode
   along with the state.
2. **B2 (T1).** A terminal encounter keeps `mode` and `pending_mode` until
   it is released. Becoming terminal never rewrites either.
3. **B3 (T2).** On publication, `clock` is `Some(EncounterClock {
   round_ticks: n, elapsed: 0 })` exactly when `ruleset.round_ticks ==
   Some(n)`, and otherwise `None`. If the encounter is RT-capable, each
   `AbilityDefinition` copies the authored `recovery_ticks` and takes
   `repeats_in_real_time` as `unwrap_or(false)`. If it is TB-only, they are
   `None` and `false` whatever was authored. `pending_mode` starts `None`.
4. **B4 (T2).** `start_encounter_in_mode(.., RealTime)` on a TB-only ruleset
   returns `ModeUnsupported`. The check order is `EncounterActive`, then
   `ModeUnsupported`, then the existing order from `TooManyParticipants`
   onward. Nothing changes: no entity, no event, no RNG stream, no interner
   entry.
5. **B5 (T2).** These are data-owned preconditions, asserted after the
   existing asserts (`combat.rs:955–960`).
   `ruleset.round_ticks == Some(0)` panics with `ruleset round_ticks is
   validated nonzero by data read-time checks`. In an RT-capable encounter,
   an ability with `recovery_ticks == Some(0)` panics with `ability
   recovery_ticks is validated nonzero by data read-time checks`. No
   `CombatError` covers either.
6. **B6 (T2).** A TB-only world contains none of these keys: `"mode"`,
   `"clock"`, `"pending_mode"`, `"order"`, `"recovery_ticks"`,
   `"repeats_in_real_time"`. Its bytes, `state_hash` and `history_hash`
   match the pre-T138 build, and every existing golden passes unedited.
7. **B7 (T2, D13).** A single-ability, single-pool, effect-free RT-capable
   encounter whose ability declares `recovery_ticks` or a `true` repeat flag
   serializes the `abilities`/`pools`/`effects` vectors. Save then load
   gives an equal `World`. Without either field the legacy shape is
   unchanged.
8. **B8 (T3).** In RT, `elapsed` grows by exactly 1 per tick while the
   encounter is alive and below the bound. At a TB rollover of an
   RT-capable encounter it grows by `min(round_ticks, RT_CLOCK_MAX -
   elapsed)`. It never changes otherwise: not in TB between rollovers, not
   in a terminal RT encounter, and not in a TB-only encounter, which has no
   clock.
9. **B9 (T3, D14).** For each clock advance `old → new`, every pool
   (primary first, then extras in template order) of every alive combatant
   (in ascending `EntityId`) whose trigger is `OnTick(p)` gets exactly one
   `refresh(RefreshEvent::Tick(Tick::new(new - new % p)))` when `new / p >
   old / p`, and nothing otherwise. TB-only encounters deliver nothing, as
   today. With `round_ticks = 120`, an `OnTick(120)` pool refreshes once per
   RT round and once per TB rollover.
10. **B10 (T4).** In TB, TB-only and RT-capable encounters behave as today:
    one entry per alive combatant at authored initiative, the head acts, an
    accepted turn-ending action pops it, and an empty timeline with two or
    more alive rolls the round over. The only difference in an RT-capable
    TB fight is B8 and B9.
11. **B11 (T5).** In RT, the timeline holds exactly one entry for each
    alive combatant and nothing else. The key is `0` after an RT start, the
    current `elapsed` after a TB→RT switch, and `min(elapsed + recovery,
    RT_CLOCK_MAX)` after an execution, where `recovery =
    recovery_ticks.unwrap_or(round_ticks)`. Keys lie in `0..=i32::MAX` and
    are built with `i32::try_from(..).expect(..)`. Recovery is a key and
    never a refresh.
12. **B12 (T5, D4).** The tick that makes `elapsed == RT_CLOCK_MAX` does
    nothing else: no `OnTick` delivery, no boundary, no execution. Every
    later tick changes nothing in the encounter. The world tick still
    advances. Keys never wrap, never reorder and are never re-keyed.
    Commands, mode requests, `despawn` and `end_encounter` still apply.
13. **B13 (T6).** At a boundary with `pending != Some(TurnBased)`,
    `rt_round_start` sets `round = round.saturating_add(1)`. Then, for every
    alive combatant in ascending `EntityId`, it refreshes `RoundStart` and
    then `TurnStart` (primary first, then extras). Then every combatant
    keeps only the attachments with `expires_round > round` (as
    `combat.rs:2178–2180`). `active` stays `None`. Clock 0, a terminal
    encounter and a frozen clock never produce a boundary.
14. **B14 (T7).** Stage 3 collects every entry with key `<= elapsed`, in
    ascending `(key, EntityId)`, **before** acting. Entries re-keyed during
    the pass never join it, so each combatant acts at most once per tick
    (recovery is at least 1).
15. **B15 (T7).** For each due entry in order: stop if `rt_alive < 2`. Skip
    the entry if it is no longer an alive scheduled combatant, or if its
    `order` is `None` (B17). Validate `UseAbility { actor, ability, target }`
    with `validate_action` (D5). If it is valid, call `resolve_use`, the
    same resolution, `combat.roll` stream, roll tag, costs, damage,
    exactly-once `Died` and effect attachment as TB. Then remove every dead
    combatant from the timeline and clear its order without an event. If
    the actor is alive, re-key it (B11) and clear a non-repeating order
    without an event; a repeating order stays. `ends_turn` is ignored in RT.
16. **B16 (T7).** A due order that fails validation (any `CombatError`,
    `InsufficientAction` included) is set to `None`. It causes no spend,
    draw, damage, effect or re-key, so the entry stays due. In T138b it
    records `TickEvent::OrderEnded { actor }` (D11).
17. **B17 (T7).** A due combatant without an order keeps its key. It acts on
    the first tick after it receives an order, provided it is still due.
18. **B18 (T7, D15).** RT terminal means `rt_alive < 2`. When an execution
    makes the encounter terminal, the pass stops at once. Later ticks change
    nothing in the encounter until it is released. An RT encounter published
    with fewer than two participants is terminal from the start.
19. **B19 (T8).** In RT, `perform_action(UseAbility)` runs `validate_action`
    in this order: `NoEncounter`, nonparticipant actor, nonparticipant
    target, `AbsentActor`, `AbsentTarget`, `DeadActor`, `DeadTarget`, the
    terminal gate (`OutOfTurn { actor, active: None }`), `UnknownAbility`,
    `SelfTarget`, then affordability as today. When the actor's key is not
    due, affordability is checked against current balances. On success it
    stores `StandingOrder { ability, target, repeat:
    entry.repeats_in_real_time }`, replacing any order, and returns
    `Ok(None)`. It changes no key, pool, RNG stream, event or interner
    entry.
20. **B20 (T8).** `Stop { actor }` validates in this order: `NoEncounter`,
    nonparticipant actor, `AbsentActor`, `DeadActor`, then `WrongMode {
    mode: TurnBased }` in TB or the terminal gate in RT. On success it sets
    `order = None` and returns `Ok(None)`. `Stop` without an order is an
    accepted no-op.
21. **B21 (T8).** In RT, `EndTurn` fails `WrongMode { mode: RealTime }` at
    the stage where TB checks `OutOfTurn`. In TB, `UseAbility` and `EndTurn`
    behave exactly as today. A TB combatant never holds an order, whether
    after start, after a switch or after loading.
22. **B22 (T8, T15).** RT `legal_actions(actor)` first validates
    `Stop { actor }`; a failure returns `Actor(error)`. It then lists every
    `UseAbility` that `validate_action` accepts, over abilities in ascending
    ULID × combatants in ascending `EntityId`, and then `Stop { actor }`.
    It never lists `EndTurn`. `MAX_LEGAL_ACTIONS` counts `Stop`, and an
    overflow still fails whole (`TooManyOptions`). TB enumeration is
    unchanged and never lists `Stop`. The query does not mutate anything,
    intern anything or touch the RNG.
23. **B23 (T9).** `request_mode(mode)` checks, in order: `NoEncounter`; then
    `ModeUnsupported` if `mode == RealTime` and `clock` is `None`. Then, if
    `mode == state.mode`, it sets `pending_mode = None`; otherwise it sets
    `pending_mode = Some(mode)`, replacing any earlier request. It changes
    nothing else and emits nothing. Requesting `TurnBased` with an active
    encounter is always `Ok`. Invariant: `pending_mode != Some(mode)`.
24. **B24 (T9).** A pending switch applies only at an RT boundary (RT→TB) or
    at a TB rollover (TB→RT). It never applies mid-round or in a terminal
    encounter, where it stays hashed until release.
25. **B25 (T10).** RT→TB at a boundary: every order becomes `None`, `mode =
    TurnBased`, then `tb_round_start` runs. That is `round + 1`
    (saturating), `RoundStart` for every alive combatant, attachment expiry,
    every alive combatant re-inserted at its stored initiative (the insert
    replaces its RT entry), one `TurnStart` for the head, and `active =
    Some(head)`. There is no RT refresh in that round. In T138b this
    records `mode_changed = (TurnBased, round)` and `turn_started = (head,
    round)`, and no `round_started`.
26. **B26 (T10).** TB→RT at a TB rollover, after B8's clock advance and
    B9's deliveries: `mode = RealTime`, every alive combatant is inserted at
    key `elapsed`, `active = None`, then `rt_round_start` runs (B13). There
    is no TB refresh and no `TurnStart` fact. In T138b this records
    `mode_changed = (RealTime, round)` and `round_started = round`.
27. **B27 (T10).** In every round, in either mode and however the mode is
    toggled, each alive combatant's `OnRoundStart` pools refresh exactly
    once. Its `OnTurnStart` pools refresh once per round in RT, and once per
    turn it heads in TB.
28. **B28 (T11).** The sim never chooses a mode. `start_encounter` publishes
    TB, even on an RT-capable ruleset. `start_encounter_in_mode(..,
    RealTime)` publishes RT: every key is `0`, `active = None`, there is no
    initial `TurnStart` refresh, and `StartFacts.initial_turn = None`. A TB
    publication is exactly today's.
29. **B29 (T12).** Only combatants hold timeline entries in either mode.
    Non-participants spawned during an encounter are never keyed and never
    touched by stages 2 or 3. The host keeps ticking, so they live in real
    time beside a TB fight. Their movement belongs to T034/T036.
30. **B30 (T13).** A second start fails `EncounterActive` before
    `ModeUnsupported`. There is one encounter per `World`, and nothing new
    is a collection.
31. **B31 (T14).** No join operation is added. The join rules go to T139
    (see "Out of scope").
32. **B32 (T15).** No AI stage or AI state is added. Host AI submits
    ordinary commands between ticks, and replay never runs AI.
33. **B33 (T16, D17).** Every new value is an integer, a bool, a ULID or an
    `EntityId`; `Transform` stays the only float (`transform.rs`). Load
    rejects, with these exact messages:
    - **L1**, `clock` is `None` and:
      - `mode` is RT: `combat real-time mode without a clock`;
      - `pending_mode` is `Some`: `combat pending mode without a clock`;
      - an ability has RT fields: `combat ability carries real-time fields
        without a clock`.
    - **L2**, `clock` is `Some` and:
      - `round_ticks == 0`: `combat clock declares zero round ticks`;
      - `elapsed > RT_CLOCK_MAX`: `combat clock exceeds its bound`;
      - an ability has `recovery_ticks == Some(0)`: `combat ability declares
        zero recovery ticks`.
    - **L3**, `pending_mode == Some(mode)`: `combat pending mode equals its
      mode`.
    - **L4**, RT and:
      - `active` is `Some`: `real-time combat holds an active turn`;
      - the timeline's id set differs from the alive combatants:
        `real-time timeline disagrees with its live combatants`;
      - a negative key: `real-time timeline key is negative`.
    - **L5**, orders:
      - TB with any order: `turn-based combatant holds a standing order`;
      - a dead holder: `dead combatant holds a standing order`;
      - an unlisted ability: `standing order names an unknown ability`;
      - `repeat` differs from the ability's flag: `standing order repeat
        disagrees with its ability`.

    An order's target is not checked at load: a despawned or dead target
    fails at due time (B16).
34. **B34 (T16).** In RT, `despawn` removes the entity's entry and its order.
    It never advances turns, because RT has no `active`. Orders other
    combatants hold that target it stay until due (B16). A dead or absent
    holder never executes.
35. **B35 (T16, replay).** Two runs of one RT script (same seed, same
    commands and ticks) give equal per-tick `state_hash` sequences over
    1 000 ticks in one binary.

History (T138b):

36. **H1 (N5).** The three payloads encode exactly as shown under "Hash and
    history" and round-trip. Duplicate, unknown and missing keys fail, and
    so does `value` before `type`. An unknown `type` fails with the existing
    message.
37. **H2 (N5).** Emission order per operation:
    - **`tick`:** `ModeChanged`, `RoundStarted`, `TurnStarted` (whichever
      occurred). Then, in execution order, each `ActionResolved` followed at
      once by `Died { target }` if that action killed, and each
      `OrderEnded`. Last, one `EncounterEnded` if the pass made the
      encounter terminal. Each drained legacy `Died` is translated exactly
      once, in queue order, as the `Died` after the k-th killing
      resolution.
    - **`perform_action` and `despawn`:** keep today's order, with the
      trailing transition extended to `ModeChanged`, `RoundStarted`, then
      `TurnStarted` or `EncounterEnded`.
    - **RT `despawn`:** records `encounter_ended = (encounter, round)`
      exactly when it drops `rt_alive` from 2 or more to below 2.
    - **No events:** RT order setting, `Stop` and `request_mode`.
    - **RT start:** journals only its `Spawned` events. A TB start journals
      `Spawned` plus `TurnStarted`, as today.
38. **H3 (N5, D16).** `version()` is 1 for a new wrapper and stays 1 for
    every TB-only history. The first successful commit whose staged world
    has `combat.clock: Some(_)`, or whose events include a v2 variant, sets
    it to 2. It never returns to 1, not after release and not after
    acknowledgement. A rejected commit changes nothing.
39. **H4 (N5).** The loader rules are exactly as stated under "Hash and
    history". A version-1 wrapper that is valid today loads, re-serializes
    byte-identically and hashes unchanged.
40. **H5 (T11, T16).** `HistoryWorld::start_encounter_in_mode` and
    `request_mode` stage, run the combat function, and commit through
    `commit`. Gameplay errors win over history errors. `request_mode`
    commits zero events, so it needs no free slot or sequence.
41. **H6 (N5).** The caps apply unchanged. If a tick's events would exceed
    `MAX_HISTORY_EVENTS` or `MAX_HISTORY_BYTES`, the tick returns the
    history error and commits nothing: no clock advance, no RNG draw.
    `HistoryWorld::tick` no longer asserts that it emits no events
    (`history.rs:511–514`).

## Out of scope and hand-off
T138 stops at the sim API above. It changes no host, protocol, data or
script code beyond the three mechanical companions.
- **T137 (adapter generalization)** builds on `start_encounter_tracked(..,
  mode)`. It must extend `ability_is_legacy` (D13) for every new
  `AbilityDefinition` field. RT keys stay clock-based. An authored
  initiative spec changes only TB keys and the RT→TB rebuild ("stored
  initiative").
- **T139 (persistent state, join and leave)** owns T13 and T14:
  - TB first round: the joiner is inserted at its initiative, never ahead
    of `active`.
  - TB later rounds: the joiner enters at the next rollover.
  - RT: the joiner is keyed at `elapsed` with `order: None`.
  - T139 decides whether a join into a terminal RT encounter (D15: derived,
    so a join could revive it) is rejected. It also decides how `OnTick`
    pools refresh outside encounters, where there is no encounter clock.
- **T140 (protocol)** carries the N1 facts:
  - `mode`, `pending_mode`, `round`, `clock.elapsed`, `clock.round_ticks`,
    timeline keys, `active` (TB), and orders (default: the controlling peer
    only, N2);
  - the three events (H1);
  - the intents `DeclareAction` (TB: act; RT: `UseAbility` sets the order),
    `EndTurn`, `Stop` and `RequestMode`;
  - wire codes for `ModeUnsupported` and `WrongMode`.
- **T141 (server)** owns P1–P9. Pause stays outside `World`. The host calls
  `start_encounter_in_mode` with the session setting and `request_mode`
  with host authorization. It replaces T138d's withholding with projection,
  evaluates auto-pause from `RoundStarted`, `ModeChanged`, `OrderEnded` and
  `Died`, and runs RT AI when an entry is due (key `<= elapsed`) with
  `order() == None`. Every needed fact is public through `world()`, so no
  sim helper is added. `crpg-script`'s `EndTurn` gate (`bindings.rs:417`)
  fails in RT. RT script proposals need a later `crpg-script` task, owned
  with T141.
- **Also out of scope:** movement (T034/T036, per T12), reactions, rest,
  partial-refill exposure in data (D31h), an RT replay golden in
  `crpg-testkit` (open question 6), `crpg.ui/1`, and the spec §2.5/§10
  notes (manager edit, per ADR Consequences).

## Open questions
1. **What does `OrderEnded` cover?** *Recommend:* (a) only a due order that
   fails validation and is cleared (T7 literally, D11). (b) Also completed
   one-shot orders, which would make the single-player "order ended"
   auto-pause fire after every one-shot action.
2. **Should an unaffordable due order wait or clear?** *Recommend:* (a)
   clear, as T7 says for any invalid order. In this release that matters
   only when `recovery_ticks < round_ticks`, because a round boundary
   always falls within a default recovery. (b) Wait, with the key kept and
   no event, until it is affordable. Revisit at T141 or T034 playtesting.
3. **Does order admission check affordability?** *Recommend:* (a) yes,
   which both drafts propose. It keeps `legal_actions` honest for AI, which
   would otherwise churn unaffordable orders into `OrderEnded`. The cost:
   right after acting, a player cannot queue an order before the next
   boundary refreshes the pool. (b) Admit without the cost check and check
   only when due. Revisit with T051/T141.
4. **History versioning.** *Recommend:* (a) lazy and sticky (D16). (b)
   Always write 2, which moves both `history_v1` goldens and every
   `history_hash`.
5. **Companion packaging.** *Recommend:* (a) three single-crate packages,
   T138c–e (AGENTS.md "one task = one crate"). (b) One package across
   three crates, which would need your authorization under the T017d
   precedent.
6. **RT replay golden in `crpg-testkit`.** *Recommend:* (a) defer it to a
   testkit package after T141 has an RT host. The sim `history_v2` golden
   already covers T6–T10 per target, as the ADR's Acceptance section
   requires. (b) Add it now, as a fourth companion package.
7. **RT terminal error.** *Recommend:* (a) reuse `OutOfTurn { actor,
   active: None }` (D15). (b) Add `EncounterOver`.
