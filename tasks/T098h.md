# T098h — pin the T098g `Flush` reserve wiring with tests (`crpg-net-quic`): contract draft

## Task / Crate(s) / Purpose

Sole crate: `crpg-net-quic`. Tests only: no change under `src/`. The T098g
Claude review ran three planted mutants — (c) client `stop`, (d)
`QuicServer::close(Flush)`, (e) `shutdown` — each made to install the
`FlushRequest` with `flush_end = overall` instead of `flush_end`, i.e. to
drop the reserve (`R = min(200 ms, B/4)`, `src/teardown.rs:12-14`). All three
survived T098g tests 3, 4 and 5, because those tests only prove the close
still *goes out*, and the single `yield_now` in `finish_endpoint_close`
delivers it even at the deadline (`src/teardown.rs:47-53`). This contract
pins the wiring: three new tests, one per site, each failing when its mutant
is applied and passing on the current code. No product-code change, so the
wire format, config defaults and goldens cannot move.

Status: **draft, awaiting user approval** (it changes T098g's contract test
list, so the user approves it).

## Exact contract

### Decision

**D1. The three sites, read not inferred.**

- (c) client `QuicClient::stop`: `close_deadlines(...)` at `src/client.rs:464`
  splits the budget; the reserve enters at `src/client.rs:476`,
  `flush_end: deadlines.flush_end` inside the `FlushRequest`. The guard is
  `deadlines.overall + SYNC_GRACE` (`:481-484`) and `Stop.deadline` is
  `deadlines.overall` (`:501-504`) — both stay on `overall`.
- (d) `QuicServer::close(.., Flush)`: deadlines at `src/server.rs:623`; the
  reserve enters at `src/server.rs:627`, `flush_end: deadlines.flush_end`.
  The guard is `overall + SYNC_GRACE` (`:631-634`).
- (e) `QuicServer::shutdown`: deadlines at `src/server.rs:713`; the reserve
  enters at `src/server.rs:733`, `flush_end: deadlines.flush_end`. The guard
  is `overall + SYNC_GRACE` (`:740-743`) and `Stop.deadline` is `overall`
  (`:758-761`).

**D2. The exact mutant, one line each.** Change the `flush_end` field's
value from `deadlines.flush_end` to `deadlines.overall`:

- (c) `src/client.rs:476`
- (d) `src/server.rs:627`
- (e) `src/server.rs:733`

Nothing else changes, so `overall` and the guard keep their meaning and the
`yield_now` still runs; the flush simply occupies the whole budget.

**D3. Why tests 3/4/5 cannot kill them, and what can.** The reserve's only
observable effect is to move the flush cutoff from `overall` (= B) to
`flush_end` (= B − R) earlier. A peer that *fully* stalls (or fully drains)
makes the flush's outcome — which frames arrive, the `outbound_frames_discarded`
count, that the close is eventually seen — identical under both deadlines, so
tests 3/4/5's assertions pass on the mutant. The only thing that differs is
*when* the flush stops, and R is capped at 200 ms (`src/teardown.rs:9`), so
that difference is a wall-clock gap of at most 200 ms. The new tests therefore
assert an elapsed-time **upper bound**: with `B = 2_000` (the max,
`src/limits.rs:35`), `F = 1_800`, `R = 200`, a stalled peer makes the flush run
to its deadline, so `close`/`shutdown` returns at ≈ F (correct) vs ≈ B
(mutant). `took < B` kills the mutant deterministically and gives the correct
code the whole 200 ms reserve as its one-sided margin.

**D4. The stall is deterministic.** The peers below reuse T098g's
credit-bounded stalls, so the flush *always* runs to its deadline and the
lower bound `took >= F` is load-safe (it fails only if the stall breaks, never
if the timer fires late). The upper bound `took < B` is the load-sensitive
side: tokio `sleep_until` fires late under a descheduled test thread, so a
> 200 ms stall could push the correct code past B. That is the irreducible
flake risk of pinning a 200 ms reserve with wall clocks; it cannot be widened
without a product test hook (see Open questions). The mutant can never pass
`took < B`: `flush_end = overall` is computed from the same `Instant::now()`
taken after the test's `t0`, so `took >= B` always.

**D5. Placement.** Tests 6–8 append to `crates/crpg-net-quic/tests/close_budget.rs`,
reusing `stalled_client`, `pattern`, `epoch`, `connect_accepted`,
`bind_server`, `client_recv`, `server_recv`, `next_closed`. `B = 2_000`,
`F = 1_800`, `R = 200` are local constants with a comment citing
`src/teardown.rs:9` and `src/limits.rs:35`.

### Behaviour (observation per site)

**Site (c) — client `stop` (`src/client.rs:476`).**

1. *Elapsed upper bound on `QuicClient::close(Flush)`* (recommended). The
   T098g test-3 stalled-server shape (server never drains during the close)
   makes the client flush run the full `flush_end`, so `close` returns at ≈ F.
   Assert `took < B`. Correct ≈ 1_800; mutant ≈ 2_000. Flake: only a > 200 ms
   deschedule of the test thread can false-fail; the mutant cannot pass.
2. *Peer-side observation.* Measure on the server the instant it first reads
   `Closed(Peer{0})`, against a shared `t0`, assert `< B`. Same 200 ms gap but
   adds close-transmit latency to the correct side, so strictly less margin.
   Not recommended.
3. *Two-sided band `F <= took < F + δ`* (δ ≈ 100 ms). Pins F exactly and also
   catches a removed flush, but both sides are tight → most flaky. Not
   recommended.
4. *Discarded-count boundary.* Tune a server to drain its backlog to
   completion strictly inside `(F, B]`, then assert `outbound_frames_discarded
   == 0` (mutant) vs `>= 1` (correct). Drain rate is machine/time dependent and
   cannot be made deterministic without a hook. Rejected.

**Site (d) — `QuicServer::close(Flush)` (`src/server.rs:627`).**

1. *Elapsed upper bound on `close(Flush)`* (recommended). The test-5
   `stalled_client` (absorbs one delta frame, then its 65,540-byte windows
   stop it) makes the server flush run the full `flush_end`. Assert
   `took < B`; test 5 already asserts the load-safe `took >= 1_800`. Same
   flake profile as (c).
2. *Peer-side observation* on the stalled client (`client_recv` returns
   `Err(Peer{0})`), assert `< B` from a shared `t0`. Less margin. Not
   recommended.
3. *Two-sided band.* Not recommended.
4. *Discarded-count boundary.* Rejected (same as (c)).

**Site (e) — `shutdown` (`src/server.rs:733`).**

1. *Elapsed upper bound on `shutdown`* (recommended). The test-4 shape — one
   `stalled_client` plus one steady client — lets the steady flush finish
   early while the stalled flush pins `shutdown` to return at ≈ F. Assert
   `took < B`. Same flake profile.
2. *Per-client peer observation*: the stalled client's `client_recv` returns
   `Err(Peer{1})` at ≈ F (correct) vs ≈ B (mutant); assert `< B` from a shared
   `t0`. Less margin. Not recommended.
3. *Two-sided band.* Not recommended.
4. *Discarded-count boundary.* Rejected.

### Tests

All in `crates/crpg-net-quic/tests/close_budget.rs`. The waits are the rig's
30 s guards, never oracles. Each test records its `took` and asserts the same
pair of elapsed bounds; the upper bound `took < B` is the killer, the lower
bound `took >= F` documents that the flush ran to its cutoff. **The
implementer must, for each test, apply its mutant (D2), run the single test,
record `EXIT=101` with the failing assertion, then restore the line.**

6. **`client_flush_close_stops_at_flush_end`** (kills (c)).
   - Setup: `bind_server(ServerLimits::v1())`. `ClientLimits::v1()` with
     `close_flush_timeout_ms = 2_000`; `connect_accepted(.., epoch(1))`. Send
     `pattern(1, n, INTENT_CAP)` for n = 1..=10, `server_recv` all 10, then
     n = 11..=128 via `until("queue", ..)` (test-3 shape).
   - Run: `let t0 = Instant::now(); let report = client.close(CloseCode::Normal,
     CloseMode::Flush); let took = t0.elapsed();`
   - Assert: `took < Duration::from_millis(2_000)` (killer) and
     `took >= Duration::from_millis(1_800)`; `report.inbound_frames_discarded
     == 0`; `report.outbound_frames_discarded >= 1`; server reads prefix
     k = 11.. (k < 128) then `Err(ServerError::Closed(Peer{0}))`;
     `k + report.outbound_frames_discarded <= 128`;
     `next_closed(&mut server) == (conn, Peer{0})`.
   - Mutant: apply (c) → `took < 2_000` fails (`took ≈ 2_000`); the remaining
     assertions still pass (invariants, not killers). Record, restore.

7. **`single_close_flush_stops_at_flush_end`** (kills (d)).
   - Setup: `bind_server(ServerLimits::v1())`; one `stalled_client()` on
     `epoch(3)`; queue 8 × `pattern(3, n, DELTA_CAP)`.
   - Run: `let t0 = Instant::now(); let report = server.close(conn,
     CloseCode::Normal, CloseMode::Flush).expect("close"); let took =
     t0.elapsed();`
   - Assert: `took < Duration::from_millis(2_000)` (killer) and
     `took >= Duration::from_millis(1_800)`; `report.outbound_frames_discarded
     >= 1`; `report.inbound_frames_discarded == 0`; client reads prefix
     k < 8 then `Err(Peer{0})`; `k + report.outbound_frames_discarded <= 8`;
     `next_closed(&mut server) == (conn, Local(Normal))`.
   - Mutant: apply (d) → `took < 2_000` fails. Record, restore.

8. **`shutdown_stops_at_flush_end`** (kills (e)).
   - Setup: `bind_server(ServerLimits::v1())`; `stalled_client()` on `epoch(1)`
     and a v1 steady client on `epoch(2)`; queue 8 × `pattern(1, n, DELTA_CAP)`
     to the stalled and 3 × `pattern(2, n, 1_000)` to the steady.
   - Run: `let t0 = Instant::now(); let report = server.shutdown(); let took =
     t0.elapsed();`
   - Assert: `took < Duration::from_millis(2_000)` (killer) and
     `took >= Duration::from_millis(1_800)`; `report.connections_closed == 2`;
     `report.inbound_frames_discarded == 0`; `report.outbound_frames_discarded
     >= 1`; steady reads its 3 frames then `Err(Peer{1})`; stalled reads
     prefix k < 8 then `Err(Peer{1})`; `k + report.outbound_frames_discarded
     <= 8`.
   - Mutant: apply (e) → `took < 2_000` fails. Record, restore.

## Open questions for the user

1. **The 200 ms flake window.** The reserve is capped at 200 ms, so any
   wall-clock test of it has at most 200 ms of one-sided margin (D3/D4). The
   recommended `took < B` (B = 2_000) uses all of it; the mutant can never
   pass, but a > 200 ms deschedule of the test thread could false-fail the
   correct code. *Recommendation:* accept the wall-clock test, run the three
   with `-j 2` and record any failure with its panic line rather than
   retrying it away; if it proves flaky in practice, revisit with a
   product-code hook (out of scope here).
2. **Lower bound needed?** `took >= F` is load-safe and documents the stall,
   but is not a killer. *Recommendation:* keep it; it guards against a future
   change that makes the flush complete early and silently turns `took < B`
   vacuous.
