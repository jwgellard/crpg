# T135 — pool refill amount and maximum setter (`crpg-rules`, ADR-0029 K3(b))

## Task / Crate(s) / Status
ADR-0029 Follow-on row 2: kernel gap K3(b). Today a pool refreshes to its
maximum only, and its maximum is fixed at construction (`resource.rs:1–9`,
`:164–181`). Action-point carry-over (+n per turn up to a cap) and mid-fight
maximum changes need an optional refill amount and a validated maximum setter
that clamps `current`. Sole crate: `crpg-rules` (`src/resource.rs`, a new
test file, and its two docs). The crate change is outside the plan §1.4
S-set. But `ResourcePool` is serialized inside the hashed `World`
(`crpg-sim/src/combat.rs:81`, `:84`, through `Combatant`), so ADR-0029 marks
this row S and its contract and diff are **serialized and human-reviewed**.
Status: **contract proposed — awaits the user's approval.**

## Decision
- **D1. `refill: Option<NonZeroU32>`, private field.** Absent means today's
  full refill. Present `n` means a matching refresh adds `n`, saturating at
  `max`. Zero cannot be written down, so it has no second meaning.
- **D2. `set_max(&mut self, max: u32) -> bool`, infallible.** Every `u32` is
  already a valid maximum (zero included, `resource.rs:70`). "Validated"
  reads as: the setter restores `current <= max` by clamping, so no invalid
  state can result (open question 1).
- **D3. Skip-when-absent serde.** A pool without `refill` encodes exactly as
  today, so no existing hashed byte changes.
- **Rejected:** a `RefreshTrigger` payload for the amount, because it changes
  every trigger's wire and the T015 tests. A fallible `set_max` whose `Err`
  is unreachable. Raising `current` together with `max`: that is a gain
  operation, which has no consumer yet.

## Behaviour
1. **Construction.** `with_refill` validates exactly as `new` does today, in
   the same order. `current > max` fails with `InvalidResource` at
   `/resource/current`, then `OnTick(0)` fails at `/resource/refresh`. The
   `refill` value adds no failure. `new(a, b, c, d)` returns exactly
   `with_refill(a, b, c, d, None)`.
2. **Refresh.** The match rule is unchanged (`resource.rs:165–174`). On a
   match with `refill == None`, `current = max`. On a match with `Some(n)`,
   `current = min(max, current.saturating_add(n.get()))`. The return value is
   `true` exactly when `current` changed. With no match, nothing changes and
   the return value is `false`.
3. **Repeated delivery.** A partial-refill pool gains `n` on every matching
   delivery until it is full, so duplicate deliveries are not idempotent for
   it. The host delivering each logical event exactly once
   (`crpg-rules/AGENTS.md` mutation rules) is now load-bearing.
4. **`set_max(max)`.** It sets `self.max = max`. Then, if `current > max`,
   it sets `current = max`. Raising the maximum never raises `current`.
   `refill` and `refresh` are untouched. It returns `true` exactly when `max`
   changed, which is the only case in which `current` can change.
5. **Invariant.** After every public operation, and after every successful
   decode, `current <= max`.
6. **Equality** is the derived equality and includes `refill`. `Debug` gains
   a `refill` field. No golden or test pins a pool's `Debug` (checked: the
   six goldens and the history goldens are hashes only).
7. **Encode (the hash rule).**
   - H1. With `refill == None` the encoding is byte-identical to today's:
     `{"id":…,"max":…,"current":…,"refresh":…}`, `serialize_struct` length 4.
   - H2. With `Some(n)` it is the same four fields in the same order, then
     `"refill":n` as a decimal `u32`, length 5.
8. **Decode.**
   - H3. `refill` may be absent (`None`) or appear at any key position. A
     present value must be an integer in `1..=u32::MAX`. The values `0`,
     `null`, negatives, `> u32::MAX`, strings and non-integer numbers are
     rejected, and so is a duplicate `refill` key. Unknown keys stay
     rejected. The result then goes through `with_refill` (item 1).
9. **Hash and save compatibility.**
   - H4. Every pool the sim builds today comes from `new`
     (`crpg-sim/src/combat.rs:1368`, `:1377`). `state_hash` is BLAKE3 over
     the World's `serde_json` bytes (`crpg-sim/src/hash.rs:37–47`). So by H1
     every World, save, history journal, `state_hash`, `history_hash`, replay
     golden and history golden stays byte-identical. A `Some` refill enters a
     World only when a later task (T137/T139) builds one.
   - Old saves decode unchanged, because the key is absent.
10. **Docs in code.**
    - The module doc drops "no maximum adjustment API" and says that a
      refresh refills to maximum or by the pool's refill amount.
    - The `RefreshTrigger` first line becomes "When a pool refills."
    - The `RefreshEvent` idempotence sentence is limited to full-refill
      pools, and item 3 is added.
    - The `refresh` doc states item 2. `set_max` and `with_refill` are
      documented per the crate's missing-docs rule.

## Open questions (each with a recommendation)
1. **Is "validated maximum setter" infallible?** The ADR's word can read as
   `Result`. Recommend infallible `-> bool` (D2). Every `u32` is a legal
   maximum, so an `Err` path would be dead API.
2. **Raising `max` leaves `current` alone?** Recommend yes. "Grant the
   difference" is a gain operation; add it with its first consumer.
3. **Allow `refill >= max`, and `refill` on a `Never` pool?** Recommend
   allowing both. `set_max` can later drop `max` below a refill, so a
   construction-time ban would be inconsistent. Such pools behave like
   full-refill or never-refill pools and differ only in hashed bytes.
4. **Representation.** Recommend `Option<NonZeroU32>`, absent meaning full
   refill. H1 falls out of it, and zero cannot be a second spelling of
   anything.
5. **Wire key name.** Recommend `refill`, which pairs with `refresh`. The
   alternative is `refill_amount`.
6. **`set_max` return value.** Recommend `bool` ("max changed"), matching
   `refresh`. A caller that needs the clamped amount reads `current()`
   before and after.
